- §15.2 password verification (task 153, spec §15.2, §15.1; decision D-122): the missing half of `src/services/password-hash.ts` lands beside task 144's hashing (D-118) — one module now owns the whole §15.2 credential format. **`verifyPassword(stored, candidate)`** takes the stored hash exactly as the configuration holds it (`stored: string | undefined` — the optional `auth.passwordHash` field passes straight through, and runtime junk beyond it answers `false` through the same guard) and parses the stored self-describing encoding strictly (exactly four `$`-fields, the one `scrypt` algorithm id, the canonical parameter grammar `N=…,r=…,p=…,keylen=…` — canonical key order, plain decimal, no leading zeros — canonical padded base64 for salt and hash with a re-encode round-trip that rejects non-canonical trailing bits and everything Node's permissive decoder would silently forgive, and internal consistency: the decoded hash byte length must equal the `keylen` the string claims), then re-derives the candidate under **the parameters the string itself carries**, never `SCRYPT_PARAMETERS` — D-118's forward-compatibility rule made executable: a future cost raise changes only what newly set hashes use, and every already-stored hash keeps verifying (pinned with a hand-built `N=16384, keylen=32` encoding whose derivation the test recomputes itself). The derivation runs inside two exported budgets: `VERIFICATION_MAXMEM_BYTES` (1 GiB of memory — sixteen times today's 64 MiB requirement, so any plausible raise verifies unchanged while a corrupt or hostile stored string can never talk the verifier into unbounded allocation: `node:crypto` refuses beyond `maxmem`, and the refusal classifies as a mismatch) and `VERIFICATION_MAX_PARALLELIZATION` (1024 — the CPU twin `maxmem` cannot provide: `p` multiplies compute without touching memory, and an unbounded `p` in a corrupt string could pin a libuv thread for hours, measured `p=4000` ≈ 21 s on the pinned runtime; the producer writes `p=1`, so 1024 is generous). **Constant-time discipline:** the comparison is `timingSafeEqual` over the derived key bytes, never over strings, with the equal-length precondition guaranteed _before_ any secret is touched (the parse rejects self-inconsistent lengths; the encoding's length facts are public — whoever can read them already has the `0600` file), and there is no early exit on candidate content: every candidate under a parseable stored hash costs exactly one full derivation, wrong passwords included. **Fail closed, never throws:** an absent/empty stored hash, any malformed shape (unknown or miscased algorithm id, wrong field count, off-grammar parameters, non-canonical base64, `keylen` disagreement), and parameter sets `node:crypto` refuses (a non-power-of-two `N`, a set beyond the ceiling) all answer `false` — an unverifiable credential is a wrong password to this function, never an error and never an accept. Parameter _semantics_ stay with `node:crypto` as the single authority (the parse owns structure plus the module's own two budgets — no mirrored validation table to drift); the operator-facing diagnosis of a corrupt configuration belongs to the config layer. **No §15.1 seam wiring, by design:** the `RequestAuthenticator` seam authenticates _requests_, which carry session cookies (154/155) — the password is presented only at the login endpoint, which stays public through `PUBLIC_AUTH_ROUTE_CONFIG` and consumes this primitive there; the seam's docblock and the server README now say exactly that. The done-condition ("password verification and invalid-password paths are tested") is pinned executably by the extended `test/unit/password-hash.spec.ts` (24 new cases): the round-trip against the module's own `hashPassword` (accept/reject), unicode accept/reject, the string-parameters pin, a seventeen-row malformed-encoding table (empty, unknown and miscased algorithm ids, missing/trailing fields, swapped order, unknown key, non-numeric, leading-zero and zero values, non-canonical / non-quantum / non-zero-trailing-bits / empty base64 fields, `keylen` disagreement, `p` beyond the CPU ceiling), the absent (`undefined`) and JS-boundary (`null`, number) stored-hash rows, and both `node:crypto` refusal arms (`N=1`; a parameter set beyond the memory ceiling, derived from the exported bound so the pin follows it) — deterministic (no clocks, fixed salts where determinism matters), each invalid path asserted through `resolves` (fail closed is also never-throws).
