## [Unreleased]

### Changed

- Mutation-report score now follows Stryker's own formula (decision D-055): `detected / scoreable` per file and overall, with ignored and error-status mutants excluded from the denominator but still visible as counts — the issue's score can no longer disagree with the verdict line once deliberate in-code Stryker ignore comments exist (U-006).

### Fixed

- Z.ai metric derivations stay finite (task 101, spec §8.4; decision D-057): an arithmetic derivation (`remaining = limit − used`, `used = limit − remaining`, `limit = used + remaining`, `percentUsed = 100 · used / limit`) or the `windowSeconds = number × 3600` scaling whose result overflows IEEE-754 finiteness (extreme magnitudes; zero allowances in a quotient) now leaves the field absent and unlisted instead of emitting `Infinity`/`NaN` values the shared §8.4 snapshot invariants reject — the supplied values survive and the metric stays valid. Zero-allowance behavior from task 100's review is unchanged: result-finiteness subsumes the old `limit !== 0` guard.
- The rolling mutation-report issue no longer shows a self-contradictory 0% report: the renderer (extracted to `scripts/render-mutation-report.mjs`, now callable by the workflow and by hand against any artifact JSON) normalizes Stryker's PascalCase mutant statuses, so the score, per-file table, and survived triage list match the report JSON, with runtime/compile-error mutants surfaced as counts and files (U-005, decision D-054).
- The daily mutation workflow now bootstraps its `mutation-report` label idempotently before first use: `gh issue create --label` requires the label to already exist and cannot create it, which failed the workflow's validation run at the issue-upsert step (U-004).
- `npm audit` restored after the npm registry retired the quick-audit endpoint: the dev image and CI now pin npm 11 (bulk advisory endpoint) while Node stays at the 22.13.0 minimum.

### Added

- Within-cycle retry/backoff (spec §7.2) in `src/services/polling-retry.ts` (task 106, decision D-059): `runCycleWithRetries` wraps one collection-cycle attempt and retries network failures, timeouts, and HTTP 5xx up to three times with the exponential 2/4/8 s delays plus a uniform bounded jitter of 0–500 ms — eligibility delegated in full to task 105's `classifyTransportError().retryable`, so 429, 401/403, and parse defects report immediately with a single attempt. The result object `{ ok, value | error, attempts }` never throws for provider failures and carries the total attempt count (1–4) that `collection_runs.attempts` will persist; a caller abort interrupts the backoff and surfaces as `TransportAbortError` (the `'cancelled'` pseudo-outcome); the per-attempt 15 s request timeout stays with the transport, a timed-out attempt being simply one more retryable failure. Randomness and sleep are injectable seams; fake-timer tests prove the counts and exact delay/jitter boundaries, and integration tests pin eligibility and attempts against the mock provider server over real sockets.
- Atomic collection-cycle persistence (spec §11.1) in `src/storage/collection-cycles.ts`: `persistCollectionCycle(repository, cycle)` writes the run row every cycle leaves behind — successful or not — and, in one `withTransaction` unit, the snapshot, its metric rows, and its reset events (a parse-failure cycle carries its §7.4 sanitized payload beside the run instead; other failures carry only run evidence). The writer supplies every identity field — the cycle's account, the assigned run id, the snapshot's collection time — so metric/event/payload inputs cannot express D-039 denormalization drift or a wrong-account event. Any failure — a named CHECK, a UNIQUE collision, or a driver-level throw — rolls the whole cycle back and propagates unchanged; the done-condition ("injected failures leave no partial snapshot") is verified by failures injected at every insert position, each asserting zero residue (decision D-060; task 089).
- Typed repository facade `QuotaRepository` (spec §8.1/§11) in `src/storage/repository.ts`: synchronous CRUD/query methods over every §11.2 table plus `meta` — accounts (insert/get/list/update/archive-once/cascade-purge), collection runs (insert returning the assigned id, latest-by-outcome for §7.3 status, filtered history), snapshots (success-only by structure — the composite FK makes an error cycle unable to create one), metric values (the §8.4 persisted model with `derived_fields` bitmask encode/decode and the `metric_values_series_access`-served series query), quota events (§12.1 evidence JSON round-trip), raw responses (parse-error-only by structure, newest-first bounded listing), sessions (digest lookup, joint last-seen/expiry refresh, single/all/expired deletes), and meta key/value upsert — with `withTransaction` as the §11.1 atomicity seam task 089 composes, writer-supplied timestamps everywhere, and the named CHECK constraints as the write gate (decision D-058). The task-088 done-condition is mechanically enforced: `test/unit/storage-sql-gate.spec.ts` fails the build on any uppercase house-style SQL statement literal outside `src/storage/` (a tripwire against accidental ad hoc SQL complementing the existing `node:sqlite` import gate — deliberately not a security boundary, D-058); `test/integration/repository.spec.ts` pins the surface against the canonical schema.
- Property-based derived-field audit (task 101, spec §8.4/§17.1) in `test/unit/zai-coding-plan-mapping.property.spec.ts`: the done-condition — percentages are never used to invent token counts — is proven over every recognized identity and arbitrary finite percentages (no absolute fields, `unit: PERCENT`, verbatim `percentUsed`, `percentRemaining = 100 − percentUsed`, `derivedFields` exactly `['percentRemaining']`), and a generated field-subset oracle (exact and provably violated triples, arbitrary field presence, IEEE-754 extremes always in play) holds every derivation path to its exact firing condition, exact value, `derivedFields` recording, the no-chaining rule, and the shared snapshot invariants. Example additions pin the overflow guards, the window-scaling overflow, a lone allowance, and a derived `remaining` beside a supplied percentage.
- `sessions` and `meta` tables (spec §11.2/§15.2) as canonical migration `0007-sessions-meta` in `src/storage/migrations.ts` — the last §11.2 tables, in one entry: sessions store only the SHA-256 hex digest of the cookie token as their identity (an exact 64-lowercase-hex-char CHECK — the raw token's non-hex wire forms cannot fit and the pinned column set admits no raw/cookie/secret column; D-056 records the non-hex cookie-encoding precondition task 154 must keep, a hex cookie being shape-identical to the digest), with `created`/`last-seen`/effective-expiry timestamps and both §15.2 bounds CHECK-enforced (`expires_at <= created + 30 d` absolute, `expires_at <= last_seen + 7 d` inactivity, durations exported as `SESSION_MAX_AGE_MS`/`SESSION_INACTIVITY_TIMEOUT_MS`); the spec-named `sessions_expiry` index proven used via query plans for §11.3's expired-session cleanup. `meta` is the exact key/value service-state table (non-empty key, any TEXT value) for task 091's cleanup metadata. Neither table is account-bound — purging accounts leaves both untouched (decision D-056).

### Fixed

- Invalid-JSON configuration problems no longer echo raw input regions that may contain secrets: every V8 `JSON.parse` snippet shape is cut at the first double quote (U-003, decision D-033).
- Intermittent child-process failures in the server lifecycle tests (U-001): the tests now wait for a `signals-ready` marker — emitted through the new `runServer` `onSignalsReady` seam — before sending SIGTERM/SIGINT, eliminating the kill-before-handler race (decision D-024).
- Same kill-before-handler race closed in the single-instance SIGTERM child test (U-002): the runner emits `signals-ready` through the existing seam and the test waits for it before signaling the holder child (decision D-035).
