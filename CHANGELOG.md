## [Unreleased]

### Added

- MIT `LICENSE` and attribution `NOTICE` files.
- Project documentation: technical specification, implementation task plan, decision log, contributing guide.
- Docker-based development environment pinned to Node.js 22.13.0 with isolated data volumes.
- Testing foundation: Vitest (unit, integration, component projects), Playwright E2E smoke and accessibility checks, fast-check property tests, local mock provider server, no-network guard.
- Quality gates: ESLint with security and i18n rules, strict TypeScript for server and UI, Prettier formatting, coverage thresholds, Stryker mutation testing.
- CI pipeline: Node.js matrix, Ubuntu/Debian clean-install containers, tarball allowlist check, unsupported-Node behavior test, Dependabot.
- Bootstrap `quotameter` CLI binary reporting the package version with a runtime version gate.
- Application package layout: layered `src/` modules (schemas, util, config, providers, storage, services, server, cli) with documented dependency rules enforced by a structural import-direction test.
- Server bootstrap: process entry point with a runtime gate (Node.js >= 22.13.0, non-root), signal-driven startup/shutdown, and the application lifecycle skeleton in `src/server/`.
- Normalized snapshot and metric model (spec §8.4) in `src/schemas/metrics.ts`: closed `LimitType`/`MetricUnit`/derived-field enums with runtime guards, `ProviderSnapshot`/`NormalizedMetric` types, and spec invariant checks shared by server, storage, API, and UI.
- Central typed configuration contract (spec §6.2) in `src/schemas/config.ts`: TypeBox schemas for server, app, auth, logging, providers (incl. peak-hours), and accounts, with derived types, spec defaults, and cross-field invariant checks; adds the `@sinclair/typebox` runtime dependency.
- XDG path resolution (spec §6.1) in `src/config/paths.ts`: config/data directories from `XDG_CONFIG_HOME`/`XDG_DATA_HOME` defaults with `QUOTAMETER_CONFIG_DIR`/`QUOTAMETER_DATA_DIR` overrides (decisions D-011, D-012).
- Published JSON Schema for `config.json` (spec §6.2, §18) at `schema/config.schema.json`: generated from the configuration contract, shipped in the npm tarball, documented for editor validation (decision D-015).
- Atomic configuration writes (spec §6.3) in `src/config/write.ts`: serialize, same-directory temp file (`O_EXCL`), `fsync`, `rename`, with the file mode pinned to `0600` on every write — interrupted writes can never promote a partial config (decision D-016).
- Provider contracts and `ProviderRegistry` (spec §8.1) in `src/providers/registry.ts`: the `QuotaProvider` interface over the normalized snapshot model, a branded `AccountContext` factory whose secret cannot travel into logs by accident, and a fail-fast registry (duplicate/unknown-id errors).
- Single-instance protection (spec §5.6) in `src/server/single-instance.ts`: an atomic lockfile per data directory (`createSingleInstanceLock` lifecycle component) that refuses a second process with an actionable error, breaks stale locks of dead pids, and releases on shutdown (decision D-017).
- Configuration loading and validation (spec §6.2) in `src/config/load.ts`: the `config.json` loader that compiles the TypeBox contract with Ajv (2020-12), rewords validation failures into field-addressed English problems that never echo secrets, and completes spec defaults into a canonical configuration — invalid configuration cannot silently reach runtime services (decision D-018).
- Configuration permission enforcement (spec §6.3, §15.4) in `src/config/permissions.ts`: startup creates the config directory `0700` (umask-proof at every level), verifies/fixes directory and file to exactly `0700`/`0600`, and refuses to start when unsafe permissions cannot be corrected — foreign ownership, symlinked objects, or an ineffective `chmod` (decision D-019).
- Graceful-shutdown coordination (spec §5.6) in `src/server/shutdown.ts`: a shared in-flight tracker plus the `graceful-drain` lifecycle component that waits for active work — bounded at 10 s — between scheduler shutdown and storage close (decision D-020).
- Environment-variable overrides (spec §6.3, §6.4) in `src/config/env.ts`: `QUOTAMETER_*` variables for the scalar settings apply on top of `config.json` (environment wins; environment-only configuration works when the file is absent), values fail through the same parser as the file, unknown `QUOTAMETER_*` names are rejected, and the result reports which fields and account secrets came from the environment for read-only UI marking (decision D-023).
- Clock/time utility (spec §10) in `src/util/clock.ts`: injectable epoch/monotonic clock, branded IANA zone validation aligned with the configuration contract, UTC epoch↔ISO conversions, and Luxon-based zoned formatting — business logic never depends on implicit machine-local time (decision D-021); adds the `luxon` runtime dependency.
- Structured redacting logger (spec §16, §15.4) in `src/util/logger.ts`: a Pino JSON-lines logger factory with deep secret redaction (sensitive key names at any depth, known secret values in any string, error payloads incl. cause chains), all-six-level emitters proven marker-secret-free at every level, a synchronous never-throwing lifecycle sink for the server seams, and the raw Pino instance exposed as the base for the HTTP logger (decision D-025); adds the `pino` runtime dependency.
- Service settings validation (spec §5.3, §6, §7.1) in `src/services/config-validation.ts`: the `validateSettings` entry point for externally supplied settings — string-answer coercion, blank-means-not-supplied, a keep-or-change merge over the current configuration, and the plaintext-password rules of §15.2 — with every range, enum, and cross-field check delegated to the landed configuration parser, so invalid settings surface as field-specific English problems (decision D-022).
- Configuration reload (spec §5.2, §6.2, §6.4) in `src/config/reload.ts`: re-runs the load pipeline on request, classifies changes per §6.4 (`applied` / `pending-restart` / `rejected` result), atomically swaps the effective configuration on success, keeps the last valid configuration after a failed reload, re-applies environment overrides, and reports restart-requiring fields against the startup baseline (decision D-026).
- Forward-only migration harness (spec §3, §11.4) in `src/storage/migrations.ts`: Umzug wired to the built-in `node:sqlite` driver through a journal-table storage adapter — each migration and its journal entry commit atomically, re-runs are no-ops, applied/pending state is queryable, and a failed migration rolls back whole and stays pending (decision D-027); adds the `umzug` runtime dependency.
- Coverage-consolidation tests for the Stage-7 lifecycle and configuration core (spec §17.1): bootstrap-default assembly in `runServer`, the reload environment snapshot's construction-time pinning, environment composition rejections, atomic-write cleanup-failure swallowing, single-instance refusal wrapping (unreadable locks, failing liveness probes), the secret-safe `parseJson` snippet strip, and the `formatSchemaError` totality vocabulary — remaining untestable branches recorded as findings (decision D-028).
- Architecture decision overview (task 077, spec §18) in `docs/architecture/decision-overview.md`: the maintainable narrative tying the decision log together — why Umzug, the executable package layout, the TypeBox+Ajv configuration contract, and the island/registry provider model were chosen, with trade-offs and deferred-work pointers for maintenance.
- Database connection (spec §11.1) in `src/storage/connection.ts`: opens `<data>/quotameter.sqlite` automatically, applies and verifies the required pragmas (`journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`), refuses databases that cannot hold them, and closes idempotently (decision D-030).
- Migration metadata and version checks (spec §11.4) in `src/storage/migrations.ts`: versioned migration names with strictly increasing application order, the canonical migration set tasks 081–087 grow, a read-only applied-migrations journal query, and the schema-version status (`up-to-date`/`behind`/`newer`) that startup and the task-092 newer-schema refusal consume (decision D-031).
- `accounts` table (spec §11.2) as the first canonical migration `0001-accounts` in `src/storage/migrations.ts`: stable account ids and provider ids CHECK-constrained to the URL-safe D-014 charset, label, optional plan name, an `active`/`archived` enum tied to its timestamp, and epoch-ms timestamps with no SQL defaults — no credential columns (secrets stay in the config file, §11.1/§15) and archiving keeps rows queryable (spec §8.2) (decision D-032).
- `collection_runs` table (spec §11.2/§7.2) as canonical migration `0002-collection-runs` in `src/storage/migrations.ts`: one row per polling cycle with outcome constrained to §7.2's seven classes, wall-clock start/end, interval in effect, HTTP status, total attempts, retry-after, already-sanitized error text (success runs stay error-free), a cascading account reference, and the spec-named account/start and account/outcome/start indexes proven used via query plans (decision D-034).
- `snapshots` table (spec §11.2/§8.4) as canonical migration `0003-snapshots` in `src/storage/migrations.ts`: one header row per successful run — unique run reference, account reference, collection time, optional plan name — with the success-only linkage enforced structurally through a composite foreign key over the run's account, id, and outcome, and the spec-named account/time index proven used via query plans (decision D-036).
- Z.ai Coding Plan provider dossier (task 094, spec §8.3) in `docs/providers/zai-coding-plan.md`: dated official-documentation research snapshot (2026-10-30) covering the fourteen sources checked (one not retrievable) — establishing that no authenticated quota/usage/statistics endpoint, request contract, or example response is documented anywhere in official Z.ai docs (the official OpenAPI spec lists only model/tool endpoints), what else is and is not specified (peak hours unchanged, credits/reset rules, key types), and what tasks 095–097 must therefore obtain from the prototype and a sanitized live response.
- Response sanitization (spec §7.4, §15.4) in `src/providers/sanitize.ts`: `sanitizeRawResponse(body, secrets)` redacts exact secret values wherever they occur (nested values, arrays, substrings, object keys, unparsable text) and empties sensitive-named fields using the logger's D-025 vocabulary (so usage fields like `tokens` survive), then caps the payload at 64 KiB UTF-8 — codepoint-safe deterministic truncation, marker included — as the text the `raw_responses` store (086) and `quotameter doctor --raw` (103) will consume (decision D-041).
- Verified Z.ai quota-data source (task 093, spec §8.3/§20) appended to the provider dossier: the original prototype (`glm-quota`) reads three undocumented `api.z.ai` monitor/biz endpoints (`/api/monitor/usage/quota/limit`, `/api/biz/subscription/list`, `/api/biz/customer-package-reset/list?targetType=PERSONAL`) with the Coding Plan Bearer key — live-probed 2026-10-30 (all HTTP 200) and corroborated by path strings inside the first-party ZCode client for two of the three — with full sanitized response shapes, window-unit semantics (`unit` 3=hours/5=months/6=weeks), the observed-vs-inferred split, open interpretation questions, and consequences for tasks 095–098 (decision D-038).
- `metric_values` table (spec §11.2/§8.4) as canonical migration `0004-metric-values` in `src/storage/migrations.ts`: one row per metric per snapshot — the persisted §8.4 normalized metric with denormalized account/time pinned to its snapshot by a composite foreign key, `limit_type`/`unit` enums mirrored from the canonical model, REAL quota values, validity invariants (a valid row needs at least one numeric; an invalid row stores NULL numerics plus a reason, never zero placeholders), a bitmask `derived_fields` bound to D-010's closed set with each derived bit coupled to its column's presence, and the spec-named series-access index proven used via query plans (decision D-039).
- Sanitized Z.ai Coding Plan fixtures (task 095, spec §8.3/§17.1) under `test/fixtures/sanitized/`: one redacted live-capture response (2026-10-30) per verified endpoint — structure and closed vocabularies kept verbatim, every account-linked value re-invented — plus three synthetic error-shape fixtures (empty limits array, unknown limit type, malformed envelope) for the upcoming parsing tests; the §8.3 availability statement and approval live in the provider dossier (decision D-040).

### Fixed

- Invalid-JSON configuration problems no longer echo raw input regions that may contain secrets: every V8 `JSON.parse` snippet shape is cut at the first double quote (U-003, decision D-033).
- Intermittent child-process failures in the server lifecycle tests (U-001): the tests now wait for a `signals-ready` marker — emitted through the new `runServer` `onSignalsReady` seam — before sending SIGTERM/SIGINT, eliminating the kill-before-handler race (decision D-024).
- Same kill-before-handler race closed in the single-instance SIGTERM child test (U-002): the runner emits `signals-ready` through the existing seam and the test waits for it before signaling the holder child (decision D-035).
