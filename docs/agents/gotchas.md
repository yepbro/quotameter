# Known pitfalls

Lessons already paid for — do not repeat them.

## Container / host boundaries

- **Container-side writes to host-owned tracked files used to fail with EACCES — resolved by D-181 (the container now runs as the host user; see [environment.md](environment.md) "Matching the host user").** Root cause: the `node` base image's user is uid 1000, this host's user is uid 1001, and tracked files are `1001:1001` mode 664 — group/other have no write. It bit live on 2026-11-06 (`prettier --write docs/agents/review.md` inside the dev container during the 67b75c1 formatting fix, worked around with a temporary `chmod 666`), and it was structural: `make format` / `make lint-fix` write only the files that _need_ changing — exactly the host-owned ones — so they failed precisely when they had work to do, even though a clean tree formatted fine. The fix bakes the host uid/gid into the image (build args `DEV_UID`/`DEV_GID`, exported by the Makefile); container-side format/lint-fix/codegen rewrites of tracked files now just work.
- **Generated output still goes to the data volume** (`REPORTS_DIR`, `DIST_DIR`, `COVERAGE_DIR`, `E2E_OUTPUT_DIR`, Stryker `tempDirName`) — not because of local EACCES (gone since D-181) but to keep artifacts out of the tracked tree under one convention on every runner; a new tool writing generated files into the repo from the container breaks `git status` cleanliness and the pattern — see [environment.md](environment.md).
- **After adopting D-181, pre-existing environments must migrate their volumes.** Volumes created before the fix are owned by uid 1000; once the image is rebuilt as the host user, the first container write _inside the volumes_ fails with EACCES — a coverage/reports/build-output write, or `npm ci` when the lockfile changed (`make deps` alone can pass untouched with an up-to-date stamp, so a healthy deps run is not proof of migration). Check which uid an environment runs as with `docktree exec dev -- id`. Disposable worktree: `make clean && make image && make up`. Data-preserving recipe (the main tree): the chown loop in [environment.md](environment.md) "Migrating a pre-D-181 environment".
- **Direct `docktree build` (outside make) rebuilds at the 1000:1000 defaults and flips the trap back** — the Makefile exports `DEV_UID`/`DEV_GID`, a bare docktree invocation does not, so the image comes back as uid 1000 while the volumes are already host-owned (EACCES everywhere, both directions). Build via `make image` / `make restart`, or pin the ids in the worktree's `.env` (`.env.example` documents them).
- For environments not yet migrated, the pre-D-181 recipe for formatting host-authored files still applies: run `docktree exec -T dev -- npx prettier <file>` (stdout mode, no write) redirected to a temp file, then copy the output back over the repo file from the host — formatting stays in the container (one Prettier version), the write stays with the file's owner.
- Host `node_modules/` can end up root-owned after Docker created the mountpoint: `sudo chown -R brooks:brooks node_modules` (via the askpass helper), then `npm install` works.
- The Playwright download CDN is unreachable from containers — browsers come from the read-only host cache mount.

## CI parity

- **No hosted runner image is a stable systemd-less environment — the systemd-pinned suites get that class from the job container (D-162).** GitHub moved `ubuntu-latest` to the 26.04 image (observed between the green 2026-10-29 and red 2026-11-01 runs), whose job sessions run a **live** systemd user manager — and D-160's follow-up pin to `ubuntu-24.04` proved no better: every hosted image now ships a live user systemd. The real-launcher service tests then really installed a user unit into the runner's passwd home (env `HOME` does not redirect the §5.3 owner) and ~15 suites failed through the cross-test contamination. The fix (D-162) is the job container: CI's `test` job runs `container: node:${{ matrix.node }}` and the mutation workflow `container: node:22.13.0` — a fresh, root-HOME, systemd-less environment per job, immune to image migrations (the workflow's container block says so). The CLI side is already honest on any machine: an inert systemd (marker present, manager dead) routes to the graceful fallbacks per D-160.
- CI runs `typecheck:all` (server `tsc` + `vue-tsc`), `test:ci` (coverage + thresholds), `check:package`, and e2e on every push; mutation testing runs once a day in `.github/workflows/mutation.yml` (rolling `mutation-report` issue, DECISIONS.md D-045), not per push. A green local `make test` proves nothing about thresholds — `make check` runs the same `test:ci` coverage pass (global 90% over `src` + `ui/src` combined, the UI's own 90% aggregate key, and the D-085 critical-module 100% keys — the map widened by U-060/D-188) — and both `make check` and `make check-all` run `typecheck-all`, the same `typecheck:all` command CI's `static` job runs, so a UI type error is caught before committing too (D-092; the standalone `make typecheck` remains the fast server-only loop); `make check-all` remains the pre-push gate (it mirrors the per-push CI exactly; run `make mutation` manually when you need Stryker locally).
- Commit message conventions are checked by humans only, but the workflow files are linted with `actionlint` (docker: `rhysd/actionlint`) — run it after editing workflows.
- **The CI supply-chain pins are repository content plus repository metadata — the two halves fail differently (U-033, decision D-157).** The `install` job's Node runtime archive is verified against SHA-256 digests pinned in the workflow itself (repository history is the one trust domain a compromised nodejs.org CDN cannot rewrite); `test/unit/ci-workflow.spec.ts` pins the exact download/verify/extract shapes and the version consistency across every site, so a Node bump that skips one site (the `version=` line and step name, the digest arms, the `node -v` expectation, the unsupported-node grep, `package.json` `engines.node`, the Dockerfile `FROM node:` tag, the guard's own constants) fails `make check` with a message naming the miss — bump through the procedure documented in the workflow's comment, never by editing one line. The Dependabot `dependencies` label, in contrast, is **repository state, not content**: a label listed under `labels:` that is missing from the repository is silently ignored by Dependabot (documented behavior — the U-004 failure class), and no workflow can bootstrap it (nothing of ours runs before Dependabot opens PRs; Dependabot auto-creates only its own defaults, not `labels:`-assigned ones) — if it ever goes missing, the repair is the documented one-liner in `dependabot.yml`'s header and `docs/agents/workflow.md`, not a config change.

## Test stability under parallel load

- **Strict-equality parity against a third-party resolver is season-dependent on ambiguous DST readings — assert occurrence membership there.** Luxon (and similar offset-guessing resolvers) resolves an ambiguous wall time from a guess seeded by the _current instant_ (decision D-079's recorded caveat), so which valid occurrence it returns flips with the schedule zone's season — while every returned instant stays a genuine occurrence. Observed live 2026-11-01: `test/unit/peak-hours-dst.property.spec.ts`'s every-minute Luxon-parity sweep went red the day America/Havana crossed to standard time (the zone's ambiguous midnight resolved to the second occurrence all winter) after months green, with no code change anywhere. The fix pattern, now in that suite: keep strict `toBe` parity for unambiguous and gapped readings (those converge seed-invariantly — verified for the matrix zones), assert `toContain` against the oracle's full occurrence set for ambiguous readings, and pin the seeding mechanism executably (Luxon `Settings.now` overridden to both seasons — the regression sits next to the sweep). Any new test asserting exact equality against a resolver it does not own must first ask whether the input is ambiguous in a DST zone.
- **Compute-bound property tests declare explicit per-test timeouts — Vitest's default 5 s is a flake under parallel-wave load.** A property doing ~100 fast-check runs over `size: 'max'` series with brute-force oracle walks is legitimately compute-bound: the downsample cluster property measures 0.95 s clean, 1.4 s under v8 coverage (permanent in `make check` since D-085), and **6.8 s** worst in a full coverage run under the starvation rig — past the default at exactly the ambient load (~18) where U-012's matrix flaked it. ## Test infrastructure

- **Real-launcher children must not inherit the session manager: build the child env through `hermeticChildEnv` (U-045, decision D-173; adopted in `cli-init-yes.spec.ts` — `cli-init.spec.ts`, `cli-init-idempotent.spec.ts`, and `cli-init-service.spec.ts` still spawn with the parent environment and stay correct only in the D-162 systemd-less class).** A spawned `bin/quotameter.mjs` runs the §5.3 step-7 service-setup probe against the machine it lands on, and on a host with a live user systemd (every hosted runner image since GitHub's 26.04 migration — D-162) the inherited `XDG_RUNTIME_DIR` does not just let the child OBSERVE that manager, it makes it ACT: the `user-unit` route executes `systemctl --user daemon-reload` + `enable --now quotameter.service` against one shared unit name whose `quotameter run` ExecStart exits 1 (no configuration in the unit's clean env) and auto-restarts — so the start-job outcome is machine state at the instant of the call. That is what killed the daily mutation runs of 2026-11-02→04: Stryker's initial test run failed `cli-init-yes`'s reproducibility cell — both launcher runs byte-identical through the whole collected block (including the guard-blocked `provider-unavailable` connection-test row) and diverging at the first service-setup line, run 1's `enable --now` exiting 0 ("installed the user service") against run 2's `Job for quotameter.service failed because the control process exited with error code.` (the "could not be enabled automatically" fallback) — while push CI and local `make check` (the systemd-less job containers) stayed green, and Stryker's ~40-character assertion truncation hid the bytes from the logs (the divergence was re-captured in privileged systemd containers on both Debian 252 and Ubuntu 26.04/257, and reproduced only under concurrent invocations — the dry run's parallel load; sequential pairs stay green, which is why only the daily gate saw it). The machine-coupling has a second face the same jobs expose: the probe's own 10-second timeout race — `cli-init-service.spec.ts` passed beside the failing cell, and on a systemd host its asserted absent-route text is reachable only through the probe timing out, so the race was firing under the dry run's saturation and can split the absent/present routes between two back-to-back runs. The fix lives at the spawn boundary because the real launcher offers no seam to inject (D-162's own reason): `test/helpers/hermetic-child-env.ts` strips `XDG_RUNTIME_DIR` and the `DBUS_*` session addresses, so the probe never spawns the user query (`userManager: false` by construction) and the step takes the deterministic write-only `user-manager-unavailable` route on systemd machines — byte-identical between runs, D-100's contract intact (byte-identity was always over "flags + environment"; the environment's one mutable dimension is now pinned; verified 160/160 cells green across 8 concurrent full-suite runs on the live-systemd box that reproduced the failure). Two residuals are documented, not fixed: on a live-systemd machine that route still WRITES the unit file under the invoking user's passwd home (`HOME` does not redirect the §5.3 owner — D-162), and a saturated live-systemd machine can still flip the read-only system-manager probe between absent and present through its 10-second timeout race — nothing at the env boundary can pin a machine fact, which is why the daily gate's guarantee is the D-162 systemd-less job container, not the helper alone. When a byte-identity assertion can still fail someday, make it self-evidencing: the reproducibility cell dumps BOTH full normalized stdouts AND both stderrs (the original diagnosis lived on stderr) plus the divergence offset in its assertion message, and compares stderr for identity too (never rely on a runner to show the diff — Stryker truncates).

- **The no-network guard is a tripwire, not a sandbox (U-031, decision D-154).** `test/helpers/network-guard.ts` inspects every `fetch` input shape — `string`, `URL`, and `Request` get their host extracted (reading exactly what fetch reads: the stringified URL and the Request's internal-slot-backed `url` getter, never shadowable accessors); anything else is rejected outright, because fetch webidl-coerces non-Request objects via `ToString` and any property-based guess would inspect a decoy — and intercepts `node:http`/`node:https` at `Agent.prototype.createConnection`, so the global agents, `agent: false` default agents, and custom `new Agent()` instances alike are covered. It deliberately does **not** cover: a `createConnection` passed as a request or agent option, direct `node:net`/`node:tls` sockets, direct `undici` module imports (`undici.fetch`, `undici.request`, `setGlobalDispatcher`), `node:dns`, and **fetch redirect following** (undici follows a `3xx Location` to an external origin after the initial input is inspected — a loopback mock answer can therefore redirect a test fetch off-host; keep `redirect: 'error'` in test fetches, as the provider transport does) — closing those would mean intercepting socket creation or response processing process-wide, invasive far beyond §17's "tests must not require a real API key or internet access" intent. Consequences for test authors: never reach for those paths against anything but loopback (use `test/helpers/mockProviderServer.ts` on 127.0.0.1), and remember a test deliberately opening raw sockets to an external host will not be stopped by the guard — review attention, not the guard, covers that. The guard's own docblock is the canonical scope statement.
- **Playwright's `context().cookies(urls)` filters by URL path, and the session cookie is path-scoped to `/api`.** Querying with the bare origin (`cookies(baseUrl)`) returns an empty jar even though the browser stores and sends the cookie — RFC 6265 path-matching excludes `/` from a `/api`-scoped cookie. Query the cookie's own path (`cookies(`${baseUrl}/api`)`) and filter by name (names are not URL-shaped; passing a cookie name as the URL argument throws `Invalid URL`). Bit the task-183 auth scenario live.
- **Seeded §12.2 timeline worlds: run stamps, not just valid metric points, participate in the silence judgments — and any finite history inside a wide range carries a leading stopped period.** `buildTimelineIndicators` walks the RUN sequence (every outcome): each inter-run silence beyond three intervals is a stopped-service region, and the range-start → first-run silence is one too, so "a couple of successful cycles plus one gap" in a 7-day window is NOT `1 gap / 0 stopped` — the leading region plus every inter-run pair counts (observed: `2 collection gaps, 4 stopped periods` from four runs with two long silences). The gap service likewise judges silences between stamps that include non-success runs. For exact marker-count assertions, shape the world deliberately: place every non-gap pair far under the threshold (a failed cycle 5 minutes after a success adds its error marker without a silence), isolate exactly one beyond-threshold silence, and count the leading stopped region in the expectation — the `test/e2e/acceptance/chart-markers.spec.ts` world documents its arithmetic inline.

## Tooling quirks

- **ESLint flat presets**: `@intlify/eslint-plugin-vue-i18n`'s `flat/recommended` is an **array**, not an object — spreading it into a config object breaks with `Unexpected key "0"`. Register the plugin manually and enable the single rule instead.
- **Prettier vs `eslint-plugin-vue`** disagree about line breaks in short `<p>` elements: the residual warnings in the UI's short `<p>` lines (`ui/src/views/*.vue` today) are expected; do not "fix" them (the two formatters will ping-pong).
- **Vitest project `sequence.sort`** does not exist — use `sequence.shuffle: false` for determinism.
- **`node:sqlite`** imports fine on 22.13.0+ but prints an `ExperimentalWarning` — expected, not an error.
- **`npm pack`** silently skips allowlisted-but-missing files (`LICENSE`/`NOTICE` were reserved before they existed) — the allowlist check only fails on _unexpected_ entries.
- **Dependabot PRs** go `BEHIND` after every merge (strict branch protection): rebase each remaining PR (`@dependabot rebase`) before merging it.
- **A tsconfig that `extends` another inherits its `exclude` — resolved against the _base_ config's directory, and an explicit `exclude` in the extending config replaces both the inherited one and TypeScript's defaults (`node_modules`, `bower_components`, …).** This bit `ui/tsconfig.json`: its `include` named `../test/component/**/*.ts`, but the inherited root `exclude: ["test/component"]` (root-relative, i.e. exactly that directory) killed it, so the component specs were type-checked by no project while both `tsc` and `vue-tsc` stayed green (U-030). An extending config whose include reaches outside its own directory must verify the inherited `exclude` does not remove its includes — override or redeclare the `exclude` when it does (a redeclared `exclude` must itself re-cover whatever defaults matter; U-030's `["**/node_modules"]` restores the `node_modules` default only). Verify ownership with `--listFiles` per project rather than trusting that an include line takes effect.
