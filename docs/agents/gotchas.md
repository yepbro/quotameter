# Known pitfalls

Lessons already paid for — do not repeat them.

## Container / host boundaries

- The container (uid 1000) cannot write into host-owned bind-mount dirs (uid 1001). Every generated directory must be env-configured into the data volume (`REPORTS_DIR`, `DIST_DIR`, `COVERAGE_DIR`, `E2E_OUTPUT_DIR`, Stryker `tempDirName`). A new tool writing into the repo from the container will hit `EACCES` until it follows the pattern — see [environment.md](environment.md).
- **Host-authored files cannot be auto-formatted from the container: `prettier --write` hits the same `EACCES`, and making the container own repo files would invert the uid invariant.** The working recipe for files created host-side (an agent's file tool): run `docktree exec -T dev -- npx prettier <file>` (stdout mode, no write) redirected to a temp file, then copy the output back over the repo file from the host — formatting stays in the container (one Prettier version), the write stays with the file's owner.
- Host `node_modules/` can end up root-owned after Docker created the mountpoint: `sudo chown -R brooks:brooks node_modules` (via the askpass helper), then `npm install` works.
- The Playwright download CDN is unreachable from containers — browsers come from the read-only host cache mount.

## CI parity

- **`ubuntu-latest` is not a stable test environment — the systemd-pinned suites run on the pinned 24.04 image (D-160).** GitHub moved `ubuntu-latest` to the 26.04 image (observed between the green 2026-10-29 and red 2026-11-01 runs), whose job sessions run a **live** systemd user manager; the real-launcher service tests then really installed a user unit into the runner's passwd home (env `HOME` does not redirect the §5.3 owner) and ~15 suites failed through the cross-test contamination. CI's `test` job and the mutation workflow pin `runs-on: ubuntu-24.04`; re-pointing them at a newer image means re-working those suites' environment premises first (the workflow comments say so). The CLI side is already honest on any machine: an inert systemd (marker present, manager dead) routes to the graceful fallbacks per D-160.
- CI runs `typecheck:all` (server `tsc` + `vue-tsc`), `test:ci` (coverage + thresholds), `check:package`, and e2e on every push; mutation testing runs once a day in `.github/workflows/mutation.yml` (rolling `mutation-report` issue, DECISIONS.md D-045), not per push. A green local `make test` proves nothing about thresholds — `make check` runs the same `test:ci` coverage pass (global 90% plus the D-085 critical-module 100% keys) — and both `make check` and `make check-all` run `typecheck-all`, the same `typecheck:all` command CI's `static` job runs, so a UI type error is caught before committing too (D-092; the standalone `make typecheck` remains the fast server-only loop); `make check-all` remains the pre-push gate (it mirrors the per-push CI exactly; run `make mutation` manually when you need Stryker locally).
- Commit message conventions are checked by humans only, but the workflow files are linted with `actionlint` (docker: `rhysd/actionlint`) — run it after editing workflows.
- **The CI supply-chain pins are repository content plus repository metadata — the two halves fail differently (U-033, decision D-157).** The `install` job's Node runtime archive is verified against SHA-256 digests pinned in the workflow itself (repository history is the one trust domain a compromised nodejs.org CDN cannot rewrite); `test/unit/ci-workflow.spec.ts` pins the exact download/verify/extract shapes and the version consistency across every site, so a Node bump that skips one site (the `version=` line and step name, the digest arms, the `node -v` expectation, the unsupported-node grep, `package.json` `engines.node`, the guard's own constants) fails `make check` with a message naming the miss — bump through the procedure documented in the workflow's comment, never by editing one line. The Dependabot `dependencies` label, in contrast, is **repository state, not content**: a label listed under `labels:` that is missing from the repository is silently ignored by Dependabot (documented behavior — the U-004 failure class), and no workflow can bootstrap it (nothing of ours runs before Dependabot opens PRs; Dependabot auto-creates only its own defaults, not `labels:`-assigned ones) — if it ever goes missing, the repair is the documented one-liner in `dependabot.yml`'s header and `docs/agents/workflow.md`, not a config change.

## Test stability under parallel load

- **Strict-equality parity against a third-party resolver is season-dependent on ambiguous DST readings — assert occurrence membership there.** Luxon (and similar offset-guessing resolvers) resolves an ambiguous wall time from a guess seeded by the _current instant_ (decision D-079's recorded caveat), so which valid occurrence it returns flips with the schedule zone's season — while every returned instant stays a genuine occurrence. Observed live 2026-11-01: `test/unit/peak-hours-dst.property.spec.ts`'s every-minute Luxon-parity sweep went red the day America/Havana crossed to standard time (the zone's ambiguous midnight resolved to the second occurrence all winter) after months green, with no code change anywhere. The fix pattern, now in that suite: keep strict `toBe` parity for unambiguous and gapped readings (those converge seed-invariantly — verified for the matrix zones), assert `toContain` against the oracle's full occurrence set for ambiguous readings, and pin the seeding mechanism executably (Luxon `Settings.now` overridden to both seasons — the regression sits next to the sweep). Any new test asserting exact equality against a resolver it does not own must first ask whether the input is ambiguous in a DST zone.
- **Compute-bound property tests declare explicit per-test timeouts — Vitest's default 5 s is a flake under parallel-wave load.** A property doing ~100 fast-check runs over `size: 'max'` series with brute-force oracle walks is legitimately compute-bound: the downsample cluster property measures 0.95 s clean, 1.4 s under v8 coverage (permanent in `make check` since D-085), and **6.8 s** worst in a full coverage run under the starvation rig — past the default at exactly the ambient load (~18) where U-012's matrix flaked it. There is nothing to synchronize (the D-087 synchronization pattern needs a phase; here the test simply needs more wall time) — declare the timeout instead: `it('…', { timeout: 20_000 }, fn)` on the installed Vitest 5 (options-object form; `describe`-level options and the legacy trailing-number form also exist — `peak-hours-dst.property.spec.ts` uses the latter). **Size from the measured worst case under the rig, never guess**: six busy-loop hogs pinned across the container's 8 cores (`taskset -c 0..5 sh -c 'while :; do :; done'`, the U-010/U-012 method), run the _full_ `make check` under it (the 104-file pool contends far more than isolated suite runs: 3.8 s isolated-rig worst vs 6.8 s full-rig worst for the same test), then take ≈3× that worst (U-020 chose 20 s; `peak-hours-dst`'s task-115 pins were re-margined to 25/60 s the same way by U-025 — its scan-oracle property measured 19.3 s worst against the pinned 30 s, the exhaustive minute block 7.1 s against 15 s). A test joins the census when it measures ≥ ~250 ms clean or ≥ ~1 s under the rig — anything measured far below (events-detection 0.8 s, history-gaps 0.37 s, history-timeline 0.62 s, rolling-ranges 18 ms under the rig) stays on the default, keeping the timeout a meaningful statement. Never lower `numRuns` to fit a timeout — the properties are the §17.1 coverage. Recorded as decision D-094; the same load-sensitivity family as D-087 (validate-suite deadlines) and measured over the D-090 comparator paths these suites walk. The census family includes **spawn-bound real-launcher suites**, not only compute-bound properties: a test that boots the `quotameter` binary through `jiti/register` pays a 1–2 s child transpile (4.6 s cold, right after a fresh install) that parallel waves inflate identically — U-039 pinned `cli-service-control.spec.ts` and `cli-service-install.spec.ts` at the house 30 s the 141/142/143 real-launcher suites (`cli-service-reload`/`-status`/`-logs`) already declare for the same boot shape (full-rig worst 5.9 s at load 16–21; 13.4 s, still green, through a load-38 sibling burst — tail evidence, not the sizing basis, since the hogs are the instrument calibrating to the observed ambient waves ~18). `cli-doctor.spec.ts`'s `--help` spawn test was the family's last default-timeout member (U-044 pinned it at the house 30 s after the 2026-11-04/05 waves expired it at the 5 s default; decision D-163). The census equally covers **process-orchestration marker waits** — a `vi.waitFor` around a child boot is a boot-time assertion in disguise, and the same waves tripped `single-instance.spec.ts`'s U-017 guard-waiting/saw-stale waits and `server-main.spec.ts`'s `signals-ready` wait at their 10 s default before U-044 sized the class from the same rig census: marker latency ≈ one runner boot (1.8–2.2 s isolated, worst ≈5.5 s in-pool under the rig) → the 20 s wait default with the runner-side `blockUntil` park bound a strict step above it (25 s: the child parks from its marker write, the parent waits only after observing it), with the single-boot test pins at 30 s, the two-boot real-process pins at 45 s, and the U-017 arms kept at 60 s (≈3.4× their 13.9–17.4 s full-rig worst); every handshake stayed as-is because each marker is provably causal (the U-001/U-002 pattern already — e.g. `guard-waiting` is the third starter's first and only reachable liveness probe while the lock path is vacant). An extreme burst can still exceed even landed per-test pins (`cli-init-yes` 20 s) or trip internal readiness deadlines well inside them (`cli-init-service`'s 15 s `waitFor` markers under 40 s pins). **A test that depends on how a child's writes coalesce into reads gets an explicit chunk-boundary handshake, never OS-read luck** (U-047, decision D-167): `test/unit/cli-service-logs.spec.ts`'s backpressure cell used to flood 200 lines and silently require the pipe to deliver ≥ 2 reads — under load the flood coalesced into one read, the re-pause proof never happened, and the cell flaked three full runs (U-039's rig run 3, U-044's final-value rig run, task 181's landing) while green in every isolation. It now signals each chunk into existence (`SIGUSR2` → the child writes `CHUNK<n>` and marks `wrote-<n>` from the write callback — the marker exists only once the bytes reached the OS pipe), announces its pid only after its handlers are installed (the U-001 discipline), and proves the held gate by causality plus a settle window the causality makes flake-proof: a holding pause means no data event can exist (the window is vacuously stable, so it cannot flake), while the pending-proven chunk means a pause-less runner must forward inside it — loop-turn lateness, not a race.
- **Short total transport deadlines belong only to deadline-expiry tests; delivered-response assertions run at a round-trip-justified generous deadline (decision D-087).** §7.2's `timeoutMs` is one total bound that starts inside `providerFetch` before dispatch (D-042), so a short deadline in any test that merely awaits an arrived outcome silently asserts "the runner completes the whole exchange within N ms" and races v8 instrumentation plus parallel load — the validate suite flaked once at 120 ms (U-012) and the snapshot suite carried the same coupling at 2 s until U-021; both suites' delivered-response cases now run at 5 s, the transport suite's value for the same loopback round-trip since task 104 and §7.2's minimum configured timeout — the house value for new real-socket suites. "Delivered response" is the assertion class, not a literal body: arrived statuses, parse failures, refusals, destroyed sockets, and caller-abort tests all belong here — anywhere the deadline is scenery (an abort racing a short deadline can even invert through D-072's deadline-wins precedence). Where the deadline itself is the subject, keep it short but load-uninvertible: the server delay must start at request arrival — strictly after the deadline starts; the mock's `delayMs` timer arms inside `req.on('end')` — and exceed the deadline by a wide margin, ≥10× for new or reworked expiry cases (the validate and snapshot suites' choice; the snapshot suite's expiry case sat at only 5× before U-021), so every load factor moves the response further past the deadline, never before it. The transport suite's legacy expiry shapes (60 vs 400 ms, 120 vs an ~800 ms trickle ≈ 6.7×) were the last carry-overs below the margin and were raised to 10× (60 vs 600 ms, 120 vs a 1200 ms trickle) by U-026 — every real-socket expiry case in the tree now meets the convention.

## Test infrastructure

- **The no-network guard is a tripwire, not a sandbox (U-031, decision D-154).** `test/helpers/network-guard.ts` inspects every `fetch` input shape — `string`, `URL`, and `Request` get their host extracted (reading exactly what fetch reads: the stringified URL and the Request's internal-slot-backed `url` getter, never shadowable accessors); anything else is rejected outright, because fetch webidl-coerces non-Request objects via `ToString` and any property-based guess would inspect a decoy — and intercepts `node:http`/`node:https` at `Agent.prototype.createConnection`, so the global agents, `agent: false` default agents, and custom `new Agent()` instances alike are covered. It deliberately does **not** cover: a `createConnection` passed as a request or agent option, direct `node:net`/`node:tls` sockets, direct `undici` module imports (`undici.fetch`, `undici.request`, `setGlobalDispatcher`), `node:dns`, and **fetch redirect following** (undici follows a `3xx Location` to an external origin after the initial input is inspected — a loopback mock answer can therefore redirect a test fetch off-host; keep `redirect: 'error'` in test fetches, as the provider transport does) — closing those would mean intercepting socket creation or response processing process-wide, invasive far beyond §17's "tests must not require a real API key or internet access" intent. Consequences for test authors: never reach for those paths against anything but loopback (use `test/helpers/mockProviderServer.ts` on 127.0.0.1), and remember a test deliberately opening raw sockets to an external host will not be stopped by the guard — review attention, not the guard, covers that. The guard's own docblock is the canonical scope statement.
- **Playwright's `context().cookies(urls)` filters by URL path, and the session cookie is path-scoped to `/api`.** Querying with the bare origin (`cookies(baseUrl)`) returns an empty jar even though the browser stores and sends the cookie — RFC 6265 path-matching excludes `/` from a `/api`-scoped cookie. Query the cookie's own path (`cookies(`${baseUrl}/api`)`) and filter by name (names are not URL-shaped; passing a cookie name as the URL argument throws `Invalid URL`). Bit the task-183 auth scenario live.
- **Seeded §12.2 timeline worlds: run stamps, not just valid metric points, participate in the silence judgments — and any finite history inside a wide range carries a leading stopped period.** `buildTimelineIndicators` walks the RUN sequence (every outcome): each inter-run silence beyond three intervals is a stopped-service region, and the range-start → first-run silence is one too, so "a couple of successful cycles plus one gap" in a 7-day window is NOT `1 gap / 0 stopped` — the leading region plus every inter-run pair counts (observed: `2 collection gaps, 4 stopped periods` from four runs with two long silences). The gap service likewise judges silences between stamps that include non-success runs. For exact marker-count assertions, shape the world deliberately: place every non-gap pair far under the threshold (a failed cycle 5 minutes after a success adds its error marker without a silence), isolate exactly one beyond-threshold silence, and count the leading stopped region in the expectation — the `test/e2e/acceptance/chart-markers.spec.ts` world documents its arithmetic inline.

## Tooling quirks

- **ESLint flat presets**: `@intlify/eslint-plugin-vue-i18n`'s `flat/recommended` is an **array**, not an object — spreading it into a config object breaks with `Unexpected key "0"`. Register the plugin manually and enable the single rule instead.
- **Prettier vs `eslint-plugin-vue`** disagree about line breaks in short `<p>` elements: the residual warnings in the UI's short `<p>` lines (`ui/src/views/*.vue` today) are expected; do not "fix" them (the two formatters will ping-pong).
- **Vitest project `sequence.sort`** does not exist — use `sequence.shuffle: false` for determinism.
- **`node:sqlite`** imports fine on 22.13.0+ but prints an `ExperimentalWarning` — expected, not an error.
- **`npm pack`** silently skips allowlisted-but-missing files (`LICENSE`/`NOTICE` were reserved before they existed) — the allowlist check only fails on _unexpected_ entries.
- **Dependabot PRs** go `BEHIND` after every merge (strict branch protection): rebase each remaining PR (`@dependabot rebase`) before merging it.
- **A tsconfig that `extends` another inherits its `exclude` — resolved against the _base_ config's directory, and an explicit `exclude` in the extending config replaces both the inherited one and TypeScript's defaults (`node_modules`, `bower_components`, …).** This bit `ui/tsconfig.json`: its `include` named `../test/component/**/*.ts`, but the inherited root `exclude: ["test/component"]` (root-relative, i.e. exactly that directory) killed it, so the component specs were type-checked by no project while both `tsc` and `vue-tsc` stayed green (U-030). An extending config whose include reaches outside its own directory must verify the inherited `exclude` does not remove its includes — override or redeclare the `exclude` when it does (a redeclared `exclude` must itself re-cover whatever defaults matter; U-030's `["**/node_modules"]` restores the `node_modules` default only). Verify ownership with `--listFiles` per project rather than trusting that an include line takes effect.
