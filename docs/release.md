# Release and versioning policy

## Versioning

The package follows [Semantic Versioning](https://semver.org/) strictly:

- **MAJOR** — incompatible changes to configuration, CLI commands, HTTP API, storage schema, or documented behavior.
- **MINOR** — new backwards-compatible functionality (new provider adapters, new API endpoints, new CLI commands).
- **PATCH** — backwards-compatible fixes and internal changes.

Until the first public release the version stays `0.0.0`; the first tagged release will be `1.0.0` and must satisfy the MVP acceptance criteria in the specification (§19).

## Tagging

- Release tags are named exactly `vX.Y.Z` (for example `v1.0.0`), created on a commit that has passed CI on `master`.
- Tags are immutable: a bad release is fixed by a new version, never by moving a tag.

## Changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/):

- Every merged pull request that changes user-visible behavior adds an entry under **Unreleased**.
- Entries use the categories _Added_, _Changed_, _Fixed_, _Deprecated_, _Removed_, _Security_.
- At release time, **Unreleased** becomes the new version section with its date, and a fresh **Unreleased** section is opened.

## Publishing

**npm publishing happens only from CI on a pushed `vX.Y.Z` tag** (see `.github/workflows/release.yml`, task 058). Local `npm publish` is never used; the package manifest keeps `private: true` and the release workflow removes it as part of the release build. Releases carry provenance attestations generated by the workflow's OIDC identity.

## Release checklist

Run through every step; the release is aborted if any check fails.

1. **Verify CI is green** on the release commit for: `master` (unit/integration/component/E2E, lint, types, format, audit, licenses, mutation, clean-container installs, unsupported-Node behavior).
2. **Update the changelog**: fold **Unreleased** into the new version with today's date; open a new **Unreleased** section.
3. **Bump the version** in `package.json` to the target `X.Y.Z` following the semver rules above.
4. **Commit and push** the version commit (`chore(release): vX.Y.Z`); wait for CI.
5. **Create and push the tag**: `git tag vX.Y.Z && git push origin vX.Y.Z`.
6. **Watch the release workflow**: it builds, packs, re-checks the tarball allowlist, and publishes with provenance. Publication only happens from this workflow.
7. **Verify on npm**: the new version exists, provenance is linked, `npm install -g quotameter@X.Y.Z` works in a clean container.
8. **Announce** in the repository release notes if the release is notable; link the changelog section.

## Rollbacks

A broken published release is superseded by a PATCH release. `npm unpublish` is reserved for catastrophic leaks (e.g. accidental secret exposure) within npm's policy window and requires rotating anything the leak exposed first.
