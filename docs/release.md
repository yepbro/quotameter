# Release and versioning policy

## Versioning

The package follows [Semantic Versioning](https://semver.org/) strictly:

- **MAJOR** — incompatible changes to configuration, CLI commands, HTTP API, storage schema, or documented behavior.
- **MINOR** — new backwards-compatible functionality (new provider adapters, new API endpoints, new CLI commands).
- **PATCH** — backwards-compatible fixes and internal changes.

Until the first public release the version stays `0.0.0`. The first published release is **`v0.1.0`** — a full-cycle rehearsal of the release process (version commit, tag, release workflow, trusted publishing, npm publication, clean-container install) with no §19 completeness requirement, leaving room for iteration while the product stabilizes. **`1.0.0` is a distinct milestone**: the release that closes every MVP acceptance criterion in the specification (§19).

While the version is `0.x`, breaking changes and new functionality bump MINOR (`0.Y+1.0`); PATCH is backwards-compatible fixes. The MAJOR/MINOR/PATCH rules above apply unchanged from `1.0.0` on.

## Tagging

- Release tags are named exactly `vX.Y.Z` (for example `v0.1.0`), created on a commit that has passed CI on `master`. The release workflow verifies this mechanically: it refuses to publish unless the tagged commit is on `master` and its `CI` check run completed successfully.
- Tags are immutable: a bad release is fixed by a new version, never by moving a tag. The one exception is a tag whose release **never published** (the workflow run failed before the publish step, so the version does not exist on npm): such a tag may be deleted and re-pointed at the fixed commit — the registry, not the git ref, is the arbiter of what shipped (decision D-211). Once a version exists on npm, its tag is immutable for good.

## Changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/):

- Every merged pull request that changes user-visible behavior adds an entry under **Unreleased**.
- Entries use the categories _Added_, _Changed_, _Fixed_, _Deprecated_, _Removed_, _Security_.
- Each category heading appears **at most once per section** — entries for one category are never appended under a second, duplicate heading.
- Sections are ordered newest first, and entries inside a category are ordered newest first (newest task at the top).
- At release time, **Unreleased** becomes the new version section with its date, and a fresh **Unreleased** section is opened.

The structure the fold depends on is enforced by `test/unit/release-checklist.spec.ts` (decision D-205): the first section heading is exactly `## [Unreleased]` and carries no date; every released section is `## [X.Y.Z] - YYYY-MM-DD` — a real calendar date; each category heading appears at most once per section; every entry line is a `- ` list item under a category heading. That is what makes the fold a deterministic edit rather than a restructuring:

1. Rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, using the release date.
2. Insert a fresh `## [Unreleased]` heading directly above it.

Nothing else moves: the section already carries each category at most once, so the folded section is a complete Keep a Changelog version section as-is, and the next entry lands under the new **Unreleased**.

## Publishing

**npm publishing happens only from CI on a pushed `vX.Y.Z` tag** (see `.github/workflows/release.yml`) — spec §4.4's rule, which governs releases. The one recorded exception is the one-time `quotameter@0.0.0` name-reservation stub (decision D-204): a manual, untagged publish of a manifest-and-README-only stub that reserves the package name and carries no product code — a reservation, not a release. Outside that exception, local `npm publish` is never used. The package manifest keeps `private: true` and the release workflow removes it as part of the release build. Releases carry provenance attestations generated by the workflow's OIDC identity.

### What the release workflow does

The publish job runs this pipeline, in order, on the tagged commit:

1. Check out the tag, set up Node.js 22 with the npm cache, and install dependencies (`npm ci`).
2. **Update npm to the shared ≥ 11 pin** (`npm install -g npm@11.9.0`, the same pin as the Dockerfile and ci.yml): tokenless OIDC trusted publishing requires npm ≥ 11.5 — the npm bundled with Node 22 cannot publish this way.
3. Verify the tag matches `package.json`'s version (a mismatch aborts before the CI gate, tests, build, and publish).
4. **Require a green `CI` check run on the tagged commit**: the workflow first verifies the commit is on `master` (a compare against `master` must report the tag at or behind it — a green check run on an unmerged PR-head commit does not qualify), then queries the commit's check runs via the GitHub API and refuses to publish unless the latest `CI` run (the required gate that protects `master`) completed successfully. This mechanically enforces the rule above that tags point at a green `master` commit — a tag pushed while CI is still running, pointing at a commit that never ran CI, pointing at a red commit, or pointing off `master` is refused with an explanation (after CI finishes, re-run the workflow; tags are immutable).
5. Run the test suite (`npm run test:ci` — the same coverage-gated run CI's test job and `make check` use) **inside the CI test container**: the step executes `npm ci` and the suite in the same `node:` image as the CI test matrix's declared-minimum cell (`node:22.13.0`, non-root via `setpriv`, exactly the CI cell's shape — the image is cross-pinned by `test/unit/release-workflow.spec.ts`), chowns the workspace to the container's node user for the run and restores the runner's ownership afterward so the host build/publish steps keep writing freely. The container matters: the first `v0.1.0` tag ran the suite on the bare runner and failed 29 CLI integration tests deterministically, because the runner host ships systemd/`timedatectl` while the CI test containers do not and the CLI suites are calibrated to the container (U-062, D-211).
6. Build the web UI (`npm run build:ui`), build the compiled CLI (`npm run build:cli` — the `dist/` graph the installed `quotameter` command resolves, task 185/D-195), and verify the build artifacts (`npm run verify:build`, which requires both halves' entries).
7. Check the tarball contents against the allowlist (`npm run check:package`). The builds (step 6) happen first, so the check validates the built artifacts: the package manifest's `files` allowlist covers `ui/dist` (task 184, D-194) and `dist/` (task 185, D-195), so the published tarball ships the prebuilt UI and the compiled CLI.
8. Remove the `private` marker and publish with `npm publish --provenance --access public`.

The workflow carries no npm token or secret of any kind; its only elevated permission is the workflow-scoped `id-token` used for the OIDC exchange.

> **§17.2 is closed in full (tasks 053/186/195 + 196):** the installation matrix and the systemd lifecycle half together prove the spec's complete installation/package contract. The tarball ships `bin/`, the published JSON Schema, the OpenAPI reference, the compiled CLI under `dist/`, and — from the release build — `ui/dist`. The CI install matrix crosses the three supported stock distributions (Ubuntu 22.04, Ubuntu 24.04, Debian stable — each verified compiler-free, the toolchain absence itself checked) with §17.2's two runtimes (the declared minimum `22.13.0` and the 24 LTS line the spec names, `24.22.2`, each installed from SHA-verified official binaries), and verifies on the machine npm actually wrote: no install-time lifecycle script in the installed manifest, nothing native (`*.node`/`binding.gyp`) or script-carrying anywhere in the resolved tree, the compiled `dist/` present, `--version`/`--help` through the installed command, and — task 195, D-203 — `init --yes` completing non-interactively with the provider host blackholed for both address families and the blackhole verified through Node's own resolver (the §5.3 step-5 configuration written at the enforced `0700`/`0600` directory/file modes and the database created under the `0700` data directory, exit 0, no provider contact); sub-minimum Node versions get the clear error (`unsupported-node`). The lockfile-side guarantee (the production dependency closure is pure JavaScript) is pinned executably by `test/unit/install-time-build.spec.ts` over the committed lockfile snapshot. The systemd-capable half (task 196, D-206) runs the same tarball artifact in a purpose-built systemd container (`make test-systemd` locally, the CI `systemd` job): install/start through the genuine `sudo quotameter service install` route reaching active+enabled+healthy, crash restart under `Restart=on-failure` with the §5.6 single-instance lock re-acquired, reboot enablement across real container reboots, §6.4 reload (accepted with the service's own journald reload record, rejected without any SIGHUP), and the user unit with linger — the exact §5.3 enable-linger guidance when linger is disabled, the lingered manager keeping the enabled unit alive without a session, and both surviving a reboot. What §17.2 leaves to other sections: the provider-connected flows are the CLI suites' and the optional manual smoke test's (§17.3), never the install/lifecycle matrices'.

### Trusted publishing setup (one-time, before the first release)

The release workflow uses **npm trusted publishing**: GitHub Actions proves its identity to the npm registry via a short-lived OIDC token, so no `NPM_TOKEN` secret exists in this repository and no long-lived credential can leak. **The bootstrap order matters** (decision D-204): npm cannot configure a trusted publisher for a package that does not exist — there is no pending-publisher mechanism — so the name is reserved first, and the publisher is configured on the now-existing package. In order:

1. The npm account enables **2FA** (required, spec §4.4): enrollment for both login and publish actions. Done.
2. **Recheck the package name immediately before reserving** (spec §4.2: recorded checks are not reservations): `GET https://registry.npmjs.org/quotameter` must answer 404. Done — free at the 2026-11-08 recheck.
3. **Reserve the name by publishing a one-time `quotameter@0.0.0` stub manually** — the deliberate, scoped exception to "local `npm publish` is never used" (decision D-204): a reservation is not a release, and the stub carries no product code (manifest + README only, the README marking it a name reservation with `v0.1.0` coming). Done 2026-11-08 17:39 UTC; `dist-tags.latest` = `0.0.0` (a cosmetic `0.0.0-stage` artifact from a staging first attempt also sits in the version history — harmless, ignore it). **The stub is never unpublished**: unpublishing the only version frees the name for anyone after npm's window, an unpublished `0.0.0` can never be republished, and nothing needs it gone — `latest` moves to the first real release automatically (the release workflow publishes with no dist-tag override, and npm assigns `latest` to an untagged non-prerelease publish).
4. **Configure the package-side settings on the now-existing package**: the trusted publisher in the npm registry settings — repository `yepbro/quotameter`, workflow `release.yml`, environment `npm`, allowed actions npm publish (direct), stage publish, and dist-tag — and the strict package-level 2FA option ("Require two-factor authentication and disallow bypass 2fa tokens"), which only an existing package can carry. Create the GitHub environment `npm` and declare `environment: npm` in the workflow — the OIDC claim must match the configuration. Done 2026-11-08.
5. **Mind the 48-hour pending-validation window**: npm marks a new trusted-publisher configuration "Pending validation" and **deletes it** unless one publish goes through it before the deadline. The 2026-11-08 configuration (deadline 2026-11-10 17:41 UTC) is expected to expire unused — the owner kept the task order (196→197→199→200) ahead of a throwaway validation publish — so the release checklist re-creates it before the first real release.
6. Dry-run once: push a throwaway tag on a branch that mirrors this workflow and delete the attempt — the publish step must fail safely if the trusted-publisher link is misconfigured.

### Required npm account 2FA

Two-factor authentication is mandatory on the publishing npm account: without it the registry rejects provenance-linked trusted publishing. The package additionally carries the **strict package-level 2FA option** ("Require two-factor authentication and disallow bypass 2fa tokens", decision D-204), so no automation or bypass token can publish or alter `quotameter` outside the flows configured here. Recovery codes are stored outside this repository (password manager), never in code or CI secrets.

## Release checklist

Run through every step; the release is aborted if any check fails. Every step names its executable form — step 5 is necessarily prose (npm exposes no CLI for a package's trusted-publishing settings; the registry's package settings page is the mechanism), and step 9's whether-to-announce is a judgement call while its mechanism is still a command. `test/unit/release-checklist.spec.ts` (decision D-205) fails when this checklist goes stale: a command naming a script or target that no longer exists, a Node image version that no longer matches the Dockerfile pin, a changelog that loses the structure step 2's fold needs, or a version bump that leaves `package-lock.json` behind.

1. **Verify CI is green** on the release commit for `master`: `gh run list --workflow ci.yml --commit <release-commit-sha> --limit 1` finds the run of the required `CI` gate for exactly that commit (unit/integration/component/E2E, lint, types, format, audit, licenses, clean-container installs, unsupported-Node behavior); `gh run watch <run-id> --exit-status` waits for it and itself fails when the run fails. Mutation testing runs on its own daily schedule (D-045) and does not gate the release.
2. **Update the changelog**: fold **Unreleased** into the new version exactly as the [Changelog](#changelog) mechanics describe — rename the section heading to `## [X.Y.Z] - YYYY-MM-DD` with today's date, insert a fresh `## [Unreleased]` heading above it, move nothing else.
3. **Bump the version** with `npm version X.Y.Z --no-git-tag-version` — it updates `package.json` **and** both `package-lock.json` version sites without committing or tagging — then regenerate the version-stamped OpenAPI document (`make openapi`). The version commit carries `package.json`, `package-lock.json`, `CHANGELOG.md`, and `docs/openapi.json` together — the drift guard fails CI on a stale artifact otherwise.
4. **Commit and push** the version commit (`chore(release): vX.Y.Z`); wait for CI exactly as in step 1.
5. **Verify the npm trusted-publisher configuration** right before tagging (decision D-204): a configuration npm has not validated within 48 hours of creation is **deleted** — the 2026-11-08 configuration was expected to expire unused, so assume re-creation. Check the package's trusted-publishing settings on npm for repository `yepbro/quotameter`, workflow `release.yml`, environment `npm` (publish/stage/dist-tag actions, strict package 2FA intact); if missing or still pending, re-create it — this release's own publish is the validating publish, so it must happen inside the fresh 48-hour window.
6. **Create and push the tag**: `git tag vX.Y.Z && git push origin vX.Y.Z`.
7. **Watch the release workflow**: `gh run list --workflow release.yml --limit 1` finds the run the tag push started; `gh run watch <run-id> --exit-status` waits for it and fails with it. The workflow verifies the tag/version match and the green CI run on the tagged commit, runs the test suite (`npm run test:ci`) in the CI test container (see above), builds and verifies the web UI and the compiled CLI, re-checks the tarball contents against the allowlist (`npm run check:package`), and publishes with `npm publish --provenance --access public`. Publication only happens from this workflow (see "What the release workflow does" above).
8. **Verify on npm**:
   - `npm view quotameter@X.Y.Z` — the version exists with the expected metadata.
   - `npm view quotameter@X.Y.Z dist.attestations` — the provenance check: this must print the attestations object (`url` plus `provenance.predicateType` `https://slsa.dev/provenance/v1`), not empty output. Empty means the publish carried no provenance — treat that as a failed release.
   - `npm view quotameter dist-tags --json` — `latest` moved off the `0.0.0` reservation stub to `X.Y.Z` (decision D-204).
   - Clean-container install: `docker run --rm node:22.13.0-slim sh -c 'npm install -g quotameter@X.Y.Z && quotameter --version'` — prints `X.Y.Z` through the registry-installed command. The image is pinned to the declared minimum, the same Node line the Dockerfile carries.
9. **Announce**: for a notable release, publish GitHub release notes from the tag — `gh release create vX.Y.Z --title "vX.Y.Z" --notes "…"` — linking the version's `CHANGELOG.md` section.

## Rollbacks

A broken published release is superseded by a PATCH release. `npm unpublish` is reserved for catastrophic leaks (e.g. accidental secret exposure) within npm's policy window and requires rotating anything the leak exposed first.
