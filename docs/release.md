# Release and versioning policy

## Versioning

The package follows [Semantic Versioning](https://semver.org/) strictly:

- **MAJOR** — incompatible changes to configuration, CLI commands, HTTP API, storage schema, or documented behavior.
- **MINOR** — new backwards-compatible functionality (new provider adapters, new API endpoints, new CLI commands).
- **PATCH** — backwards-compatible fixes and internal changes.

Until the first public release the version stays `0.0.0`; the first tagged release will be `1.0.0` and must satisfy the MVP acceptance criteria in the specification (§19).

## Tagging

- Release tags are named exactly `vX.Y.Z` (for example `v1.0.0`), created on a commit that has passed CI on `master`. The release workflow verifies this mechanically: it refuses to publish unless the tagged commit is on `master` and its `CI` check run completed successfully.
- Tags are immutable: a bad release is fixed by a new version, never by moving a tag.

## Changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/):

- Every merged pull request that changes user-visible behavior adds an entry under **Unreleased**.
- Entries use the categories _Added_, _Changed_, _Fixed_, _Deprecated_, _Removed_, _Security_.
- At release time, **Unreleased** becomes the new version section with its date, and a fresh **Unreleased** section is opened.

## Publishing

**npm publishing happens only from CI on a pushed `vX.Y.Z` tag** (see `.github/workflows/release.yml`). Local `npm publish` is never used; the package manifest keeps `private: true` and the release workflow removes it as part of the release build. Releases carry provenance attestations generated by the workflow's OIDC identity.

### What the release workflow does

The publish job runs this pipeline, in order, on the tagged commit:

1. Check out the tag, set up Node.js 22 with the npm cache, and install dependencies (`npm ci`).
2. **Update npm to the shared ≥ 11 pin** (`npm install -g npm@11.9.0`, the same pin as the Dockerfile and ci.yml): tokenless OIDC trusted publishing requires npm ≥ 11.5 — the npm bundled with Node 22 cannot publish this way.
3. Verify the tag matches `package.json`'s version (a mismatch aborts before the CI gate, tests, build, and publish).
4. **Require a green `CI` check run on the tagged commit**: the workflow first verifies the commit is on `master` (a compare against `master` must report the tag at or behind it — a green check run on an unmerged PR-head commit does not qualify), then queries the commit's check runs via the GitHub API and refuses to publish unless the latest `CI` run (the required gate that protects `master`) completed successfully. This mechanically enforces the rule above that tags point at a green `master` commit — a tag pushed while CI is still running, pointing at a commit that never ran CI, pointing at a red commit, or pointing off `master` is refused with an explanation (after CI finishes, re-run the workflow; tags are immutable).
5. Run the test suite (`npm run test:ci` — the same coverage-gated run CI's test job and `make check` use).
6. Build the web UI (`npm run build:ui`) and verify the build artifacts (`npm run verify:build`).
7. Check the tarball contents against the allowlist (`npm run check:package`). The build (step 6) happens first, so the check validates the built artifacts: once the package manifest's `files` allowlist covers `ui/dist` (task 184, Stage 14), the published tarball ships the prebuilt UI with no further workflow change.
8. Remove the `private` marker and publish with `npm publish --provenance --access public`.

The workflow carries no npm token or secret of any kind; its only elevated permission is the workflow-scoped `id-token` used for the OIDC exchange.

> **Task 184 dependency (Stage 14):** until the package manifest is finalized (task 184 — `files` allowlist including `ui/dist`, and the `repository` field npm requires for provenance attestations), a real publish still fails at the last step: the tarball does not yet ship `ui/dist`, and `npm publish --provenance` refuses to run without repository information. Task 184 must also extend `scripts/check-package.mjs`'s exact-match `ALLOWED` with matching for the packed `ui/dist/**` entries (npm lists each built file, not a directory), and the packaged server code itself (`bin/`, `schema/`, and whatever else the shipped CLI resolves to) is 184–186's manifest work too. The workflow's step order is final: the build already precedes the tarball check and publish, so none of this needs another workflow change.

### Trusted publishing setup (one-time, before the first release)

The release workflow uses **npm trusted publishing**: GitHub Actions proves its identity to the npm registry via a short-lived OIDC token, so no `NPM_TOKEN` secret exists in this repository and no long-lived credential can leak. Before the first release:

1. The npm account owning the `quotameter` package name enables **2FA** (required, spec §4.4) — enrollment for both login and publish actions.
2. In the npm registry settings, connect the trusted publisher: repository `yepbro/quotameter`, workflow `release.yml`, environment `npm` (create the protected GitHub environment and uncomment the `environment:` line in the workflow when doing so).
3. Verify the package name is still available immediately before configuring (spec §4.2: recorded checks are not reservations).
4. Dry-run once: push a throwaway tag on a branch that mirrors this workflow and delete the attempt — the publish step must fail safely if the trusted-publisher link is misconfigured.

### Required npm account 2FA

Two-factor authentication is mandatory on the publishing npm account: without it the registry rejects provenance-linked trusted publishing. Recovery codes are stored outside this repository (password manager), never in code or CI secrets.

## Release checklist

Run through every step; the release is aborted if any check fails.

1. **Verify CI is green** on the release commit for: `master` (unit/integration/component/E2E, lint, types, format, audit, licenses, clean-container installs, unsupported-Node behavior). Mutation testing runs on its own daily schedule (D-045) and does not gate the release.
2. **Update the changelog**: fold **Unreleased** into the new version with today's date; open a new **Unreleased** section.
3. **Bump the version** in `package.json` to the target `X.Y.Z` following the semver rules above, then regenerate the version-stamped OpenAPI document (`make openapi`) and include `docs/openapi.json` in the same commit — the drift guard fails CI on a stale artifact otherwise.
4. **Commit and push** the version commit (`chore(release): vX.Y.Z`); wait for CI.
5. **Create and push the tag**: `git tag vX.Y.Z && git push origin vX.Y.Z`.
6. **Watch the release workflow**: it verifies the tag/version match and the green CI run on the tagged commit, runs the test suite, builds and verifies the web UI, re-checks the tarball allowlist, and publishes with provenance. Publication only happens from this workflow (see "What the release workflow does" above).
7. **Verify on npm**: the new version exists, provenance is linked, `npm install -g quotameter@X.Y.Z` works in a clean container.
8. **Announce** in the repository release notes if the release is notable; link the changelog section.

## Rollbacks

A broken published release is superseded by a PATCH release. `npm unpublish` is reserved for catastrophic leaks (e.g. accidental secret exposure) within npm's policy window and requires rotating anything the leak exposed first.
