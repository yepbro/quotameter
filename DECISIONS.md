# Quotameter — Decision Log

This file records important technical and business decisions made during development: what was decided, why, and what it means for the project. It complements the [Technical Specification](plan/SPECIFICATION.md) (the full requirements baseline) and the [Implementation Task Plan](plan/tasks.md).

**Rules:**

- Entries are immutable once accepted; a reversed or replaced decision gets a new entry that references the old one.
- Every entry has a unique stable ID (`D-NNN`), a date, and a status (`Accepted`, `Superseded by D-NNN`, `Reversed`).
- Decisions live here even when they are also described in the specification; this file records the _reasoning_, not the full requirements.

## D-001 — Single-user, self-hosted product shape

**Date:** 2026-10-28 · **Status:** Accepted · **Spec:** [§1](plan/SPECIFICATION.md#1-purpose-and-scope)

**Decision.** Quotameter is a personal self-hosted service operated by one person on their own Linux VPS. There is no registration, user directory, roles, or multi-user features, and it is not a hosted/cloud service.

**Reasons.** The tool exists to monitor the author's own AI subscription quotas; multi-tenancy adds auth complexity, attack surface, and operational burden with no benefit for the target user.

**Consequences.** Authentication is a single optional password with hardened `auto`/`required` modes instead of an account system. Data model, UI, and deployment assume one operator. A future hosted offering would be a new product, not an extension.

## D-002 — Node.js/TypeScript stack with built-in `node:sqlite`

**Date:** 2026-10-28 · **Status:** Accepted · **Spec:** [§3, §11](plan/SPECIFICATION.md#3-technology-and-packaging)

**Decision.** Server and tooling run on Node.js `>=22.13.0` with TypeScript in `strict` mode; the web layer uses Fastify and Vue 3; history is stored in SQLite through the built-in `node:sqlite` module. No external database process, ORM-free direct usage per the spec.

**Reasons.** One runtime covers the server, CLI, build tooling, and tests. `node:sqlite` imports without the `--experimental-sqlite` flag starting from Node.js 22.13.0, removing a separate database service and its upgrade/backup surface from a single-VPS deployment.

**Consequences.** The minimum supported Node version is pinned at 22.13.0 and must be verified in CI and clean-install tests. Data lives in a single SQLite file, enabling simple `VACUUM INTO` backups. Any feature requiring a richer data engine must justify abandoning this simplicity.

## D-003 — Provider adapter architecture; Z.ai Coding Plan only in v1.0

**Date:** 2026-10-28 · **Status:** Accepted · **Spec:** [§1, §8](plan/SPECIFICATION.md#8-provider-architecture-and-zai-adapter)

**Decision.** Providers are integrated as isolated adapters behind a stable provider interface. Version 1.0 ships exactly one adapter: Z.ai Coding Plan. Multiple accounts per provider (including several Z.ai accounts) are first-class.

**Reasons.** Quota APIs differ per vendor and change independently; isolating them keeps the polling engine, persistence, history API, and charts provider-agnostic. Shipping one production adapter keeps the MVP verifiable end-to-end.

**Consequences.** Adding a provider must not require changes outside its adapter (plus configuration schema entries). The Z.ai adapter doubles as the reference implementation; its verified API behavior is documented separately in `docs/providers/`.

## D-004 — Secrets live in the config file, never in the database

**Date:** 2026-10-28 · **Status:** Accepted · **Spec:** [§6.3, §15.4](plan/SPECIFICATION.md#63-secret-storage-and-writes)

**Decision.** API keys and the password hash are stored in the JSON config file with mode `0600` (directory `0700`), not in SQLite. `apiKeyEnv` is an alternative to `apiKey`; exactly one may be set per account. Config writes are atomic (temp file, `fsync`, `rename`).

**Reasons.** Database files are the artefact most likely to be copied into backups, bug reports, and diagnostics; keeping secrets out of them limits exposure. A single sensitive file with enforced permissions is easier to reason about and to protect.

**Consequences.** Database backups and sanitized raw responses are secret-free by construction. The config file becomes the one object requiring strict permission checks at startup (fix or refuse). UI key inputs are write-only; only masked state is ever displayed.

## D-005 — Public repository with English-only artefacts

**Date:** 2026-10-28 · **Status:** Accepted · **Spec:** [§4.1](plan/SPECIFICATION.md#41-public-repository-and-language)

**Decision.** The source repository is public on GitHub (`yepbro/quotameter`, default branch `master`) from day one, and every repository artefact is in English: branches, issues, PRs, commit messages, code comments, docs, UI strings, CLI output, API errors, and logs.

**Reasons.** Public development from the start enables community contributions and verifiable releases. A single language avoids mixed-language drift across code, docs, and support threads.

**Consequences.** Non-English contributions must be reworked before merge. All user-facing strings, including logs and errors, are part of this contract and are tested/reviewed accordingly.

## D-006 — Repository workflow: protected `master`, squash-only merges, minimal Actions token

**Date:** 2026-10-29 · **Status:** Accepted · **Tasks:** [003–005](plan/tasks.md)

**Decision.** `master` is protected: pull requests and a required `CI` status check are enforced before merging, force-pushes and branch deletion are disallowed. Only squash merges are allowed and branches are deleted on merge. The GitHub Actions default token is read-only (`read`), and workflows must request additional permissions explicitly.

**Reasons.** Linear, one-commit-per-change history matches the Conventional Commits convention and keeps `git log` and releases auditable. A read-only default token limits the blast radius of a compromised or malicious workflow.

**Consequences.** Every contribution lands as exactly one squashed Conventional Commit. Until the CI workflow exists, the required `CI` check holds PRs open — accepted as preventive. Admin enforcement is currently off to permit direct bootstrap pushes during Stages 0–1; it will be revisited once CI is live.

## D-008 — Releases are published only from CI on version tags

**Date:** 2026-10-28 · **Status:** Accepted · **Spec:** [§4.4](plan/SPECIFICATION.md#44-cicd-and-supply-chain-safeguards)

**Decision.** npm publication happens only from GitHub Actions, only on a pushed `vX.Y.Z` Git tag, using trusted publishing with provenance. Versioning follows semver; a `CHANGELOG.md` is maintained.

**Reasons.** Tag-gated, CI-only publishing makes releases reproducible and auditable, prevents accidental local publishes, and attaches provenance attestations required for supply-chain trust.

**Consequences.** No local `npm publish` workflow exists by design. Every release requires a green CI run on the tagged commit; package content is restricted by a `files` allowlist and audited (`npm audit --omit=dev`, license checks) before publication.

## D-009 — Layered `src/` package layout with enforced import direction

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§3, §8.1](plan/SPECIFICATION.md#3-technology-and-packaging) · **Tasks:** [059](plan/tasks.md)

**Decision.** Server-side code is organized into layer directories under `src/` — `schemas`, `util`, `config`, `providers` (shared core + one subdirectory per adapter), `storage`, `services`, `server` (composition root), `cli` — with a one-way dependency table: leaves (`schemas`, `util`) import nothing; adapters are islands reachable only through the registry and wired only by the composition root; `bin/` stays a build-free launcher over `src/cli/`. The map and rules live in [docs/architecture/package-layout.md](docs/architecture/package-layout.md) and are enforced mechanically by `test/unit/package-layout.spec.ts`, which resolves every relative import in `src/`, `ui/`, and `bin/`. `ui/` may consume `src/schemas/**` only through type-only imports; it has no runtime dependency on server code.

**Reasons.** Spec §8.1 requires that adding a provider never rewrites the scheduler, persistence, history endpoints, or charts — only a mechanical import boundary makes that guarantee instead of a hope. Spec §3 requires all `node:sqlite` access isolated behind a storage module. A second interpretation was settled here: §8.1 names `QuotaRepository` among the "core services", so it is implemented as the storage layer's public facade — services consume it, but all SQL stays in `src/storage/`.

**Consequences.** Parallel plan tasks target disjoint file sets by construction (each task's placement is listed in the layout doc; directories may repeat across sequential stages). `src/version.ts` moved to `src/util/version.ts` so no loose files sit at `src/` root. Forbidden or unresolved relative imports, cross-adapter imports, and `node:sqlite` usage outside `src/storage/` fail `make check`. Publishing (compiled output, `files` allowlist) remains owned by tasks 184–186 and must respect the documented packaging constraints.

## D-010 — Normalized metric model interpretations (spec §8.4)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§8.4](plan/SPECIFICATION.md#84-normalized-snapshot-and-metric-model) · **Tasks:** [069](plan/tasks.md)

**Decision.** Three interpretations of the §8.4 sketch are pinned in `src/schemas/metrics.ts`: (1) `derivedFields` is a closed union of the five numeric metric fields (`used`, `remaining`, `limit`, `percentUsed`, `percentRemaining`), not the sketch's `string[]`; (2) "an invalid metric is stored without numeric values" covers exactly those five quota-value fields — `windowSeconds` and `resetsAt` are metadata an invalid metric may still carry; (3) the model is pure TypeScript without TypeBox, because it is the validated _output_ of trust boundary 2, not a validation schema.

**Reasons.** (1) §8.4 asks for "derived field names" — names of the metric's own fields; the closed set gives adapters compile-time checking, enables a runtime guard for database read-back, and makes the "listed as derived but not set" invariant expressible; the sketch is prefixed "equivalent to", which allows strengthening. (2) The parenthetical "(not as zero)" targets quota placeholders — the failure mode is unknown quota being recorded as 0 — while a window length or reset schedule can remain known when a reading fails, and discarding it would lose provider information. (3) Runtime validation of provider payloads is adapter-local (Stage 9, trust boundary 2); TypeBox enters the repository with the configuration contract (task 061), so the normalized model needs no dependency.

**Consequences.** Storage (tasks 078+) mirrors these rules in its constraints: invalid rows NULL the five quota columns and require `invalid_reason`; `window_seconds`/`resets_at` may be retained. Adding an enum value or derivable field remains a code change plus a database migration (§8.4). Adapters list derivations explicitly and only for fields computed from supplied originals.

## D-011 — XDG path resolution semantics (spec §6.1)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§6.1](plan/SPECIFICATION.md#61-paths) · **Tasks:** [063](plan/tasks.md)

**Decision.** `src/config/paths.ts` resolves directories with the precedence `QUOTAMETER_CONFIG_DIR`/`QUOTAMETER_DATA_DIR` → `XDG_CONFIG_HOME`/`XDG_DATA_HOME` + `quotameter` segment → `<home>/.config/quotameter` / `<home>/.local/share/quotameter`. Five edge rules are pinned: (1) an empty string counts as unset for all four variables (the XDG wording "either not set or empty", applied uniformly); (2) a `QUOTAMETER_*` value is the directory itself — no `quotameter` segment is appended — because it replaces the whole path the way `AWS_CONFIG_FILE` does, not the base the way `XDG_CONFIG_HOME` does; (3) relative `XDG_*` values are ignored (default applies) because the XDG Base Directory Specification requires absolute paths and leaves relative ones undefined — silently honoring them would make secret-bearing paths depend on the working directory; (4) relative `QUOTAMETER_*` values are honored, anchored to the current working directory via `path.resolve`, because silently discarding an explicit override could redirect secrets back to the default location; (5) the home directory is a non-empty `HOME` from the injected environment snapshot, else `os.homedir()`, and resolution throws when neither yields a value rather than producing a relative default.

**Reasons.** §6.1 names the variables and defaults but not the edge behavior; these choices keep resolution pure and deterministic (environment and home lookup are injectable, so unit tests never mutate `process.env`), keep results absolute and normalized in every branch, and prefer loud failure over guessing where secrets are stored.

**Consequences.** Consumers (config loading 064, permissions/startup 066, `init` CLI) receive only directory paths — file naming (`config.json`) stays with 064 and directory creation/permission enforcement with 066. Deployments that set a relative `QUOTAMETER_*` value get working-directory-anchored paths; deployments with a broken `HOME` get a startup error explaining the home-directory lookup.

## D-012 — Absolute-home requirement and verbatim values in path resolution (refines D-011)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§6.1](plan/SPECIFICATION.md#61-paths) · **Tasks:** [063](plan/tasks.md) · **References:** D-011

**Decision.** Two refinements of D-011, from the review of task 063. (1) The home directory behind the XDG defaults must be an **absolute** path: a `HOME` that is empty or relative is skipped in favor of the `os.homedir()` fallback — the same fall-through D-011 applies to relative `XDG_*` values — and resolution throws when the fallback is also empty or relative. (2) All variable values are used **verbatim**: a leading `~` is not expanded (matching the XDG Base Directory Specification, which performs no shell expansion), so `QUOTAMETER_CONFIG_DIR=~/conf` denotes a directory literally named `~` under the current working directory.

**Reasons.** (1) With a relative `HOME`, D-011's implementation returned a relative, cwd-dependent default path — contradicting its own "results absolute and normalized in every branch" guarantee and reproducing exactly the cwd-dependent-secrets failure mode that motivated ignoring relative `XDG_*` values; a loud failure is preferable to guessing where secrets are stored. (2) Tilde expansion would import shell semantics (leading `~/` only? `~user`?) that directory-valued environment variables, including the XDG specification itself, do not provide; documenting the verbatim rule is the consistent choice, and the review's only objection was the silent middle ground.

**Consequences.** `src/config/paths.ts` returns an absolute path in every branch or throws. Environments with a relative `HOME` and no usable OS lookup fail with an explanation instead of writing secrets relative to the working directory. The `init`/config documentation (tasks 064, 128) should state that override values are taken verbatim and that `~` is not expanded.

## D-013 — Provider registry semantics and log-safe AccountContext (spec §8.1)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§8.1](plan/SPECIFICATION.md#81-provider-interface) · **Tasks:** [070](plan/tasks.md)

**Decision.** `src/providers/registry.ts` pins four interpretations the spec leaves open: (1) `ProviderRegistry.register` **throws** on a duplicate provider id — and on a blank or whitespace-padded id, a blank name, or non-function methods — instead of replacing or ignoring: registration happens once in the composition root, so a wiring bug must fail at startup rather than silently route accounts to the wrong adapter or surface at the first poll; (2) `get` throws for an unknown id with the registered ids listed, and `has`/`list` support the non-exceptional paths — `list()` returns a fresh array in registration order, giving polling a deterministic sequence; (3) `AccountContext` is a **branded** type (the `Validated<T>` pattern from `src/schemas/boundary.ts`) constructible only through `createAccountContext`, which rejects blank fields, defines `secret` as non-enumerable and read-only, and freezes the object; (4) `QuotaProvider.fetchSnapshot` returns the §8.4 `ProviderSnapshot` from `src/schemas/metrics.ts` unchanged, and the registry performs no runtime validation of snapshot contents — that is the polling service's job (task 093+).

**Reasons.** (1)/(2) The registry's only writers are trusted, compile-time-checked call sites, so its runtime checks target startup wiring mistakes and diagnosability, not untrusted input. (3) Spec §8.1 requires that secrets "remain in process memory and must not be logged": non-enumerability defeats the accidental leak vectors (`JSON.stringify`, `util.inspect`, object spread), branding makes the factory the only construction path so the guarantee cannot be bypassed by building a plain object literal, and error messages never echo values. This is defense at the type/object layer; the exit-side counterpart is the redacting logger (task 072, §15.4). (4) Keeps the registry pure — a mock provider registers and runs through it without any polling, storage, or transport code existing (the task-070 done-condition).

**Consequences.** Future adapters implement `QuotaProvider` and are registered by the composition root; nothing else changes (D-003). Services build `AccountContext` values from validated configuration (boundary 3) via the factory and may hand the object to log calls or spread it — only safe fields travel. Registry error messages are part of the English-only contract and are pinned by tests.

## D-014 — Configuration contract interpretations (spec §6.2)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§6.2](plan/SPECIFICATION.md#6-configuration-and-secrets) · **Tasks:** [061](plan/tasks.md)

**Decision.** The configuration contract in `src/schemas/config.ts` pins these interpretations of §6.2 and its neighbors: (1) **schema/invariants split** — structural rules (types, ranges, patterns, closed enums) live in TypeBox schemas; cross-field rules (exactly one secret source per account, unique account/window ids, IANA time zone validity, `start < end`, same-day window overlap, password required for non-loopback binds or `auth.mode: required`) live in one `findConfigProblems` checker, mirroring the `metrics.ts` precedent (D-010); task 064 composes both into a boundary parser. (2) **Field naming** carries units explicitly (`pollingIntervalSeconds`, `historyRetentionDays`, `requestTimeoutSeconds`); spec §6.2's key names are illustrative, not a contract. (3) **Defaults** are annotated inside the schemas (JSON Schema `default`) and mirrored in one `CONFIG_DEFAULTS` constant with a drift test; `app` is the only required section because `app.timezone` is mandatory and must never be defaulted (§10). (4) **`additionalProperties: false` everywhere**: the file is hand-edited and reloaded (§9.2), so typo'd keys must fail, not silently pass. (5) **Exactly one secret source is an invariant, not a `oneOf` union** — both fields stay optional strings so the derived `AccountConfig` type stays ergonomic for consumers. (6) **The schema is provider-agnostic**: Z.ai's `offPeakMultiplier: 0.5` (§9.1) is seeded data in init/example config, never a schema constraint; `peakHours` is required per provider entry with possibly-empty `windows` (§9.2 "not configured"), and window `multiplier` defaults to `1.0` like `offPeakMultiplier` (§9.2 says "multipliers" plural). (7) **`requestTimeoutSeconds` (5–60, default 15) lives in provider config** because §7.2 fixes the range for provider HTTP requests. (8) **IANA validity follows `Intl` resolution** (aliases, `UTC`, V8's case-insensitive lookup) minus ECMA-402 offset identifiers such as `+03:00` — the same resolver the display path uses. (9) **Account ids and provider record keys are constrained to `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`** because both appear in API paths (§13); the provider record is closed (`additionalProperties: false` alongside `patternProperties`), since a key matching no pattern would otherwise be unconstrained under JSON Schema semantics and skip validation entirely (found in review); loopback for the password rule is `localhost`, `127.0.0.0/8`, `::1` (§15.1/§15.3).

**Reasons.** (1) JSON Schema cannot express the cross-field rules without unreadable `oneOf`/`if-then` constructs, and the project already has a "problems" vocabulary for them (`boundary.ts`); encoding the rules once keeps the config loader, CLI `doctor` checks, and future UI validation from diverging. (2)(3) Explicit units and one defaults source prevent unit confusion and drift between the published JSON Schema (task 062) and applied values (task 064). (4) Silent-ignore of unknown keys is the classic hand-edited-config failure mode. (5) A union type would force narrowing on every consumer for two plain-string fields. (6) Hardcoding vendor values into the contract would violate the provider-agnostic architecture (D-003). (7) The timeout governs provider HTTP calls, so it travels with the provider section and stays independently configurable per provider. (8) Rejecting what `Intl` accepts (or accepting offsets it also accepts) would make config validation disagree with the rendering path.

**Consequences.** Tasks 062–068 and 112 consume these export names unchanged (`ConfigSchema`, section schemas, `Config` types, `CONFIG_DEFAULTS`, `findConfigProblems`, closed enums for UI selects). Adding a configuration field is a schema change plus a `CHANGELOG` entry; adding a provider-specific constraint belongs in provider data, not here. Secrets remain opaque strings: no pattern, no transformation, no echo.

## D-015 — The configuration JSON Schema is a committed generated artifact (spec §6.2)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§6.2, §18](plan/SPECIFICATION.md#62-configuration-contract) · **Tasks:** [062](plan/tasks.md) · **References:** D-014

**Decision.** The published JSON Schema is `schema/config.schema.json` — a **committed, generated** file, not a build-time output. (1) **Source of truth:** `CONFIG_SCHEMA_DOCUMENT` in `src/schemas/config.ts` (an additive export: the contract schema spread under `$schema: draft 2020-12`, `title`, and a `description` marking it structural-only; no `$id` until a canonical distribution URL exists — adding one later is additive). TypeBox schemas are plain JSON Schema and the emitted `exclusiveMinimum` is the numeric 2020-12 form, so draft 2020-12 is declared. (2) **Committed vs generated-at-build:** the development container runs as uid 1000 and must never write into the bind-mounted repository tree, so no CI/check flow may produce the file in-tree. `scripts/generate-schema.mjs` serializes the document deterministically (Prettier's JSON layout, so the artifact is always formatting-clean) into an env-configured output directory (`SCHEMA_DIR`, host default `schema/`, container `/var/lib/quotameter/schema` — the `docs/agents/environment.md` pattern), and `make schema` streams the generated bytes back so a host-side process owns the repository copy. Freshness is enforced where no writes are needed: `test/unit/config-schema-published.spec.ts` asserts the committed file deep-equals the document's JSON projection and pins the constraint keywords (ranges, closed enums, patterns, defaults, `additionalProperties: false` everywhere) that editor tooling and task 064's Ajv compilation read. (3) **Distribution:** the file is allowlisted explicitly in `package.json` `files` and required-present by `scripts/check-package.mjs` (it is always committed, unlike the pre-reserved LICENSE/NOTICE entries). `scripts/verify-build.mjs` is untouched — the schema is a source artifact, not a build output, and the freshness test owns its verification. (4) **Honesty about scope:** the document deliberately excludes the cross-field invariants of `findConfigProblems` (D-014); users are told a config passing the schema may still be rejected at startup/reload. Behavioral validation of the contract stays in `test/unit/config.spec.ts` on the live TypeBox schemas — `Value.Check` dispatches on a `Symbol(Kind)` marker that JSON serialization strips, so TypeBox cannot validate the published file itself.

**Reasons.** (1) Keeping the document inside the contract module makes drift impossible at the source and gives tests, generator, and schema one definition site. (2) A build-time-generated schema would either violate the uid invariant (container writing in-tree) or require CI-only verification with no local gate; a committed artifact verified by a read-only test gives the same guarantee with `make check`. Deterministic serialization keeps regeneration churn-free. (3) An explicit `files` entry plus a required-present tarball check keeps the §4.4 allowlist truthful in both directions. (4) Editors and Ajv read standard keywords, so the artifact's guarantees are exactly the pinned structural keywords; claiming more would mislead users.

**Consequences.** Changing `src/schemas/config.ts` structurally requires `make schema` before `make check` passes (the freshness test names the command). The published path `schema/config.schema.json` is a public artifact: moving or renaming it is a breaking change for users' editor associations and needs a changelog entry and a `D-015` successor. Task 064 compiles the same document/contract with Ajv rather than re-deriving keywords.

## D-016 — Atomic write semantics: pinned 0600 mode, no directory creation, inert stale temps (spec §6.3)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§6.3, §15.4](plan/SPECIFICATION.md#63-secret-storage-and-writes) · **Tasks:** [065](plan/tasks.md) · **References:** D-004

**Decision.** `src/config/write.ts` implements the §6.3 mechanism — serialize, create a same-directory temp file `.<basename>.tmp-<pid>-<random>` with `open('wx', 0600)`, write, `fchmod(0600)`, `fsync`, close, `rename` onto the parameterized target — with four interpretations pinned: (1) the result file mode is **exactly `0600` on every write**, enforced by an explicit chmod that defeats the process umask, rather than copying the replaced file's mode; (2) a missing target directory is a loud `ENOENT` failure — the module never creates directories; (3) stale temp files left by a hard crash are inert garbage with a documented naming pattern, never activated and never blocking later writes (sweeping them is future housekeeping, e.g. 066/doctor); (4) serialization runs before any filesystem effect, and any rejection after temp creation closes, unlinks the temp, and rethrows one wrapped error whose `cause` preserves the original `code` — the message never echoes serialized content, since the config carries secrets.

**Reasons.** (1) `rename` replaces the inode, so the old mode is silently lost in a naive temp-file write; inheriting whatever mode the temp got from creation-plus-umask is how files drift to `0644`, and _copying_ the previous mode would perpetuate permissive drift instead of correcting it — §6.3 fixes the mode at `0600`, and startup enforcement (066) remains the verifier of last resort. (2) Directory creation and `0700` enforcement are task 066's; a silent `mkdir` here would duplicate that work, race its permission fix, and mask caller wiring bugs (e.g. an unresolved path), contradicting the loud-failure precedent of D-011/D-012. (3) Only the final rename can change the active file, so crash leftovers cannot corrupt anything — deleting files this module did not create, in a directory it does not exclusively own, buys nothing. (4) One uniform error shape lets callers (064 loader, future `ConfigService`) branch on `cause.code` without string matching, and the done-condition — an interrupted write can never leave a partially written config as the active file — is testable by injecting failures at every step.

**Consequences.** Task 064 composes this behind config loading and chooses the file name (`config.json`); tasks 066/073+ call it for every settings change, getting `0600` by construction. Stricter-than-`0600` states (e.g. a hand-set `0400`) are themselves non-compliant with §6.3 and are normalized on the next write. Operators are documented (via `src/config/README.md`) that hidden `.config.json.tmp-*` files next to the config are crash residue, not active data.

## D-017 — Single-instance lock semantics: atomic lockfile, pid liveness, safe stale-breaking (spec §5.6)

**Date:** 2026-10-29 · **Status:** Accepted · **Spec:** [§5.6](plan/SPECIFICATION.md#56-process-lifecycle-backups-and-upgrades) · **Tasks:** [074](plan/tasks.md)

**Decision.** `src/server/single-instance.ts` implements the §5.6 requirement "prevent a second process from using the same data directory at the same time" with these pinned interpretations: (1) **Mechanism** — a lockfile `.quotameter.lock` created _inside_ the data directory (the lock keys on the data directory, so different data directories never contend), acquired by writing a unique scratch file and hardlinking it onto the lock path: `link(2)` is exclusive, so acquisition is one atomic decision and the lock is never observable half-written; chosen over a lock directory (breaking needs a two-step unlink+rmdir teardown with no atomicity gain) and over `flock` (requires a native module, forbidden by §3/D-002). (2) **Payload and staleness** — the lock records `{"pid":N,"id":<random token>}`; holder liveness is probed with `process.kill(pid, 0)` (`ESRCH` dead, `EPERM` alive-another-user, anything else conservatively alive); a dead holder's lock is **broken automatically**, because the systemd unit restarts on failure (§5.4) and a refuse-until-manual-removal policy would turn every crash into human intervention; pid recycling is accepted as a safe false-busy (never a false-dead break), so no `/proc` start-time parsing is added. (3) **Race safety** — concurrent contenders are settled by renaming the lock path aside under a name only the renamer knows (one rename wins) and then verifying the captured _content_: stale-breaking removes only a file byte-identical to the one inspected (a replacement installed by the concurrent winner is restored, never over a newer lock), and release removes only a file carrying this acquisition's random token — content identity, not inode identity, because an inode can be reused by a same-path delete-and-recreate; acquisition retries are bounded (`maxAttempts`, default 5); damaged or foreign lock content is never stomped — startup refuses with removal guidance. (4) **Integration** — the primitive is exposed as a `LifecycleComponent` (`createSingleInstanceLock`): acquire in `start` (a refusal throws an actionable English error and aborts startup through the task-060 rollback), release in `stop` (idempotent, infallible); registered first, it is released last, realizing the §5.6 order by construction; the data directory is created if absent (`0700`), while resolution (task 063) and permission enforcement (task 066) stay with their owners; `pid`, the liveness probe, `maxAttempts`, and an `onContended` hook are injectable so every branch is deterministically testable.

**Reasons.** Node's `fs` offers no `flock`, and the spec forbids native modules and new dependencies for this task; the link-publish pattern gives O_EXCL semantics without an empty-file window; pid liveness beats mtime/lease staleness for crash recovery (no timers, no flakiness) and errs only in the safe direction; the rename+content verification is the classic lockfile safeguard against the two racers that can otherwise both end up "holding" the lock (unlink-racing breakers, and release-after-replacement), with a random token per acquisition because inode numbers can be recycled by same-path recreation.

**Consequences.** The composition root passes the resolved data directory into `createSingleInstanceLock` when it assembles components; two Quotameter processes on one data directory coexist never, on two data directories always. The lock payload format (`{"pid":N,"id":<token>}` plus tolerated extra fields) is a cross-process contract followed by test tooling and future tooling alike. After a crash the next start self-heals; after a pid-recycle false busy the error names the lock file to remove. Graceful-shutdown orchestration around the component (in-flight wait, WAL checkpoint) stays with task 075.

## D-018 — Configuration loading: Ajv 2020-12, explicit defaults, problems-only failures (spec §6.2)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§3, §6.1, §6.2, §15.4](plan/SPECIFICATION.md#62-configuration-contract) · **Tasks:** [064](plan/tasks.md) · **References:** D-011, D-014, D-015, D-016

**Decision.** `src/config/load.ts` composes the contract (D-014), the resolved directories (D-011), and the atomic writer's path convention (D-016) into trust boundary 3's runtime side, with these pinned interpretations: (1) **Engine** — the TypeBox contract is compiled once with the 2020-12 variant of Ajv (`ajv/dist/2020`, `allErrors: true`), adding `ajv` as a runtime dependency per spec §3 ("TypeBox + Ajv") and D-015's recorded intent ("task 064 compiles the same document/contract with Ajv"); the 2020-12 variant is required because TypeBox emits the numeric `exclusiveMinimum`, which draft-07 Ajv rejects. A unit parity test guards the compilation against drift from TypeBox's own `Value.Check`. (2) **Defaults are applied explicitly from `CONFIG_DEFAULTS`, not via Ajv's `useDefaults`** — three grounds: Ajv _documents_ default insertion only for `properties`/`items` schemas, so whatever a given version does with the providers record's (`patternProperties`) three defaults (`requestTimeoutSeconds`, `offPeakMultiplier`, window `multiplier`) is undocumented behavior (ajv 8.20 happens to apply them — verified in review — but relying on that pins the loader to an implementation detail); `useDefaults` mutates the validated input, breaking the parser's read-only-input guarantee; and it cannot materialize absent whole sections, which the canonical output needs. `applyConfigDefaults` runs after structural validation and materializes **every optional section** (`providers: {}`, `accounts: []` when absent), so the loader's output is canonical and consumers never re-implement fallback precedence, while absent secrets (`passwordHash`, `apiKey`, `apiKeyEnv`) stay absent instead of becoming `undefined` keys. (3) **Readable, field-specific, value-free problems** — Ajv errors are re-worded into `<path>: <message>` (`server.port: must be >= 1`, `auth.mode: must be one of: 'auto', 'required'`, `providers: property name 'za i' must match the pattern …`), with failed literal unions collapsed from their per-branch `const` errors into one "must be one of" line, record-key rejections distinguished from plain typos via the parent schema's `patternProperties`, and type errors naming the actual JSON type; **no data value is ever echoed** (spec §15.4) — only paths, schema constants, limits, and type names. (4) **JSON errors are redacted** — V8 embeds a quoted input snippet in some `JSON.parse` messages (`Unexpected token 's', "{"a": sec}" is not valid JSON`), which could quote a secret from the broken line, so the snippet is stripped. (5) **Failures are problems, never throws** — missing file (`configuration file not found: <path>`, distinct for `init`/`doctor`), unreadable file (`… : EACCES`), malformed JSON, schema violations, and cross-field violations all return `{ ok: false, problems }` in the `BoundaryParser` vocabulary; the caller (startup, reload, `doctor`) decides what to do, keeping spec §6.2's "refuse to start and explain" / "retain the last valid configuration" in the consuming tasks. (6) **File naming pinned**: `config.json` (spec §6.1 names it), exported as `CONFIG_FILE_NAME` + `configFilePath(configDir)`.

**Reasons.** (1) The spec names the pairing and two landed decisions already anticipate Ajv; deviating to TypeBox's `Value.Errors` would deviate from the §3 letter for no gain, and Ajv's compiled validator plus its `params` (comparison, limit, pattern, allowed values) is exactly what readable messages need. (2) Only documented validator behavior is relied upon: defaults live in one visible, tested pass instead of depending on which keyword positions a validator version happens to support, the parser stays pure (its input is never mutated), and `CONFIG_DEFAULTS` is already drift-locked to the schema annotations — sourcing from it is equivalent to sourcing from the annotations. (3) Field-addressed messages are the contract's own convention (`findConfigProblems`), and hand-editing is the primary workflow (spec §9.2: users edit JSON and run `quotameter reload`), so message quality is a feature; suppressing the per-branch noise of failed unions keeps one mistake one line. (4) §15.4 forbids secrets in error messages; the snippet is the one place a parser would leak one. (5) The problems-only result is the established boundary vocabulary, makes the loader total (no exception paths to test separately), and leaves policy to the tasks that own it. (6) Spec §6.1 fixes the name; exporting it removes the last hardcoded string from future callers.

**Consequences.** Consumers call `loadConfigFile(configFilePath(resolveConfigDir(env)))` and get either a `Validated<Config>` canonical object or problems; `parseJson` and `parseConfig` are exported as composition seams for env overrides (067: inject between the two) and reload (068: re-run the pipeline, keep the last valid result on failure). `doctor` reuses `formatSchemaError` for schema diagnostics. Startup permission checks (066) and writes (065) are untouched and composable. Adding a configuration field remains a schema change plus defaults entry; message wording is pinned by unit tests and is part of the English-only contract. `ajv` is the only runtime dependency this task adds (spec §3's "keep runtime dependencies minimal" respected: one package, no transitive dependencies).

## D-019 — Configuration permission enforcement: exact modes, verified fixes, refusal on the uncorrectable (spec §6.3, §15.4)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§6.3, §15.4](plan/SPECIFICATION.md#63-secret-storage-and-writes) · **Tasks:** [066](plan/tasks.md) · **References:** D-004, D-016

**Decision.** `src/config/permissions.ts` implements the §6.3 startup rule — "verify permissions; fix them when possible, otherwise refuse to continue" — with these pinned interpretations: (1) **Exact modes**: compliance means `mode & 0o7777` equals `0700` (directory) / `0600` (file), so setuid/setgid/sticky bits are cleared by the same fix, and stricter-than-required states (a hand-set `0500`/`0400`) are corrected, not accepted — the exact-mode policy D-016 already pins for writes. (2) **Fix = explicit `chmod` + re-verify**: `chmod` is umask-exempt (the creation-side counterpart of D-016's `fchmod`), and the mode is re-read afterwards, so a filesystem that accepts but does not apply the correction (simulated in tests, real on exotic mounts) still refuses startup. (3) **Directory creation** walks the missing levels of the path and creates them one at a time, each `mkdir` followed by an explicit `chmod` to `0700` — a single recursive `mkdir` applies `mode & ~umask` to every level it creates, and a umask containing the owner-execute bit (e.g. `0177`) would leave the first new ancestor untraversable (`0600`), failing the next level's creation with a misleading `EACCES` (review finding, task 066); pre-existing levels are never touched, because §6.3 pins the configuration directory itself and the ancestors hold no secrets. (4) **The configuration file is never created by enforcement**: an absent file passes (`'absent'`) — creation with `0600` by construction belongs to the write path (D-016), and an empty placeholder would be invalid JSON for the loader (064); startup enforcement is the verifier of last resort. (5) **Symlinks are refused on the final objects only**: a symlinked directory or file redirects where a `chmod` would land (and, for a directory, where later writes resolve; the atomic write's `rename` would instead replace a symlinked file) — either way the operator's redirect is not honored, so both are refused; symlinked _ancestors_ are not policed, because normal path resolution through them still yields the real secret-bearing objects, which the mode checks then bind, and a symlinked `~/.config` is a legitimate OS configuration this project must not reject. (6) **Ownership precedes fixing**: both objects must belong to the running uid (`process.getuid`; undeterminable → refuse, mirroring the task-060 runtime gate) — a foreign-owned object is uncorrectable by `chmod` for a regular user, and root is already banned at the runtime gate. (7) **Integration**: the check is exposed as a lifecycle component (`createPermissionsCheck`, name `config-permissions`) in the 074 shape — `start` enforces and a refusal aborts startup through `QuotameterApp`'s rollback; `stop` is a no-op. The component type is _structural_: the config layer may not import server code (package layout), so compatibility with `LifecycleComponent` is proven at the consumption site; composition-root wiring stays with the later assembly task.

**Reasons.** (1) Accepting stricter modes would leave the write path (D-016 pins exactly `0600`) and the verifier in disagreement about what "compliant" means, and a `0500` directory breaks temp-file writes inside it. (2) An unverified `chmod` is a silent pass on filesystems that do not implement modes; re-reading the mode is the honest definition of "fixed". (3) Policing ancestors would reject standard setups (a `0755` `~/.config`) that §6.3 never mentions, and per-level chmod is what keeps creation working under any umask. (4) Creating an empty config would turn "not configured yet" into a parse error and duplicate the write path's creation logic. (5) Following a symlinked secret location would move secrets off the operator-controlled path `chmod` verified — exactly the redirection §15.4 exists to prevent — while rejecting symlinked ancestors would reject legitimate systems without any security gain. (6) Attempting `chmod` on a foreign-owned object just converts a clear configuration mistake into an opaque `EPERM`. (7) Keeps task 060's files untouched and the config layer import-clean, exactly as 074 did.

**Consequences.** The composition root (later assembly task) resolves paths via 063, names the file via 064, and registers `createPermissionsCheck` among the components; operators with uncorrectable states get one actionable English error naming the path, the found/required modes or uids, and the remedy. The `PermissionsResult` states (`created`/`absent`/`secure`/`corrected`) are the vocabulary for the future structured logger (072) and `doctor` checks. Test seams (`filesystem`, `getuid`) exist solely for deterministic integration tests; production callers never pass them. Enforcement is a startup verifier, not a race-free guard against a concurrent writer in a parent directory: the path-based `lstat` → `chmod` window can end only in a refusal or a mode-restricting change (the post-fix re-read sees a substituted symlink and refuses), never in a silent unsafe pass.

## D-020 — Graceful-shutdown drain semantics: one shared in-flight wait between schedulers and storage (spec §5.6)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§5.6](plan/SPECIFICATION.md#56-process-lifecycle-backups-and-upgrades), [§17.1](plan/SPECIFICATION.md#171-required-test-coverage) · **Tasks:** [075](plan/tasks.md) · **References:** D-017

**Decision.** `src/server/shutdown.ts` implements the §5.6 sequence "stop scheduling new polls, wait up to 10 seconds for an in-progress request, close the database, checkpoint WAL" with these pinned interpretations: (1) **Placement** — the bounded wait is a dedicated `graceful-drain` `LifecycleComponent` registered _between_ storage and the schedulers (`[lock, storage, graceful-drain, polling, http]`), so the reverse-order teardown of `QuotameterApp` (task 060) yields the §5.6 order by construction: the schedulers stop scheduling first, the drain waits once for _all_ in-flight work (provider polls and HTTP requests alike), storage closes behind it, and the lock releases last (D-017). One centralized wait was chosen over per-subsystem drains because the polling service and HTTP listener do not exist yet (109+, 146) — a shared seam they plug into cannot duplicate timing semantics, and "in-progress request" in §5.6 covers both kinds of work. (2) **Tracker** — `createInFlightTracker` is a deliberately dumb shared counter (`begin()`/idempotent `done()`, `whenIdle()`); refusing new work ("stop scheduling") stays each scheduler's own `stop`, enforced by the stop order. The 10 s bound caps how long work in flight when the drain starts can delay shutdown; work begun after the count reaches zero is outside the wait — the tasks that build the schedulers (109+, 146) own the "no work after `stop`" contract. (3) **The bound is an invariant, not a knob** — `timeoutMs` defaults to 10 000 ms and is validated fail-fast at assembly to a finite number in (0, 10 000], mirroring the registry's wiring-check style (D-013); §5.6 fixes "up to 10 seconds" and no configuration raises it. (4) **Forced completion** — when the bound expires, the wait is abandoned, a `drain-timeout` event (with the still-in-flight count) reports it, teardown proceeds, and a later `done()` is harmless by idempotency; an idle application shuts down silently (nothing to report). (5) **Seams** — the timeout clock and monotonic `now` are injectable (`setTimeout` and `performance.now` defaults), so §17.1's "clean SIGTERM shutdown" tests run deterministically without fake-timer patching of process globals (Stryker runs tests in worker threads); `onEvent` (`drain-started`/`drain-completed`/`drain-timeout`) is the structured-logger seam (task 072) with 060's synchronous, swallow-errors `onLifecycle` contract; the idle path cancels its timer so no handle outlives the shutdown.

**Reasons.** The app skeleton already owns ordering, error isolation (a failing `stop` never skips the rest), and stop coalescing — re-implementing any of that in a coordinator would duplicate 060; the only missing §5.6 piece is the timed wait, which slots in as one component. A dumb tracker keeps "stop scheduling" where the spec puts it (the poll scheduler, §7.1) and makes misuse bounded rather than unobservable. Enforcing the 10 s ceiling at the module boundary turns a spec bound into a checked invariant instead of a convention. Abandoning the wait at the deadline (rather than killing work) is the only option available from outside the components — the process must exit within systemd's shutdown expectations — and logging the forced completion keeps it diagnosable (§16 lifecycle events).

**Consequences.** The future composition root registers the drain between storage and the schedulers when `buildComponents()` gains real components (polling and HTTP track their operations in the shared tracker; storage's `stop` owns the database close and WAL checkpoint). Signal-handling timing — installing handlers before `app.start()` and stop-during-startup semantics — remains with `main.ts`, which this task must not edit; the note stays for the first task that extends `buildComponents()`. The `ShutdownEvent` vocabulary and the tracker API are the integration contract for tasks 109+ and 146; `MAX_DRAIN_TIMEOUT_MS` is the single name for the §5.6 bound.

## D-021 — Canonical clock API: explicit zones, injectable now, no machine-local paths (spec §10)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§10](plan/SPECIFICATION.md#10-time-and-time-zones) · **Tasks:** [071](plan/tasks.md) · **References:** D-009, D-013, D-014

**Decision.** `src/util/clock.ts` is the canonical time API server-side business logic uses, with these pinned interpretations: (1) **Zones are explicit and branded** — a zone reaches the conversion/formatting helpers only through `resolveTimeZone`, which validates and returns a branded `TimeZone` (the construction-gate pattern of `AccountContext`, D-013); no function reads the system zone, `TZ`, Luxon `Settings`, or `DateTime.now()`, so "works consistently under any `TZ` setting" (§10) holds by construction, not convention. Runtime re-validation stays in every public helper: `zonedDateTime` re-runs the same IANA gate (memoized, so formatting loops pay no per-call `Intl` construction) because Luxon alone would accept pseudo-zones such as `local`, `system`, or `utc+4` — offset/machine-local zones that silently reintroduce exactly the §10 failure mode — and checks Luxon's `.isValid` for non-finite/out-of-range epochs (found in review). (2) **IANA validity is a deliberate twin of `isValidTimeZoneName` in `src/schemas/config.ts`** — identical semantics (D-014 item 8: `Intl` resolution minus ECMA-402 offset identifiers) duplicated because `schemas` and `util` are both leaves and cannot import each other (D-009); a parity test (fixed corpus plus a fast-check property over generated strings) locks the twins together instead of an import. (3) **Injectable now** — `Clock` exposes `now()` (UTC epoch ms) and `monotonicMs()`; `createSystemClock` owns the only sanctioned `Date.now()` call site, and `createFixedClock` is the test double (`set` jumps the wall clock while the monotonic reading is untouched — the shape of an NTP correction §10 assumes away; `advance` moves both readings and accepts negative deltas, since a double may deliberately simulate skew). Services receive a `Clock` and never construct time themselves. (4) **ISO strictness** — `toUtcIso` always emits millisecond precision with a `Z` suffix (§10 "ISO 8601 UTC ending in Z"); `epochMsFromIso` accepts only strings carrying an explicit `Z`/`z` or `±HH:mm`/`±HHmm` offset, because offset-less strings are exactly where Luxon would silently interpret in its default (system) zone — the failure mode this module exists to prevent. (5) **Wall-clock → epoch conversion is deliberately absent** — that direction is where DST nonexistent/ambiguous times live, and §9.3 fixes the policy (shift forward by the gap; first occurrence), owned by task 115; this module exposes only the unambiguous epoch → wall-clock direction plus the `zonedDateTime` Luxon bridge that tasks 114 (peak-hours intervals), 115, and 116 (rolling ranges) build on. (6) `luxon` becomes a runtime dependency (spec §3 names it; no own type definitions — `@types/luxon` is the dev dependency).

**Reasons.** (1) An injectable, zone-explicit API is the only shape that makes the §10 done-condition ("business logic does not depend on implicit machine-local time") mechanically true; a lint rule or convention would not survive parallel tasks. (2) Lifting the leaf rule to share one validator would couple the configuration contract to `util` or vice versa — both are consumed by disjoint task waves; a tested twin is cheaper than an architecture change and fails loudly at `make check` if either side drifts. (3) Fixed-clock semantics distinguish wall-clock jumps from elapsed time because §10 assumes NTP-synchronized clocks — the double must be able to model the correction, not just uniform passage. (4) The API contract fixes `Z`-terminated UTC, so the parser should accept nothing the formatter cannot round-trip. (5) Keeping DST policy single-sited in task 115 avoids two half-implementations of §9.3 disagreeing at a transition.

**Consequences.** The composition root (later task) creates one system `Clock` and injects it into services; tests use `createFixedClock` instead of fake timers where a clock seam suffices. Consumers convert zones via `resolveTimeZone` once at their boundary (configuration load, provider setup) and pass the branded value onward. Spec §17.1's full time-zone matrix (task 126) extends `test/unit/clock*.spec.ts` conventions without touching the API. Any change to D-014 item 8 semantics now requires deliberately editing both validators and their parity test — that friction is the point. Coverage of `clock.ts` is 100% lines/branches (§17.3 target for time-zone logic).

## D-022 — Settings-validation service boundary: normalize, merge, delegate (spec §5.3, §6, §7.1)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§5.3, §6](plan/SPECIFICATION.md#6-configuration-and-secrets), [§7.1](plan/SPECIFICATION.md#71-polling) · **Tasks:** [073](plan/tasks.md) · **References:** D-014, D-018

**Decision.** `src/services/config-validation.ts` implements task 073 as a single service-facing entry point, `validateSettings(submission, base?)` — the validation half of the future `ConfigService` — with these pinned interpretations: (1) **One submission vocabulary, config-shaped**. The submission is untrusted, config-shaped but loosely typed input (`{ server: { host, port }, app: { … }, auth: { … }, … }`); `init` (task 128+) and the CLI map their flat §5.3 answers (`--host`, `--port`, `--timezone`) onto these sections. A second, flat service vocabulary was rejected: a flat `requestTimeoutSeconds` cannot address a provider, and accepting both shapes would need conflict rules for every key. (2) **Strictly additive over the landed parser** (D-014/D-018): the service adds only what a string/JSON-boundary entry point needs — numeric-string coercion for the four integer settings (`server.port`, `app.pollingIntervalSeconds`, `app.historyRetentionDays`, `providers.<id>.requestTimeoutSeconds`) and the two peak-hours multipliers; trimming for non-secret strings; blank-after-trim means "not supplied" (§5.3: an empty prompt answer keeps the current value or default). Secrets (`apiKey`, `passwordHash`, the plaintext password) are verbatim and never echoed. Unknown keys pass through verbatim at **every** level, so `additionalProperties: false` in the landed schema stays the single authority that rejects typo'd keys. Ranges, enums, and cross-field invariants are never re-stated: a coerced value re-enters `parseConfig`, and a non-numeric string fails with one field-specific message (`server.port: expected an integer`) instead of the parser's `got a string` (true of every prompt answer, informative of none). (3) **Merge over the current configuration** (§5.3 idempotent init): `base` is the current validated config; objects merge field-wise, arrays (`accounts`, peak `windows`) and non-object section values replace wholesale (PUT semantics); the cross-field rules are re-checked against the merged result. (4) **The plaintext password is an entry-only setting** (§5.3 step 4, §15.2): the schema knows the scrypt hash, never the password, so its rules live here — at least 12 characters (§15.2), blank = skipped, never trimmed, mutually exclusive with `passwordHash`. A valid password is validated as the post-hashing state by substituting a placeholder hash — any non-empty opaque string is schema-equivalent to a scrypt hash (`minLength: 1`; the §15.1 invariant checks presence only) — which beats recognizing the invariant's message by string matching (fragile coupling to wording this module does not own). The placeholder never leaves the module; the result carries the password as `pendingPassword` plus an **unbranded** config (deliberately not `Validated<Config>`: the hash must still be written by the Stage-12 auth service), and the file a caller writes is re-validated by the loader on the next start, so trust boundary 3 stays intact end-to-end.

**Reasons.** Task 073's dimensions (intervals §7.1, timeouts §7.2, retention §11.3, host and port §5.3, auth §15.1) are already enforced by the landed contract — duplicating them in a service layer would create a second source of truth that drifts on every schema change (the exact failure mode D-014's single-checker rule exists to prevent). What the file-oriented parser cannot do is accept prompt/CLI strings, blank answers, partial updates over an existing config, or a plaintext password — the four additions above. The placeholder-hash validation checks a real, reachable state (the configuration as it will exist after hashing) rather than special-casing parser output, and the unbranded pending config prevents the `Validated` brand from asserting a guarantee (password rule satisfied) the object does not have.

**Consequences.** Task 128+ (`init`, CLI flags) and Stage 12 (`PUT /api/settings`, `AuthService`) consume `validateSettings` instead of calling Ajv or the parser with raw request data; `MIN_PASSWORD_LENGTH` is the single name for the §15.2 bound (UI password forms reuse it). Message wording is pinned by `test/unit/config-validation.spec.ts` and is part of the English-only contract. Adding a configuration field needs no change here unless the field requires coercion or entry-only semantics; adding either is a schema/service pair change plus a test. The module owns no filesystem, clock, or logging concerns — those stay with the config layer and the future `ConfigService` runtime half. Two forward-looking limits recorded for the consumers (review findings, task 073): the keep-or-change merge has **no erase semantics** — blank/omitted keeps the stored value, so clearing a field (a stored `passwordHash`, a configured provider) needs an explicit operation in the Stage-12 `ConfigService`, not this boundary; and wholesale `accounts` replacement combined with §6.3/§15.4 masked reads means a naive GET-then-PUT settings client would drop stored `apiKey`s — the settings endpoint must merge account secrets server-side or accept per-entry diffs.

## D-023 — Environment overrides: seven mirrored variables, parser-judged values, strict unknown-name rejection (spec §6.3, §6.4)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§6.3, §6.4](plan/SPECIFICATION.md#63-secret-storage-and-writes), [§14.5](plan/SPECIFICATION.md#145-settings) · **Tasks:** [067](plan/tasks.md) · **References:** D-011, D-014, D-018

**Decision.** `src/config/env.ts` implements the §6.3/§6.4 rule "environment-defined values take precedence and are read-only in the UI" with these pinned interpretations: (1) **Variable mapping** — exactly seven scalar settings are overridable (`server.host`, `server.port`, `app.timezone`, `app.pollingIntervalSeconds`, `app.historyRetentionDays`, `auth.mode`, `logging.level`, published as the `ENV_OVERRIDES` table); variable names are the mechanical mirror of the field path (upper-cased, `.` → `_`, camelCase → SNAKE_CASE, e.g. `QUOTAMETER_APP_POLLING_INTERVAL_SECONDS`), so the mapping is derivable in both directions and carries D-014's explicit units. Secrets deliberately have no `QUOTAMETER_*` channel: account keys already use the per-account `apiKeyEnv` (§6.3), and the password hash has no spec-named environment alternative; structured sections (`providers`, `accounts`) do not map to single environment strings and stay file-only. (2) **Composition** — `load.ts` (064) is composed, never edited: `parseConfigWithEnv(fileInput, env)` splices coerced values on top of the parsed file input and validates the whole through `parseConfig`, so an environment value fails exactly like a file value, with the same field-addressed, value-free problems (§15.4); `loadConfigWithEnv` composes `loadConfigFile` plus that layer — the pipeline startup and the 068 reload re-run. (3) **Coercion** — integer fields convert only pure decimal digit strings (`/^[0-9]+$/`); every other value passes through as a string and the landed parser rejects it (`server.port: expected an integer, got a string`); ranges, enums, IANA validity, and cross-field rules (a password is still required for `QUOTAMETER_AUTH_MODE=required` or a non-loopback `QUOTAMETER_SERVER_HOST`, §15.1) all come from the parser — the layer adds no error vocabulary of its own for values. (4) **An empty string counts as unset** at every level (the uniform D-011 rule). (5) **Unknown `QUOTAMETER_*` names are rejected** (`QUOTAMETER_SEVER_PORT: unsupported environment variable`, sorted by name in codepoint order — locale-independent, so problem order is host-stable) — a typo must fail, not silently pass, extending D-014's closed-contract philosophy from typo'd keys to typo'd variables; `QUOTAMETER_CONFIG_DIR`/`QUOTAMETER_DATA_DIR` are known and ignored here (owned by `paths.ts`, 063), and child-process test-runner variables never reach the service's snapshot. (6) **Absent file** — when the loader reports the pinned `configuration file not found: <path>` problem and at least one override is set, the effective configuration is built from the environment alone (§6.3; a success carries `fileAbsent: true`, a failure prepends the not-found problem so both facts are explained); with no overrides the missing file is the problem itself (unsupported `QUOTAMETER_*` names are still scanned and reported beside it, so a typo does not wait for a file to appear), and every other file failure (unreadable, invalid JSON, schema or cross-field problems) passes through verbatim — the environment never masks a broken file and overrides never rescue one (a malformed file section is left as-is for the parser to report; an override must not silently "repair" it). (7) **Read-only marking** — the success result carries `sources`: the overridden field paths in table order (a set variable marks its field even when the value coincides with the file's) plus the ids of accounts whose secret source is `apiKeyEnv` (§6.3 "environment-defined … read-only in the UI"); the marking is the data the Stage 12/13 API and UI surface (§14.5), frozen, and never contains a value.

**Reasons.** (1) The spec names only the path variables (§6.1) and the per-account `apiKeyEnv` mechanism; a closed, mechanically named set makes the feature documented by derivation (task 187), typo-checkable, and honest about what environments configure well — single scalar operational settings, not schedules or account lists. (2) The task 064 seam exists precisely so validation is not duplicated: re-running the whole merged configuration through one parser is what makes cross-field rules hold for the _effective_ configuration (e.g. an environment mode flip cannot bypass the §15.1 password rule) and keeps every message in the established problems vocabulary. (3) Value-free, field-addressed errors are already the contract (D-018); inventing a parallel per-variable error vocabulary for bad values would double the wording surface for no diagnostic gain. (5) Silent-ignore is the classic typo failure mode D-014 rejects for keys; rejecting unknown names converts a mystifying "my port didn't change" into one actionable line. (6) Env-only must be a first-class mode (§6.3), but "file missing" must not masquerade as a schema complaint when nothing is configured, nor may a partial environment hide a broken file — provenance is reported on both result paths. (7) The UI needs one authoritative marking; deriving "environment-defined" from the config at render time would re-implement precedence knowledge in Stage 13.

**Consequences.** Consumers call `loadConfigWithEnv(configFilePath(resolveConfigDir(env)), env)` (startup) or the same function on SIGHUP (068) and receive either the validated effective configuration plus `sources`, or problems; `fileAbsent` exists so callers can log the env-only mode (§16) without re-deriving absence by string matching. Adding an override is an `ENV_OVERRIDES` row plus schema/default agreement, a CHANGELOG entry, and documentation (task 187); the known-name set grows only through a decision. The Stage 12/13 settings API serializes `sources` for the read-only annotations of §14.5; account key inputs whose id appears in `accountSecrets` render read-only with the `apiKeyEnv` name, and overridden scalar fields render read-only with their variable name. The `QUOTAMETER_TEST_RUNNER_*` helper variables of test runners remain outside the scan's scope because they are set only in spawned child processes, never in the service environment. A consequence of the strict scan worth recording: an `apiKeyEnv` value must not itself start with `QUOTAMETER_` — the schema's variable-name pattern permits it, but a variable so named would be set in the service environment and rejected as unsupported; the reservation is documented in the module README, and a schema-level rejection would be a `src/schemas/config.ts` change (outside this task's ownership) for a future decision if it proves worth pinning in the contract itself.

## D-024 — Signal-readiness handshake for child-process lifecycle tests: the `onSignalsReady` seam (spec §5.6, §17.1)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§5.6](plan/SPECIFICATION.md#56-process-lifecycle-backups-and-upgrades), [§17.1](plan/SPECIFICATION.md#171-required-test-coverage) · **Tasks:** [U-001](plan/tasks.md)

**Decision.** The kill-before-handler race in task 060's child-process tests is closed with a readiness handshake, pinned as follows: (1) **Root cause** — the `started` marker is written inside a component's `start()`, but `runServer` installs its SIGTERM/SIGINT listeners only after `app.start()` settles (component hook → lifecycle emits → two promise continuations); the marker file is visible to the parent across the process boundary the moment it is written, so a signal delivered while the child process has not yet been scheduled past that continuation hits the OS-default disposition and kills the child (exit-by-signal, no `stopped` marker). Measured in the dev container (8 cores) under 8 host-wide `yes > /dev/null` processes with a `setImmediate` marker poller, alternating SIGINT/SIGTERM: 187 of 200 children died by their signal — a wide window under load, invisible at idle. (2) **Seam** — `RunServerOptions.onSignalsReady?: () => void`, a synchronous, opt-in callback invoked exactly once immediately after `installShutdownSignals()` returns, inside the existing `try`/`finally` so a throwing callback still disposes the listeners and clears the keep-alive interval; the error then propagates to the caller of `runServer`, matching "the caller owns the process". Absent by default, production behavior is byte-identical and the composition root never passes it. (3) **Handshake channel** — the runner (`test/helpers/serverMainRunner.ts`) writes a `signals-ready` marker file (`writeFileSync`) in the callback, and the spec waits for it (existing `waitForFile`) before `kill(signal)`; both signal tests harden through the shared `runUntilCleanStop` helper. (4) **Contract tests** — in-process tests pin that the callback fires exactly once by the first macrotask after start with both shutdown listeners already registered (and a signal-triggered shutdown then exits 0), that it never fires when the runtime gate refuses to start, and that a throwing callback rejects `runServer` while the `finally` still disposes the listeners and clears the keep-alive interval (fail-fast: the started components are not stopped on that path). Rejected alternatives: an environment-gated stderr marker inside `main.ts` (production code parsing test variables, a new stderr contract on the pre-logger `reportFatal` channel, and `process.exit` can truncate pending pipe writes, so stderr is not a durable handshake channel); runner-side signal listeners installed before `runServer` (they would change the very OS-default disposition under test — an early signal would be swallowed and the child would hang instead of exiting, trading a flaky failure for a deterministic one); test-side retry after a signal death (asserts on the flake instead of eliminating it); monkey-patching the global `process.on` or polling `process.listenerCount` in the runner (they observe the mechanism, not the contract — blind to whose listener registered, and they hang loudly when handler installation moves or changes API).

**Reasons.** §17.1 requires the lifecycle coverage to verify the §5.6 graceful-shutdown semantics — a test that races the scheduler verifies nothing and fails "3/3 in isolation, once in a full run" exactly as observed. The callback follows the established injected-facts pattern of `RunServerOptions` (`runtime`, `components` are already test-injectable), is type-checked, directly unit-testable (v8 branch coverage and Stryker both run over `src/**`), and keeps every test-only concern in the runner where the existing `QUOTAMETER_TEST_RUNNER_*` modes live. A marker file is durable where a pipe write is not, and reuses the `started`/`stopped` observation channel unchanged.

**Consequences.** Future child-process harnesses signal only after `signals-ready` (the SIGHUP reload test of task 068 will need the same discipline). If a later task moves handler installation ahead of `app.start()` — the move `main.ts`'s comment reserves for stop-during-startup semantics — the callback moves with that call site and these tests stay valid: they require only "handlers installed before the signal", not a specific installation point. Under the same 8×`yes` load the handshake measured 200/200 clean exit-0 children (kill on `signals-ready`), 30 consecutive runs of `test/integration/server-main.spec.ts` were green, and two full `make check` runs passed. The SIGTERM child test of `single-instance.spec.ts` (task 074's file, outside U-001's ownership) keeps the same theoretical window — practically closed there by the contender process's full startup between the lock write and the signal; hardening it with the same seam is recorded as a follow-up, not silently changed here.

## D-025 — Structured logger: two-layer redaction, full Pino ladder, never-throw emission (spec §16, §15.4)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§16](plan/SPECIFICATION.md#16-logging-and-diagnostics), [§15.4](plan/SPECIFICATION.md#154-secret-protection) · **Tasks:** [072](plan/tasks.md) · **References:** D-013, D-020, D-023

**Decision.** `src/util/logger.ts` implements the redacting structured logger with these pinned interpretations: (1) **Two redaction layers around one Pino instance.** Layer B — the wrapper every first-party call site uses — deep-sanitizes the message string and the merging object _before_ Pino sees them: sensitive keys by name at any depth (normalized matching — lowercase, non-alphanumerics stripped — so `apiKey`/`API_KEY`/`api-key`/`api_key` are one entry), known secret values supplied at creation scrubbed from every string via literal split/join (no regex-escaping hazards), and `Error` values at any position normalized through Pino's `errWithCause` (message, stack, cause chain, aggregated members, custom enumerable properties) and then sanitized — so a secret embedded in an error message or stack cannot survive. Degenerate values fail closed without costing the record: an invalid `Date` serializes as `null` (JSON's own rendering — its `toISOString()` throws), and a value whose property access throws (a hostile getter) collapses to an `[Unreadable]` placeholder in place — object properties, array elements, and error properties each individually — so one hostile value never drops the emitted record. Layer A — Pino `redact` paths (every sensitive spelling at depths 0–2, the deepest wildcards Pino's redaction supports) plus an `err` serializer running the same sanitizer — protects the raw instance exposed as `logger.pino`, which integrations (the Fastify/pino-http logger of task 146) consume directly and which must therefore redact on its own; arbitrary depth and message scrubbing on that raw path are Layer B's job, documented as the division. Pino's native redaction alone was rejected as the sole mechanism: path wildcards cannot reach arbitrary nesting, cannot match key spellings they do not enumerate, and have no value-based (marker) redaction or message-string scrubbing at all. (2) **Levels.** The wrapper exposes all six Pino levels (`trace`…`fatal`) while spec §16's four supported levels (`error|warn|info|debug`, default `warn`) remain the _configuration_ policy pinned by `LOG_LEVELS` in `src/schemas/config.ts` — a deliberate twin of the clock/schema validator pattern (both layers are leaves, D-009), needed because the task's done-condition demands a marker-secret proof at every level and §16's four would leave `trace`/`fatal` records unprovable; `fatal` also gives future crash paths a level. `setLevel` exists for the reload path (D-023 `QUOTAMETER_LOGGING_LEVEL`). (3) **Destination.** One injectable JSON-line stream defaulting to `process.stdout` (§16 "stdout/stderr, collected by journald"; no application-managed files or rotation); tests inject in-memory sinks and never patch `process.stdout`, and `no-console` stays an ESLint error in `src/**`. (4) **Failure contract.** Construction validates options and throws (wiring mistakes fail fast, the registry style of D-013), but every log call is synchronous and never throws — D-020's diagnostics rule applied to emission, so a broken destination or a hostile payload with throwing getters cannot take down business code. Emitters check `isLevelEnabled` before sanitizing, so records the level filter discards (the default `warn` makes `debug`/`info` calls the hot path) pay no deep-sanitization cost — filtering and redaction compose without waste. (5) **Lifecycle seam.** `createLifecycleSink(logger)` returns a synchronous, never-throwing `(event) => void` that logs `lifecycle: <type>` at `info` (§16: at `info`, log only lifecycle events — at the default `warn` they are filtered, by design). Its parameter type is the structural supertype `{ type: string } & Record<string, unknown>`, assignable from both the `LifecycleEvent` union of `src/server/app.ts` and the `ShutdownEvent` union of `src/server/shutdown.ts` without importing either — `src/server/*` adopts it with zero edits to this module. (6) **Sensitive-key vocabulary** is a closed, exported list (`SENSITIVE_KEY_NAMES`) that errs on the side of redaction; entries are added freely (more redaction is safe) and documented in `src/util/README.md`. The non-enumerable D-013 `AccountContext.secret` is invisible to the sanitizer by construction — own enumerable properties only.

**Reasons.** §15.4 is absolute ("never appear in … logs", "including at debug level"), so redaction must be structural rather than level-based: whatever the configured level, the same sanitizer runs on every record — proven by firing every leak vector (message interpolation, deep/nested fields, array elements, error payloads incl. cause chains and aggregate members, sensitive key spellings, the D-013 context) at each of the six levels and asserting the marker is absent from the raw serialized line. Pre-sanitizing before Pino is the only placement that covers message strings and value-based markers, which no Pino-side feature reaches; keeping a Pino-side layer as well makes the exposed base instance safe for integrations that bypass the wrapper. Splitting construction-time validation (throw) from emission (never throw) mirrors the trusted-wiring vs. runtime-diagnostics distinction of D-013/D-020. The structural sink supertype avoids a leaf importing server types while giving both seams one tested adapter, including a real `QuotameterApp` wiring test.

**Consequences.** All layers log through `createLogger`'s wrapper methods (`message`, optional data record) and never through `console` or raw Pino; task 146 wraps `logger.pino` for HTTP logging (its serializers keep Layer A; request headers with `authorization` are additionally redacted by Pino's own `req` serializer). Adding a sensitive key is a `SENSITIVE_KEY_NAMES` entry plus README/CHANGELOG notes — no decision needed; changing the two-layer split, the level ladder surface, or the seam contract is a new decision. The reload path (068+) calls `setLevel`; composition roots pass known secrets (marker list) at creation and may rotate by rebuilding the logger. Raw-instance callers remain responsible for not logging beyond depth 2 with uninspected keys — the documented boundary of Layer A.

## D-026 — Reload semantics: §6.4 classification table, startup-baseline restart diff, serialized promise-chain reloads (spec §5.2, §6.2, §6.4)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§5.2](plan/SPECIFICATION.md#52-cli-commands), [§6.2](plan/SPECIFICATION.md#62-configuration-contract), [§6.4](plan/SPECIFICATION.md#64-change-application), [§16](plan/SPECIFICATION.md#16-logging-and-diagnostics) · **Tasks:** [068](plan/tasks.md) · **References:** D-014, D-018, D-023, D-024, D-025

**Decision.** `src/config/reload.ts` implements the reload operation with these pinned interpretations: (1) **Boundary.** The reloader is a config-layer module API — `createConfigReloader({ initial, targetPath, env?, filesystem?, logger? })` — with no signal installation: `src/server/main.ts` keeps SIGHUP unhandled and the later assembly task (or CLI 141) wires `process.on('SIGHUP', …)` to `reload()`, following the D-024 readiness discipline; production behavior is unchanged until then. The factory requires the startup load's success result, so §6.2's "invalid startup configuration, refuse to start" stays with the composition root and there is no reload-without-an-incumbent state — "keep the last valid configuration" (§6.2) holds from the first reload on. (2) **§6.4 classification.** `RELOAD_FIELDS` classifies every setting of the D-014 contract: the restart set is exactly the spec's closed list (`server.host`, `server.port`, `auth.mode`, also exported flat as `RESTART_REQUIRED_FIELDS` for the §14.5 "restart required" labels); §6.4's live list is field-granular for `app.*` and scope-granular for `accounts` and `providers` wholesale (the spec speaks of the account list/labels/keys/enabled states and the provider peak-hour schedule as units, and `providers.<id>.requestTimeoutSeconds` governs the next request, so it rides the scope). The two settings §6.4 does not name are decided **live**: `logging.level` (D-025 reserved `setLevel` for exactly the reload path) and `auth.passwordHash` (data checked per authentication attempt, not wired into a listener; §6.4's restart list names the authentication _mode_ only). A unit test fails if a `ConfigSchema` section grows without a classification row. (3) **Wholesale swap, two diff baselines.** A successful reload replaces the effective configuration in one synchronous step — the effective object mirrors the file, and consumers label the reported fields rather than the reloader half-applying sections. `applied` (the result's live half) diffs against the _previous effective_ configuration — what this reload activated; `restartRequired` diffs against the _startup_ configuration — what the running process actually bound — so a second reload of an unchanged file that still differs from startup keeps reporting `pending-restart` until a real restart picks the values up, and returns to `applied` when the file returns to the startup values. The adopted configuration is deep-frozen (the D-013 immutable-in-memory precedent). (4) **Environment re-application (D-023).** Every reload re-runs `loadConfigWithEnv` with a shallow snapshot of the construction-time environment, so an environment-pinned field never flips across reloads and never enters `restartRequired` (the copy, not the live `process.env` reference, is what makes the guarantee structural — runtime env mutation by a library cannot affect it); a file that disappeared rebuilds the configuration environment-only (`fileAbsent: true`) exactly as at startup. (5) **Concurrency.** `reload()` serializes on an internal promise chain: overlapping calls run the pipeline one at a time in invocation order, every caller gets its own result, each run re-reads the file — a SIGHUP burst applies every time. (6) **Result contract.** `{ ok: true, outcome: 'applied' | 'pending-restart', effective, applied, restartRequired }` / `{ ok: false, outcome: 'rejected', problems }` — `problems` verbatim from the D-018 vocabulary (field-addressed, value-free); `reload()` never rejects for configuration problems — only an injected-dependency fault can reject, and the incumbent stays active. (7) **Logging (§16).** With an injected redacting logger: success is one `info` lifecycle event (`configuration reloaded`, carrying `outcome`/`applied`/`restartRequired`), rejection one `warn` (`configuration reload rejected; keeping the last valid configuration`, carrying `problems`), and every successful reload applies `logging.level` through `setLevel` — schema-guaranteed to be one of the four §16 levels, hence unable to throw.

**Reasons.** (1) The layout (D-009) puts configuration mechanics in `src/config/` and composition in `src/server/`; installing SIGHUP from the config layer would invert it, and installing it in `main.ts` now would change terminal-disconnect behavior with nothing to reload yet (the comment task 060 left). (2) §6.4's restart list is explicit and closed, so anything outside it must apply live or reloads would silently ignore operator edits; whole-scope granularity for `accounts`/`providers` matches how §6.4 itself groups them and avoids a diff vocabulary nested to peak-window elements. (3) Diffing restart-requiring fields against the previous reload instead of startup would report `applied` for a second no-change reload while the listener still runs the old port — the diff must measure against what the process runs. (4) D-023's precedence is defined over "environment over file"; re-reading the environment per reload could not change it, and capturing once makes the guarantee structural. (5) Queueing beats coalescing (join-in-flight) because each SIGHUP legitimately re-reads a file that may have changed again, and beats a mutex lock object because the caller-facing contract is simply a promise. (7) §16 names configuration reload an `info` lifecycle event; a rejected reload is a reportable degradation, not a crash — `warn` — and both records carry only value-free data by construction, so the redacting logger never sees a secret to leak.

**Consequences.** The future composition root loads via `loadConfigWithEnv`, refuses to start on problems (§6.2), constructs the reloader with a logger, and wires SIGHUP/CLI `reload` (task 141) to `reload()`, printing `applied`/`pending-restart`/`rejected` with the problem list; the settings UI (Stage 13) renders `RESTART_REQUIRED_FIELDS` labels and `restartRequired` per reload. Live-application by downstream services (polling interval, retention, accounts, peak hours) is re-reading `current()` — their construction tasks own the wiring; nothing in this module pushes into services. The `applied` field list and the two log messages are pinned by `test/integration/config-reload.spec.ts` and are part of the English-only contract; adding a configuration field requires a `RELOAD_FIELDS` row (guarded by the coverage test) plus a CHANGELOG entry. Changing the outcome vocabulary, the baselines, or the serialization semantics is a new decision.

## D-027 — Umzug over `node:sqlite`: injected forward-only harness with atomic per-migration journaling (spec §3, §11.4)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§3](plan/SPECIFICATION.md#3-technology-and-packaging), [§11.4](plan/SPECIFICATION.md#114-migrations-and-backup-behavior) · **Tasks:** [078](plan/tasks.md) · **References:** D-002, D-016, D-017, D-021

**Decision.** Task 078's verification of the spec-preferred library succeeded — `umzug@^3` drives migrations over `DatabaseSync` with no blocker — and the reusable harness lands as `src/storage/migrations.ts`, pinned as follows: (1) **Library** — `umzug` becomes a runtime dependency (spec §3 names migrations a product capability and prefers Umzug). Verified footprint: MIT, `engines.node >=12`, five _direct_ dependencies (`emittery`, `type-fest`, `pony-cause`, `tinyglobby`, `@rushstack/ts-command-line` — the last pulls the Rushstack CLI stack) adding ~25 small pure-JavaScript transitive packages to the tree, mixed MIT-compatible permissive licenses, no native modules and no install scripts; the package itself is CJS-only and is consumed through Node's ESM interop; `npm audit --omit=dev` stays clean. Smaller than it looks for what it buys, but recorded honestly against §3's "keep runtime dependencies minimal". (2) **Injected list, not files** — migrations arrive as `ReadonlyArray<{ name, up(context) }>` code, never file globs; the compiled package (§3 packaging: no install-time machinery) carries the set, and future migrations are additions to a typed array. Umzug sorts glob inputs but not injected arrays, so the runner itself applies **name order** (default code-unit string comparison) and rejects blank/duplicate names and a non-function `up` at construction — before touching the database (D-013 wiring-check style). (3) **Journal** — the storage adapter implements Umzug's three-method contract (`logMigration`/`unlogMigration`/`executed`) with the bookkeeping table `schema_migrations (name TEXT PRIMARY KEY, applied_at INTEGER NOT NULL) STRICT` (§11.2 strict-tables convention; §11.1 integer-UTC-epoch-millisecond timestamps): plain `INSERT` so a duplicate record fails loudly on the primary key, `ORDER BY name` reads, and `unlogMigration` implemented as a working `DELETE` only to satisfy the library's storage contract — the runner exposes **no `down`** (§3 forward-only). (4) **Atomic apply + record** — `up()` wraps each migration in one `BEGIN IMMEDIATE` … `COMMIT` transaction around Umzug's per-name slice, which spans the migration body and the storage adapter's journal insert: any failure — including a failing journal write — rolls the migration back whole and leaves it pending for the next startup, making "applied but unrecorded" and "recorded but not applied" unreachable. This is the D-016 interrupted-write standard applied to schema changes, and the reason the transaction lives in the runner rather than inside the adapter: Umzug's fixed `up()`-then-`logMigration()` sequence must be spanned by one caller-owned transaction. (5) **Seams and scope** — the runner owns no connection (task 079 supplies the `DatabaseSync` with the §11.1 pragmas) and takes the D-021 `Clock` for deterministic `applied_at` (optional, defaulting to the system clock per the optional-seam precedent of D-020; the composition root passes the shared clock); `createMigrationStorage` is exported as the standalone journal seam for future tooling, documented as atomic only under the runner. `VACUUM INTO` backups, three-generation retention, and the newer-schema refuse-to-start check remain task 092's; concurrency needs no migration lock because migrations run at startup under the D-017 single-instance lock.

**Reasons.** The verification asked for a forward migration applied and recorded in a disposable database; Umzug delivered exactly that with a three-method storage contract small enough to implement over `DatabaseSync` without a second driver or shim, so the high bar for rejecting the spec-preferred library was never approached. Injecting migrations as code keeps the §3 packaging constraints (no install-time build, no filesystem assumptions in the shipped CLI) and removes umzug's glob/TS-loading machinery from the runtime path while retaining its ordering/pending/journaling semantics. Per-migration transactions match the established crash-safety posture (D-016) and SQLite's transactional DDL: a failed migration re-runs cleanly instead of colliding with its own partial artefacts — the classic migration-library failure mode. Name-ordered application makes ordering deterministic regardless of list authoring, mirroring umzug's own glob behavior. The no-`down` surface encodes §3's forward-only rule structurally rather than by convention.

**Consequences.** Tasks 080–087 add migrations as array entries (`000N-…`-prefixed names, statements through `context.database`, no transaction management inside migrations — the runner's transaction wraps them and a nested `BEGIN` fails loudly); task 079's connection module hands the runner an already-configured database; task 092 composes `VACUUM INTO` backups and the newer-schema refusal on top of `pending()`/`executed()` and raw journal reads. `schema_migrations` is an on-disk contract: renaming it or changing its columns requires a successor decision. Integration tests (`test/integration/migrations.spec.ts`) pin the verification claims — name-ordered application, journal recording with epoch timestamps proven through an independent connection, no-op re-runs, pre-seeded journal rows respected, pending/executed reporting, brand-new-database behavior, per-migration commit granularity (a later failure keeps earlier migrations applied and recorded), rollback of a failed migration and of a failed journal write, the nested-`BEGIN` refusal, and construction-time list validation.

## D-030 — Storage connection: injected data dir, readback-verified §11.1 pragmas, idempotent close (spec §11.1)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§11.1](plan/SPECIFICATION.md#111-database-settings) · **Tasks:** [079](plan/tasks.md) · **References:** D-009, D-013, D-020, D-027, D-028

**Decision.** `src/storage/connection.ts` implements the database connection with these pinned interpretations: (1) **The data directory arrives injected; storage owns only the file name.** `openStorageConnection({ dataDir })` opens `<data>/quotameter.sqlite`, where `dataDir` is the already-resolved directory from 063's `resolvePaths` — storage may not import `src/config/` (D-009 layer gate), so re-resolving XDG paths is structurally impossible and the spec's file name lives in one exported constant (`DATABASE_FILENAME`, an on-disk contract pinned in tests the way `MIGRATIONS_TABLE` is, D-027), joined by the exported `databaseFilePath(dataDir)` (the `lockFilePath` precedent of task 074). (2) **Pragmas are applied as `PRAGMA` statements and verified by readback; a database that cannot hold a required setting refuses to open.** Driver constructor options for these settings are incomplete on the pinned minimum runtime (Node 22.13.0), and `journal_mode=WAL` is the one setting with a silent-fallback failure mode — `:memory:` reports `memory`, a WAL-incapable filesystem falls back to `delete` — while §11.1's atomic snapshot+metric+event transactions and the §11.4 migration journal both rest on WAL actually being engaged. So each of `busy_timeout=5000`, `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON` is executed then read back at open, and a mismatch is a startup failure naming the pragma and the path. Application order is fixed: `busy_timeout` first so engaging WAL on a busy existing database waits within the §11.1 budget instead of failing immediately. The values are spec-pinned constants (`BUSY_TIMEOUT_MS = 5000`), deliberately **not** injectable options — §11.1 admits no configuration. An optional `openDatabase` seam (default `new DatabaseSync`) exists solely so tests can prove the refusal against a real `:memory:` database; production callers never pass it (the optional-seam precedent of D-020/D-021). (3) **Wrap, don't re-export: a closeable handle owning close semantics.** The connection exposes `{ database, path, isOpen, close() }` where `database` is the raw `DatabaseSync` — the exact type D-027's runner receives — because close behavior must be owned: Node 22.13 has no `isOpen` on the handle and throws `ERR_INVALID_STATE` on a second `close()`, so the wrapper tracks openness itself and keeps `close()` idempotent, tolerating a close that follows a direct `database.close()` by a consumer (the D-020 shutdown sequence closes storage after the drain and must survive repeated calls). (4) **No directory creation.** The startup path creates the data directory when acquiring the single-instance lock (074's `ensureDataDir`, recursive `0700`); §11.1's "create it automatically" refers to the database file. A missing parent directory is reported loudly — full path, original error as `cause` — and nothing is created.

**Reasons.** (1) The layer rules make injection the only legal shape, and it doubles as the right test shape: disposable temp directories pass as `dataDir` with no path mocking. (2) Statement-based application is stable across driver versions the way constructor options are not, and readback converts "configure WAL" from a fire-and-forget write into a verified precondition — the difference surfaces exactly on the databases that would otherwise run degraded. Per-connection settings (`busy_timeout`, `synchronous`, `foreign_keys`) cannot silently fail outside a transaction, but verifying them costs four cheap statements at startup and self-documents the §11.1 contract as one table. (3) A bare re-export could not carry `isOpen`/idempotent `close()` on 22.13; a deeper wrapper that hides `DatabaseSync` would break the D-027 runner seam for no benefit. (4) Two creators of the same directory is a permissions race; 074 already owns creation with the right mode, and a silent `mkdir` in storage would mask operator mistakes (a mistyped `QUOTAMETER_DATA_DIR` creating a fresh tree instead of failing).

**Consequences.** The composition root (task 090+) calls `openStorageConnection({ dataDir: resolvePaths(env).dataDir })`, hands `connection.database` to `createMigrationRunner`, and closes the connection in its shutdown sequence after the drain. Task 088's repository receives the same `DatabaseSync`. `test/integration/connection.spec.ts` pins the verification: file created at the spec path, WAL proven through an independent connection and across reopen, per-connection settings read back through the handle (note `PRAGMA busy_timeout` reports under the column `timeout`), a real foreign-key violation failing, idempotent/external-tolerant close, the missing-parent refusal without side effects, the `:memory:` WAL refusal via the seam, the corrupt-file driver failure surfacing with the path and `cause` (a non-SQLite file passes the constructor's lazy header read and first fails mid-pragma), and the runner seam. Residual untestable branch (D-028 convention): `close()`'s rethrow of a non-`ERR_INVALID_STATE` close failure is unreachable without a throwing handle stub — recorded here rather than suppressed. `:memory:` databases are out of scope by construction (they cannot satisfy §11.1); tests that need disposable databases use temp directories.

## D-031 — Versioned migration names and the schema-version status layer over the 078 journal (spec §11.4)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§11.4](plan/SPECIFICATION.md#114-migrations-and-backup-behavior), [§11.2](plan/SPECIFICATION.md#112-required-logical-tables), [§11.1](plan/SPECIFICATION.md#111-database-settings) · **Tasks:** [080](plan/tasks.md) · **References:** D-013, D-027

**Decision.** Task 080 lands the bookkeeping and version-check semantics §11.4 requires on top of D-027's journal — as extensions of `src/storage/migrations.ts`, not a second journal or a sibling module (one contract family, and the module header already names tasks 080–087 as its growers). Four rules: (1) **Versioned names** — a migration name is `<version>-<description>` with a 1–8 digit prefix (sequential `0001-…` and date `20261030-…` conventions both fit; the cap keeps `Number` parsing exact) and a non-blank description; `migrationVersion(name)` parses it and throws on malformed input (a
version prefix of 0 included — version 0 is reserved for the empty journal,
the "nothing applied yet" state). In application (name) order, versions must **strictly increase** — a single rule that subsumes version uniqueness and keeps D-027's code-unit name ordering coherent with numeric version order (`10-…` sorted before `9-…` is rejected instead of silently misapplied). The check is folded into `createMigrationRunner`'s construction validation, deliberately **tightening 078's contract** (any non-blank unique name → versioned increasing names): coherence must hold wherever migrations are applied, not only where a status is computed; every 078 fixture already satisfied the rule. (2) **Canonical set** — `MIGRATIONS` is the application's one migration list, empty at task 080 (the journal table comes from the storage adapter, not a migration); tasks 081–087 append entries. `supportedSchemaVersion(set)` is the version the running application supports (`0` for the empty set — the pre-081 state of a fresh database is legitimately "schema 0, up-to-date"). (3) **Raw journal read** — `appliedMigrations(database)` returns every journal row `{ name, appliedAt }` in name order, including entries the running application does not know (078's `executed()` deliberately filters those out); it is read-only, never creates the journal table, and rejects a non-integer `applied_at` — evidence from a journal this app did not write must not flow out as a fake number. (4) **Version check** — `schemaVersionStatus(database, migrations)` answers the comparison: `supportedVersion`, `appliedVersion`, `relation` (`'up-to-date'`/`'behind'`/`'newer'`), and `newerThanSupported` (the evidence rows). Version maxima decide `'newer'`; name membership decides the rest (a set migration missing from the journal is `'behind'` work even at equal maxima); a journal row with a malformed name throws rather than silently reading as version 0.

**Reasons.** The done-condition — applied migration versions persisted and queryable — needs a version concept the 078 harness does not have (names are opaque to it), and §11.4's "newer than the running application supports" needs a comparison rule plus visibility of journal entries _beyond_ the injected list, exactly the rows 078's `executed()` hides. Deriving everything from name prefixes keeps one source of truth (the journal D-027 pinned as the on-disk contract) and zero extra schema; versions exist as an interpretation, not as a second table to drift. Strict-increase validation at construction is the D-013 fail-fast style and makes the runner's name ordering provably version-coherent rather than coherent by naming convention. Keeping the metadata in `migrations.ts` avoids a module split that would still share every type and constant.

**Consequences.** Task 092 builds the `VACUUM INTO` backups and the refuse-to-start check on `schemaVersionStatus` (`'newer'` + `newerThanSupported` for the message) and `appliedMigrations()`; the startup wiring applies while the relation is `'behind'`. Tasks 081–087 add one `NNNN-…` entry each to `MIGRATIONS` and owe the spec's "migration-forward test from the previous supported schema" — the grown-set pattern is already pinned in `test/integration/migrations.spec.ts`. Databases carry no new on-disk artefact; `schema_migrations` remains the only bookkeeping table. The runner now rejects sets it previously accepted (unversioned or non-increasing names) — a deliberate breaking change of an internal seam recorded here; nothing in `src/` consumed the old lenience.

## D-032 — The `accounts` table: minimal §11.2 column set, GLOB-enforced D-014 charsets, enum + timestamp archive state, no credential columns (spec §11.2)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§11.2](plan/SPECIFICATION.md#112-required-logical-tables), [§8.2](plan/SPECIFICATION.md#82-accounts), [§11.1](plan/SPECIFICATION.md#111-database-settings), [§15](plan/SPECIFICATION.md#15-security) · **Tasks:** [081](plan/tasks.md) · **References:** D-014, D-021, D-027, D-031

**Decision.** `0001-accounts` — the first entry of the canonical `MIGRATIONS` list (schema version 1) — creates the `accounts` table as a single STRICT `CREATE TABLE` through `context.database` (no transactions inside; D-027), with these pinned interpretations: (1) **Column set exactly §11.2's list** — `id TEXT PRIMARY KEY NOT NULL`, `provider_id TEXT NOT NULL`, `label TEXT NOT NULL`, `plan_name TEXT` (nullable; named after §8.4's `planName` and the snapshots vocabulary), `status TEXT NOT NULL`, `created_at INTEGER NOT NULL`, `archived_at INTEGER` — nothing else; the repository is task 088, future-proofing columns belong to future migrations. (2) **Id charsets in SQL**: `id` and `provider_id` carry the D-014 account-id pattern `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` as named CHECK constraints encoded with case-sensitive GLOB (`GLOB '[A-Za-z0-9]*'` for the first character, `NOT GLOB '*[^A-Za-z0-9_-]*'` for the charset, `BETWEEN 1 AND 64` for the length) plus an embedded-NUL guard (`instr(x, char(0)) = 0` — SQLite's GLOB and `length()` stop at a NUL while the stored bytes do not, so without the guard `'a\0b'` would pass as `'a'`; found in review). For `provider_id` this CHECK is the charset **gate**, not a redundant mirror: the configuration field that lands there (`accounts[].providerId`) is only `minLength: 1`, while D-014's ID_PATTERN binds provider record keys — a different surface. Verified empirically: a number bound for the TEXT id is affinity-rendered with a decimal point (`'123.0'`) before CHECK evaluation, so numeric ids cannot slip through either. (3) **Archive state as enum-plus-timestamp, tied** — §11.2 names both "active/archived status" and "created/archived timestamps" and demands constraints for enum values, so `status` is the closed `accounts_status` enum while a composite `accounts_archive_state` CHECK makes the pair drift-proof: `archived` always carries `archived_at`, `active` never does. Archiving is an UPDATE (§8.2 archive-not-delete); rows and their history stay queryable. `plan_name` follows the §8.4 `planName` shape — absent or non-blank, never `''` (`accounts_plan_nonempty`). (4) **No credential columns** — §11.2 "Credentials are not stored here" (also §11.1, §15.4); `test/integration/accounts.spec.ts` pins the exact seven-column set and rejects column names containing credential fragments, so a later migration cannot add one silently. (5) **No `enabled` column** — enable/disable is configuration state (§6.2's account `enabled`), not part of §11.2's storage list; a later migration appends it if the repository ever needs it persisted. (6) **No SQL-side defaults** — timestamps are §11.1 integer UTC epoch milliseconds supplied by the writer from the injected D-021 clock (the journal `applied_at` precedent), never computed by database time functions; `id` declares `NOT NULL` explicitly because SQLite rowid tables would otherwise accept a NULL text primary key. (7) **Named CHECK constraints** — SQLite reports failures by name (`CHECK constraint failed: accounts_status`), keeping violations self-explanatory in logs and precise in tests. (8) **No index and no FK on `provider_id`** — §11.2 names no accounts index (the table is small and configuration-synced), and providers are configuration data (§11.1), not a database table to reference.

**Reasons.** The done-condition — constraints and lifecycle tests pass — plus the task scope ("minimal and additive; no future-proofing") makes the exact §11.2 column list the whole physical design space, and encoding the D-014 charset in the database (rather than trusting writers) makes "stable account id" enforceable at the storage boundary where API-path safety (§13) and history foreign keys (§11.2's cascading deletes) consume it. A single composite CHECK beats a status column alone (no timestamp), a timestamp alone (no enum constraint, contra §11.2's "constraints for enum values"), or an unlinked pair (drift: archived status with a stale NULL timestamp). GLOB is SQLite's only built-in case-sensitive pattern matcher and — with the NUL guard — encodes the anchored regex exactly; the affinity observation was verified against the pinned runtime rather than assumed. Writer-supplied timestamps keep writes deterministic under the injected clock — the same reason `applied_at` is not a `strftime` default. `accounts_plan_nonempty` keeps the table's plan states identical to the §8.4 boundary's (absent-or-non-blank), so the repository never normalizes a state the domain cannot produce. An `archived_at >= created_at` ordering constraint was considered and deliberately rejected: §11.2 does not name it, the injected-clock writer cannot produce a violation, and clock-skew/correction leniency argues against encoding it (recorded from review).

**Consequences.** `MIGRATIONS` is no longer empty: a fresh database now migrates to schema version 1 at startup, `schemaVersionStatus` reports `up-to-date` at version 1 after the run, and 080's test pinning the canonical set as empty now pins the same version-0 semantics with an explicit empty list instead (D-031's planned growth, recorded here as the deliberate breaking change of that test's fixture). Tasks 082–087 append their `NNNN-…` migrations after `0001-accounts` and key their history tables to `accounts(id)`; task 088's repository owns typed reads/writes and must supply timestamps from the clock. The table name, column names, and constraint names are on-disk contract: renaming any of them requires a successor decision. `accounts` lifecycle in SQL is pinned by `test/integration/accounts.spec.ts` (charset boundaries, enum and drift rejections, STRICT per-value typing, duplicate-id rejection, and the §8.2 create → rename → archive flow); CHANGELOG's task-080 line lost its "(currently empty)" parenthetical because the Unreleased block ships after 081.

## D-033 — Invalid-JSON problems never echo V8 input regions: cut at the first double quote (spec §15.4, §6.2)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§15.4](plan/SPECIFICATION.md#154-secret-protection), [§6.2](plan/SPECIFICATION.md#62-configuration-contract) · **Tasks:** [U-003](plan/tasks.md) · **References:** D-018, D-028

**Decision.** `parseJson`'s error mapping (D-018) replaces the tail-anchored snippet regex with a deterministic cut: an invalid-JSON problem keeps only the `JSON.parse` message text before its **first double quote**, minus the residual `, ` / `, ...` separator tail. Reproduction on Node 22.13.0 (V8 12.4) showed D-018's `^(.*), "…" is not valid JSON$` strip covered only the quote-free whole-input shape: every other `Unexpected token` snippet embeds raw input — the whole input when it fits, or a window around the error position with `...` on each truncated side — with inner quotes left unescaped, so `{"apiKey": <secret>}` produced `invalid JSON: Unexpected token 's', ...""apiKey": sk-secr"... is not valid JSON`, a ten-character secret fragment inside the problem. Marker-secret tests pin every snippet shape (whole-input with raw inner quotes, right-, both-, and left-truncated), plus the quote-free whole-input shape (the old strip's one covered case, kept as non-regression) and the position-only families (`… in JSON at position N (line L column C)`), which contain no double quotes and pass through verbatim.

**Reasons.** (1) §15.4 forbids keys in error messages; a snippet region is a verbatim echo of file content and therefore unconditionally unsafe — the observed shape leaked a ten-character marker fragment. (2) Parsing the snippet grammar is fragility without payoff: V8's snippet format has already changed across versions (whole-input vs windowed, ellipsis flanking, unescaped inner quotes), and any pattern that matches the quoted body can be defeated by quotes inside the echoed content. Cutting at the first double quote is total over current and plausible future shapes alike, because the input echo is always the double-quoted region and nothing before it is input. (3) The surviving prefix (`Unexpected token 's'`) is V8's token-name vocabulary — the same single-quoted form used for syntax names (`','`, `'}'`) — and discloses at most one character, which is not a key appearing in an error message; D-018's value-free, field-addressed vocabulary stays intact. (4) Suppressing the position-only families would reduce readability for zero safety gain: they never quote input.

**Consequences.** `invalid JSON` problems for `Unexpected token` shapes now end at the token prefix (`invalid JSON: Unexpected token 's'`); every other message is unchanged. The exact wording is pinned by unit tests, so an engine upgrade that alters V8's message shapes fails loudly and forces a re-review of the new shapes for leaks. The cut lives in `src/config/load.ts` (`withoutInputSnippet`); no other module surfaces `JSON.parse` errors of secret-bearing untrusted input (the single-instance lockfile parser reads its own lock file, never secrets).

## D-036 — The `snapshots` table: one header row per successful run, unique run reference, success linkage via composite FK (spec §11.2)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§11.2](plan/SPECIFICATION.md#112-required-logical-tables), [§8.4](plan/SPECIFICATION.md#84-normalized-snapshot-and-metric-model), [§11.1](plan/SPECIFICATION.md#111-database-settings), [§7.2](plan/SPECIFICATION.md#72-retry-and-error-behavior) · **Tasks:** [083](plan/tasks.md) · **References:** D-014, D-021, D-027, D-031, D-032, D-034

**Decision.** `0003-snapshots` — the third entry of the canonical `MIGRATIONS` list (schema version 3) — creates the `snapshots` table, its spec-named index, and the parent key its foreign key needs, as one STRICT `CREATE TABLE` plus `CREATE INDEX`/`CREATE UNIQUE INDEX` statements through `context.database` (no transactions inside; D-027), with these pinned interpretations: (1) **Column set = §11.2's list plus one FK-carrier** — `run_id`, `account_id`, `collected_at INTEGER NOT NULL` (§11.1 epoch ms, wall-clock per §7.1, writer-supplied, no SQL default), nullable `plan_name`, and `run_outcome TEXT NOT NULL`. (2) **At most one snapshot per run = `run_id INTEGER NOT NULL UNIQUE`** — a plain UNIQUE column, deliberately **not** `INTEGER PRIMARY KEY`: verified empirically on the pinned runtime (Node 22.13.0), a NULL inserted into a NOT NULL _rowid alias_ is silently replaced by a fresh auto-assigned id — the NOT NULL declaration does not close it — which would attach a snapshot to an arbitrary run; the plain UNIQUE column rejects NULL while enforcing the same one-row-per-run identity. The alternative named in the task (synthetic snapshot id + `UNIQUE(run_id)`) was rejected for the same cost D-034 avoided in `collection_runs`: a second identity no query references — task 084's `metric_values` and §11.2's event "snapshot id" key by the snapshot's run. (3) **Success linkage via one composite foreign key** — `(account_id, run_id, run_outcome)` references `collection_runs (account_id, id, outcome)`, a parent key this migration exposes by adding the unique index `collection_runs_account_id_outcome`, with `snapshots_success_only` CHECK-binding the child's `run_outcome` to `'success'`. One constraint proves three §11.2 properties of the record: the run exists, it belongs to the same account, and it succeeded ("one row per successful run"); the parent-side default (`ON UPDATE NO ACTION`) additionally freezes a referenced run's `outcome` and `account_id` against post-hoc UPDATEs, so recorded history cannot be rewritten out from under a snapshot. (4) **`run_outcome` is the one column beyond §11.2's list** — a CHECK-bound constant carried solely so the composite FK can compare against the run's outcome; the D-032/D-034 exact-column-set rule bends only here and only for this, because no combination of the four listed columns can express "per successful run". (5) **Rejected linkage alternatives**: a partial unique parent index (`… WHERE outcome = 'success'`) because SQLite forbids partial indexes as FK parent keys; a trigger because it has no precedent in this schema, adds on-disk objects, and needs totality over the INSERT/UPDATE paths of both tables; a plain run FK + writer contract because it leaves §11.2's stated record property unenforced, against the D-032/D-034 style of encoding exactly the spec-stated properties at the storage boundary; a generated constant column because generated columns are not a sanctioned FK term. (6) **A `WITHOUT ROWID` primary key was also verified viable post-hoc (review finding)** — `run_id INTEGER PRIMARY KEY` in a `WITHOUT ROWID` table rejects NULL and enforces uniqueness on the pinned runtime, without the rowid alias's auto-assign semantics or the autoindex — but the plain-UNIQUE rowid table ships instead: equal enforcement, and the table stays in the same rowid-table family as every other table in the schema (uniform on-disk shape; the hidden rowid nothing references). (7) **The rest transfers from D-032/D-034** — the D-014 charset CHECK with NUL guard on `account_id`, `plan_name` absent-or-non-blank (§8.4's `planName` shape), both foreign keys `ON DELETE CASCADE` (run deletion removes its snapshot; account deletion removes snapshots and runs — §11.2 "use cascading deletion consistently", and D-034 named this cascade explicitly), named CHECK constraints, STRICT typing, and no cross-table time CHECK ordering `collected_at` against the run's timestamps (the clock-skew leniency both prior decisions recorded; CHECKs cannot span tables regardless). (8) **Index naming** — `snapshots_account_time (account_id, collected_at)` mirrors D-034's spec-wording precedent ("snapshots by account/time"); its leading column serves the account-FK cascade scan, the `collection_runs_account_start` pattern.

**Reasons.** The done-condition — "each successful run has at most one snapshot and lookup by account/time is indexed" — makes the uniqueness structural-enforced and the index proven, and the task left the linkage design open. The composite FK was chosen because it is the only SQLite mechanism that expresses "per successful run" as a property of the stored rows themselves (CHECKs cannot span tables, and the plain FK cannot see the parent's outcome), it does so in one constraint that simultaneously closes the account-consistency hole a plain FK would leave, and its parent-side NO ACTION default turns the linkage into immutability of the referenced history — two guarantees the repository (task 088) would otherwise have to uphold alone on every write path. The empirical rowid-alias finding decided the UNIQUE-vs-PRIMARY-KEY question: with `INTEGER PRIMARY KEY`, a single NULL-bearing INSERT from a future writer bug would silently mint a snapshot for an arbitrary run (the precheck attached one to run 1 exactly this way), while the plain UNIQUE column fails loudly — the D-013 fail-fast style applied to schema shape. The one-column deviation from §11.2's list is the price of that totality and is bounded to a CHECK-bound constant that can never hold any other value.

**Consequences.** `MIGRATIONS` carries three entries; a fresh database migrates to schema version 3 at startup, `schemaVersionStatus` reports `up-to-date` at version 3 after the run, and the schema-2→3 forward test §11.4 requires lives in `test/integration/snapshots.spec.ts`. Task 081/082 canonical-set pins in `test/integration/accounts.spec.ts` and `test/integration/collection-runs.spec.ts` were updated to the grown set, and `collection-runs.spec.ts`'s `EXPECTED_INDEXES` gained `collection_runs_account_id_outcome` (D-031's planned growth, recorded here as those tests' deliberate fixture changes). Task 084's `metric_values` and task 085/086's events reference a snapshot by `run_id` (the UNIQUE column is a legitimate FK parent key); task 088's repository owns typed reads/writes, supplies `collected_at` from the injected clock (D-021), and passes the `'success'` carrier value alongside the run reference. The table, column, constraint, and index names (including `collection_runs_account_id_outcome` and `snapshots_account_time`) are on-disk contract: renaming any of them requires a successor decision. Raw `DatabaseSync` test handles default to `foreign_keys=OFF` (D-034's pinned note) — the FK tests set the pragma explicitly.

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§11.2](plan/SPECIFICATION.md#112-required-logical-tables), [§8.4](plan/SPECIFICATION.md#84-normalized-snapshot-and-metric-model), [§11.1](plan/SPECIFICATION.md#111-database-settings), [§11.3](plan/SPECIFICATION.md#113-retention-and-cleanup) · **Tasks:** [084](plan/tasks.md) · **References:** D-010, D-014, D-021, D-027, D-031, D-032, D-034, D-036

(5) **`derived_fields` is a 5-bit mask over D-010's closed `DERIVED_METRIC_FIELDS` order** (used=1, remaining=2, limit=4, percentUsed=8, percentRemaining=16): NULL = absent, 0 = empty set, 0–31 = exactly the power set of the closed set, so a set outside the closed list is unrepresentable — the D-036 house rule that a §8.4/§11.2 property of the record should be structural, not a writer contract. A JSON array encoding was rejected because CHECK constraints cannot express per-element membership (no subqueries; `json_each` is table-valued), which would have left the closed set enforced only by the future repository. `metric_values_derived_present` additionally couples every set bit to its column's presence (`(derived_fields & bit) = 0 OR column IS NOT NULL`, five clauses) — D-010's "listed as derived but the field is not set" record invariant (`findNormalizedMetricProblems`), in SQL; as a side effect an invalid row (all five quota columns NULL) can carry only the NULL or 0 mask. This coupling was added from the review round: the initial DDL omitted it, leaving exactly the kind of boundary-stated property unenforced that this decision's own house rule rejects (review finding, verified empirically — bitwise AND is legal in a STRICT-table CHECK on the pinned runtime). (6) **The denormalization is pinned by the D-036 composite-FK technique**: `(account_id, run_id, collected_at)` references `snapshots (account_id, run_id, collected_at)` `ON DELETE CASCADE` — a parent key this migration exposes through the new unique index `snapshots_account_run_time` — so the copied account and time can never drift from their snapshot: one constraint proves the snapshot exists, the account matches, and the series time matches, and the parent-side NO ACTION default freezes a referenced snapshot's identity against post-hoc UPDATEs. The direct `account_id → accounts(id) ON DELETE CASCADE` FK is kept alongside it, the D-036 both-foreign-keys shape (§11.2's "cascading deletion consistently" names the account path explicitly). (7) **One metric per key per snapshot is structural**: `UNIQUE (run_id, metric_key)` — the storage face of §8.4's "keys are unique within a snapshot"; its autoindex (leading `run_id`) serves the run/snapshot cascade scans, and `metric_values_series_access (account_id, metric_key, collected_at)` — §11.2's "series access" named the D-034 spec-wording way — serves the series queries (§11.3's ≈52k-snapshots-per-account scale) and the account cascade scan; no other indexes. (8) **No range CHECKs on `window_seconds`/`resets_at`**: the §8.4 boundary validates only finiteness for them (D-010), so invented bounds would reject states the domain can produce; the D-034 range precedent encoded §7.1/§7.2 upstream-validated bounds, which these fields lack.

**Reasons.** The done-condition — "constraints prevent invalid enum values and valid empty measurements" — plus the task scope ("columns per §11.2 exactly", minimal and additive) fixes the column list; the design freedom is the constraints, the derived-fields encoding, and the denormalization linkage. Encoding the enums in SQL is §11.2's explicit "constraints for enum values" and makes the §8.4 closed-set rule enforceable at the storage boundary rather than trusted from every future writer. The composite FK was chosen for the same reason D-036 chose it: it is the only SQLite mechanism that expresses "the denormalized columns equal their snapshot's" as a property of the stored rows themselves (CHECKs cannot span tables), and a drifted `collected_at` would silently corrupt every series query the table exists to serve — the series index keys on the copied value. The bitmask was chosen over JSON for the derived-fields closed set because unrepresentable-invalid beats writer-validated-valid whenever SQLite can express it, which the house style has applied three times running (D-032 charset gates, D-034 outcome enum, D-036 success linkage); readability loses to enforcement, and the repository (task 088) owns the names↔bits translation as part of its row mapping. REAL quota columns follow from the D-032 identical-states rule applied to the landed D-010 model: percentages are fractional and the model types all five fields `number`, so the table accepts every finite value the boundary can emit. The one-directional reason coupling follows D-034's test — encode only what the spec states as a property of the record itself — since §8.4's boundary deliberately does not forbid a reason on a valid metric.

**Consequences.** `MIGRATIONS` carries four entries; a fresh database migrates to schema version 4 at startup, `schemaVersionStatus` reports `up-to-date` at version 4 after the run, and the schema-3→4 forward test §11.4 requires lives in `test/integration/metric-values.spec.ts`. ## D-041 — Response sanitization: string-in/string-out, shared logger vocabulary, marker-inclusive 64 KiB byte cap (spec §7.4, §15.4)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§7.4](plan/SPECIFICATION.md#74-sanitized-raw-responses), [§15.4](plan/SPECIFICATION.md#154-secret-protection), [§7.2](plan/SPECIFICATION.md#72-retry-and-error-behavior) · **Tasks:** [102](plan/tasks.md) · **References:** D-013, D-025, D-033, D-038

**Decision.** `src/providers/sanitize.ts` exports `sanitizeRawResponse(body: string, secrets: readonly string[]): string` — the payload-side counterpart of the D-025 logger, consuming the response body exactly as the transport received it plus the call's known secret values (account key and any discovered tokens; blank entries ignored) and producing the storable, displayable text for task 086's `raw_responses` table and task 103's `doctor --raw`. Pinned semantics: (1) **Exact-value redaction is positional, not structural** — every occurrence of every known secret is replaced with `[REDACTED]` in string values at any depth, array elements, substrings of larger strings, **object keys** (a key embedding the secret must not survive serialization), and raw unparsable bodies alike; each secret is scrubbed in **both spellings**, its literal value and its JSON-escaped form (`JSON.stringify(secret)` unquoted, when distinct), so a secret containing quotes or backslashes cannot survive inside a JSON blob embedded in unparsable text; string-literal `replaceAll`, no regex. (2) **Sensitive-name redaction reuses the logger's vocabulary** — `SENSITIVE_KEY_NAMES` is imported from `src/util/logger.ts` and matched by normalized equality (lowercase, non-alphanumerics stripped), so the two sanitizers share one list mechanically and cannot drift. §7.4's eight names (`api_key`, `apiKey`, `authorization`, `secret`, `password`, `access_token`, `refresh_token`, `cookie`) all normalize into it; the logger's extras (session ids, password-change fields) err on the side of redaction and never collide with quota-payload field names (checked against D-038's verified Z.ai shapes: `usage`, `tokens`, `unit`, `number`, `nextResetTime`, `currentValue`, `data.level`). The `tokens` family survives by construction: equality never matches substrings, which is §7.4's explicit "do not redact every field whose name contains `token`" (bare `token`, auth-shaped, stays redacted). The matching function itself is duplicated locally (three lines) because `util/logger.ts` is landed and immutable for this task — the vocabulary, not the helper, is the contract. (3) **The 64 KiB cap is marker-inclusive and byte-exact**: `MAX_PAYLOAD_BYTES = 65536`, measured as `Buffer.byteLength(..., 'utf8')`; oversized payloads end with the deterministic marker `[TRUNCATED at 65536 of <pre-truncation bytes> bytes]`, and the final output including the marker never exceeds 65536 bytes — a hard storage bound for 086. Sanitization runs **before** truncation (the scrubber must see the complete payload; a cut can only remove text). The cut backs up over UTF-8 continuation bytes (never splitting a codepoint or surrogate pair) and drops dangling proper prefixes of `[REDACTED]` (lengths 1–9, repeatedly until stable — payload text can end in a run like `[REDACTED[REDACT`) so no half marker misleads a reader. (4) **Structure preservation is best-effort by design**: a body that parses as JSON is walked structurally and re-serialized **compactly** (no whitespace — the budget goes to data), so a payload whose sanitized form fits stays valid JSON; object entries are re-attached as own properties, so a `__proto__` key from `JSON.parse` survives as an ordinary entry instead of silently setting the prototype (forensic fidelity — the payload is diagnostics, not executable). An unparsable body is scrubbed as raw text only (there are no fields to remove), keeping the §15.4 guarantee — the configured key never appears in a stored response — independent of parsability. Truncated payloads are forensic text, not parseable JSON.

**Reasons.** §7.4 fixes the cap and the redaction floor but leaves the truncation semantics and the key-list question open; the task orders the lists aligned with the logger with any delta justified. Importing `SENSITIVE_KEY_NAMES` (rather than copying §7.4's shorter list) is the stronger alignment: one frozen source, and the delta is one-directional — a superset that errs toward redaction, in the spirit of both §7.4's "as appropriate" and the D-025 logger, while normalized equality is the only rule that satisfies §7.4's anti-over-redaction warning structurally instead of by enumeration. Sanitize-then-truncate ordering, continuation-byte backup, and the partial-marker trim make the cap deterministic and UTF-8-safe for every input; the marker reports the original size because a CLI reader (103) diagnosing a schema change needs to know how much of the payload it is not seeing. Re-serialization over raw-text passthrough for parsable bodies enables name-based field redaction (impossible on text) and compaction; text passthrough for the rest follows from the module's purpose — §7.2 retains these payloads precisely because parsing failed, so unparsable input is a primary case, not an edge.

**Consequences.** Task 086's `raw_responses` writer stores the returned string as-is under a ≤ 64 KiB column budget, and task 103's `doctor --raw` renders it as text (pretty-printing JSON being a display concern); tasks 104/105 hand the sanitizer the raw body with `[account.secret, ...discovered tokens]` — the D-013 context keeps the secret non-enumerable, and the sanitizer's explicit `secrets` parameter is the sanctioned access path. Dual-spelling scrubbing closes the single-escape window (the escaped spelling of the configured key inside an embedded JSON blob), but secrets surviving only in **repeatedly escaped** spellings (double-escaped inside a string-encoded JSON payload) are still not matched — decoding arbitrary nested encodings is out of scope, and §15.4's actual threat (the configured key echoed back once in a response) is covered in both spellings. Distinct object keys whose scrubbed spellings collide keep the last entry — inherent to value-based key scrubbing, identical in the D-025 logger's Layer B. The property tests sidestep marker-coincidence (a generated secret that is a substring of `[REDACTED]` would be spuriously "re-created" by the replacement) by sentinel-wrapping generated secrets — a test-design note, not a module behavior. Marker text, `MAX_PAYLOAD_BYTES`, the imported vocabulary, and the normalized-equality rule are contract: changing any of them requires a successor decision.

## D-042 — The shared HTTP transport: one total §7.2 deadline, streaming 64 KiB cap, self-sanitized error taxonomy (spec §7.2, §8.1, §17.1)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§7.2](plan/SPECIFICATION.md#72-retry-and-error-behavior), [§8.1](plan/SPECIFICATION.md#81-provider-interface), [§17.1](plan/SPECIFICATION.md#171-required-test-coverage), [§15.4](plan/SPECIFICATION.md#154-secret-protection), [§7.4](plan/SPECIFICATION.md#74-sanitized-raw-responses) · **Tasks:** [104](plan/tasks.md) · **References:** D-013, D-021, D-025, D-038

**Decision.** `src/providers/transport.ts` exports `providerFetch(request, options)` — the single GET-only HTTP seam every adapter (099+) uses instead of `fetch` — with these pinned interpretations: (1) **One total deadline** — §7.2 names exactly one timeout value (default 15 s), so `timeoutMs` bounds the _whole_ exchange: DNS, connect, TLS, waiting for headers, and the full body read, implemented as `AbortSignal.timeout(timeoutMs)` composed with the caller's §8.1 signal through `AbortSignal.any`. Signal state is the classification authority, not the rejection shape: a fired deadline yields `TransportTimeoutError`, a fired caller signal `TransportAbortError`, regardless of which DOMException undici surfaces (a mid-body deadline arrives as the timeout signal's own `TimeoutError`; caller aborts as `AbortError` — both verified on Node 22.13.0). No `Clock` injection (D-021): the clock serves business time; fetch deadlines are timers, and tests use real short deadlines. `timeoutMs` accepts any positive finite value — the §7.2 5–60 s _configuration_ range stays where configuration enters (task 062); enforcing it here would make short test deadlines impossible. (2) **Streaming 64 KiB cap** — `MAX_RESPONSE_BODY_BYTES = 64 * 1024`, aligned with §7.4's sanitized-response cap (task 102's precedent): what the adapter received is exactly what §7.4 can store. The body is read incrementally and rejected the moment the accumulated total exceeds the cap (memory is bounded by cap + one chunk); a declared `Content-Length` over the cap fails before any body byte transfers; a body of exactly the cap is delivered. (3) **Content-type gate** — a 2xx must carry media type `application/json` (case-insensitive, parameters ignored) or the transport rejects with `TransportContentTypeError`; a missing header is a failure, so adapters only ever parse bodies the provider declared as JSON. (4) **Taxonomy and sanitization** — every failure extends `TransportError` with a `kind` discriminant for task 105's outcome mapping: `timeout`, `aborted`, `dns` (`ENOTFOUND`, `EAI_AGAIN`), `connection` (`ECONNREFUSED`, `ECONNABORTED`, `EHOSTUNREACH`, `ENETUNREACH`), `socket` (`ECONNRESET`, `EPIPE`, `ERR_STREAM_PREMATURE_CLOSE`, `UND_ERR_SOCKET`, codeless `terminated`), `network` (anything else), `http-status`, `response-too-large`, `content-type`. Errors are self-contained by construction: no URL, no request headers, no raw `cause` — only the machine `causeCode` survives, because Node/undici network messages embed `host:port` and may embed more in future runtimes. The only retained server strings (status text, raw `Retry-After`, observed content type) are scrubbed against the request's own credential material (whole sensitive-header values plus the credential-after-scheme for `Authorization`-style headers, matched with the D-025 `SENSITIVE_KEY_NAMES` vocabulary extended by one HTTP-specific rule — the `X-` extension prefix is stripped before the normalized-key lookup, so `X-Api-Key` stays in the scrub set; review finding), so a provider echoing a key back cannot smuggle it into an error (§15.4); marker-secret tests pin every failure class. (5) **Non-2xx = observation** — `TransportStatusError` carries `status`, scrubbed `statusText`, and the raw `Retry-After` value for tasks 106/107; the transport never retries and never parses. (6) **GET-only, `redirect: 'error'`** — the verified D-038 endpoints are stable GETs; refusing redirects removes any cross-origin credential-forwarding reasoning; widening the seam (methods, bodies) is a successor decision. `fetchImpl` is injectable (the logger-destination pattern) so classification is pinned against exact runtime shapes without patching globals.

**Reasons.** The done-condition — mock-server cases for every §7.2-required transport failure — makes real-socket reproduction the acceptance bar, and several design points needed pinning against the runtime rather than assumed: probed on Node 22.13.0, a refused connection is `TypeError: fetch failed` + cause `ECONNREFUSED` (but only on an unprivileged port — port 9 is a fetch-spec bad port producing a codeless `bad port` error), DNS failure is the same shape with `ENOTFOUND`, socket destruction before or during the body surfaces as `UND_ERR_SOCKET`/`terminated`, and undici's fetch does not use `node:http`'s agents — which is why the suite's no-network guard intercepts `*.invalid` hostnames inside its fetch wrapper _before_ DNS resolution, so the guarded integration case honestly pins the guard rejection as kind `network` while the `dns` class itself is pinned by unit tests against the verified `ENOTFOUND`/`EAI_AGAIN` shapes. A single total deadline was chosen over connect/body phase splits because §7.2 provides one number and phase-split timeouts would need two configuration values the spec does not define; `AbortSignal.any` composes without mutating the caller's signal. The transport-level cap is justified independently of §7.4: an unbounded read is a memory-exhaustion vector from a hostile or broken provider, and 64 KiB is the only response size the spec names. Two failure shapes the landed mock server (task 026, untouchable by the disjoint-file-set rule) cannot express — a body trickling slower than the deadline and a socket destroyed mid-body — are produced by file-local `node:http` servers inside the integration spec, still on 127.0.0.1. §17.1's "invalid JSON" bullet stays adapter-side: §7.2 maps invalid payloads to `Format changed` (§7.3 precedence ranks it above `Unreachable`), which is a parse outcome, not a transport class — the transport delivers text and the adapter parses.

**Consequences.** Task 099's Z.ai adapter builds on `providerFetch` and never calls `fetch` directly; task 105 maps `TransportError.kind` to §7.2 collection outcomes (D-034's outcome enum); tasks 106/107 receive `TransportStatusError.status`/`retryAfter` as their inputs. The taxonomy's kind strings, class names, and the no-echo error contract are API for those tasks: renaming any of them requires a successor decision. `DEFAULT_REQUEST_TIMEOUT_MS` (15 000) and `MAX_RESPONSE_BODY_BYTES` (65 536) are the constants the polling configuration (062) and sanitizer (102) align with. The scrub's scheme-aware extraction means a bare credential echoed anywhere in retained strings redacts even when the scheme token is absent. The guard-interception behavior of `*.invalid` is now documented contract for every future transport test (105/106 inherit the same pin).

## D-044 — CLI dispatch skeleton: parseArgs strict parsing, the 0/1/2 exit-code contract, an injected writer seam, and a jiti-compatible launcher delegation (spec §5.2)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§5.2](plan/SPECIFICATION.md#52-cli-commands), [§5.1](plan/SPECIFICATION.md#51-supported-environment) · **Tasks:** [128](plan/tasks.md) · **References:** D-012

**Decision.** Task 128 pins the CLI's mechanical contract, into which tasks 129–145 plug command bodies: (1) **Parsing** — `node:util` `parseArgs` in strict mode (built-in, no new dependency) over per-command option tables declared in `src/cli/commands.ts`; every command automatically gets `-h, --help` — a reserved-name guard in `parseCommandArgs` fails any table that shadows it loudly; options carry an optional `description` rendered in command help; `parseArgs` failure messages are trimmed to their first sentence and decapitalized because Node appends generic `--`-placement advice that buries the actual problem. (2) **Exit codes** — 0 success (including `--help`, `--version`, and the no-arguments general help: an empty invocation is a question, not an error); 1 command failure (a thrown handler error or a not-yet-implemented command — valid usage, missing feature); 2 usage error (unknown command/subcommand/option, missing `service` subcommand, unexpected argument — including a bare end-of-options `--`). (3) **Output** — `console` stays banned in `src/**` (spec §15.4 rule), and the CLI's stdout/stderr product flows through the injected `CliOutput` seam (`systemOutput()` = direct `process.stdout`/`stderr` writes, the pre-logger fatal-diagnostics precedent of `src/server/main.ts`); help and version go to stdout, every error to stderr as `quotameter [<command path>: ]<message>` with a `Try 'quotameter … --help'` hint on usage errors. (4) **Precedence** — at global level `--version` beats `--help`; at command level flags are validated before help is shown, so `status --bogus --help` is a usage error rather than disguised help. (5) **Pluggability** — `runCli(argv, deps)` in `src/cli/main.ts` never calls `process.exit` and takes the version (the launcher reads `package.json`; `src/` cannot import it — the layout test forbids imports leaving `src/`), the output sink, and the whole command table as injections; subcommand nesting is exactly one level (`service install`/`uninstall`), all §5.2 defines. (6) **Launcher** — `bin/quotameter.mjs` keeps its runtime gate first, answers a leading `--version`/`-v` itself (printing exactly the bare package version — the fixed CI install-smoke contract), then delegates via a dynamic import resolved as `mod.runCli ?? mod.default?.runCli` (jiti mounts the TypeScript module as CommonJS during development/tests; the published build is real ESM). The specifier is deliberately `'./../src/cli/main.js'` rather than `'../…'`: jiti's loader hook skips specifiers not starting with `./` or `file://`, and the plain form falls through to Node's resolver, which cannot map the `.js` spelling onto the TypeScript source. An import failure with `ERR_MODULE_NOT_FOUND` (the tarball ships `bin/` without compiled `src/` until the packaging tasks) reports a clear reinstall message and exits 1 instead of a resolver stack trace; any other module failure surfaces as itself. All exits after the gate set `process.exitCode` and let the event loop drain — an immediate `process.exit()` can truncate buffered pipe writes.

**Reasons.** The done-condition — all §5.2 commands in help, unknown commands failing clearly — fixes the command set (init, run, start, stop, restart, reload, status, logs, service install/uninstall, passwd, doctor, in spec order and wording) and leaves parsing, exit codes, output routing, and launcher mechanics as the design space. `parseArgs` strict mode is a standard-library parser with per-command option bags, so no flag grammar is hand-rolled and no dependency added (the task's constraint); its verbose error tail is cosmetic damage contained by the first-sentence trim, pinned by tests on the pinned runtime. The 0/1/2 split is the classic CLI convention (usage ≠ failure) and gives scripts a stable contract before real commands exist; stubs exit 1 because the invocation was valid — silently succeeding (bootstrap's exit-0 "not implemented" line) would mislead automation. The writer seam satisfies both the letter of the `no-console` lint rule and its intent: CLI output is product, not logging, and tests assert exact bytes through a recorder. The version injection keeps `src/cli` free of `package.json` reads (a layout violation) and lets unit tests pin `--version` without filesystem fixtures. The launcher's fast path preserves two landed contracts untouched — the CI assertions that `quotameter --version` prints exactly the package version and that Node below 22.13.0 fails with the gate message naming the minimum — because a static import would hoist above the gate, delegation is dynamic; the `runCli ?? default` shape was verified empirically in both worlds (jiti 2.7 on Node 22.13.0 and real ESM), as was the `./`-prefix requirement.

**Consequences.** `src/cli/` gains `main.ts` (dispatch), `commands.ts` (the table, context/handler types, the shared `notImplemented` stub), `parser.ts` (`parseCommandArgs`, `UsageError`), `help.ts` (pure renderers), and `output.ts` (`CliOutput`, `systemOutput`); `bin/quotameter.mjs` extends to delegation. Tasks 129–145 each replace one `stub(...)` row with a real handler plus its option declarations — the dispatcher, parser, and help renderers pick them up without structural change. The error-line format, exit codes, help layout, and the bare-version `--version` output are CLI contract: changing any of them requires a successor decision. `test/unit/cli-dispatch.spec.ts` pins the dispatch contract in-process (injected recorder and fake tables) and `test/integration/cli-bin.spec.ts` pins the launcher child-process behavior via jiti, extending task 060's runner pattern. The launcher fallback message and the `mod.runCli ?? mod.default` interop are removed by the packaging tasks (184–186) once compiled `src/` ships in the tarball.

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§8.1](plan/SPECIFICATION.md#81-provider-interface), [§8.3](plan/SPECIFICATION.md#83-zai-coding-plan-integration-contract) · **Tasks:** [098](plan/tasks.md) · **References:** D-013, D-038, D-042, D-047, D-048, D-049

**Decision.** `src/providers/zai-coding-plan/` (the first adapter island: `index.ts` barrel, `provider.ts` skeleton, `validate.ts`) implements `validateCredentials` per the dossier's endpoint-4 rule and pins what that rule leaves open. **Reasons.** The dossier (D-047's endpoint-4 paragraph) fixes the request, the status-based rule, the A3 assumption, the Authorization-only header set (A7), and the no-retry/single-GET discipline; what it leaves to this task is the boundary representation. The gates-on-2xx reading is forced by mandating `providerFetch`: the transport resolves only for 2xx JSON within the cap, so "valid" is exactly "the verified flow delivered a 2xx" — the alternative (treating a gate-failing 2xx as valid) would require bypassing the shared transport. Rejected-vs-unavailable must not collapse (§7.2 keeps them apart for polling: `Auth rejected` pauses polling, `Unreachable` does not), and unavailability must not read as a verdict on the key. The key-never-logged guarantee (§8.1/D-013) is preserved compositionally: errors are built only from static English plus transport fields D-042 already scrubbed against the request's own credential material, and `account.secret` is read exactly once, into the header.

**Consequences.** The adapter's later tasks (099/100) add `fetchSnapshot` and mapping without touching `validate.ts`; composition-root registration (a later assembly task) imports only the island barrel. The `kind` vocabulary, the two error classes' fields, the default endpoint URL, the options names, and the stub message are contract: changing any requires a successor decision. A first observed bad-key response that is not HTTP 401/403 (A3's reopen trigger — e.g. an envelope-encoded rejection reading 200 + error `code`) requires a new dated dossier section, a D-047/D-052 successor, and new fixtures before the classification may change. **Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§7.2](plan/SPECIFICATION.md#72-retry-and-error-behavior), [§7.4](plan/SPECIFICATION.md#74-sanitized-raw-responses), [§8.1](plan/SPECIFICATION.md#81-provider-interface), [§8.3](plan/SPECIFICATION.md#83-zai-coding-plan-integration-contract) · **Tasks:** [099](plan/tasks.md) · **References:** D-010, D-025, D-040, D-041, D-042, D-047, D-048, D-049, D-052

## D-054 — Mutation-report rendering: one committed renderer, normalized status vocabulary, loud failure on the unknown (spec §4.4, §17.3)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§4.4](plan/SPECIFICATION.md#44-cicd-and-supply-chain-safeguards), [§17.3](plan/SPECIFICATION.md#173-required-test-coverage) · **Tasks:** [U-005](plan/tasks.md) · **References:** D-045

**Decision.** The rolling `mutation-report` issue body is rendered by a single committed script, `scripts/render-mutation-report.mjs`; the workflow's "Render report markdown" step is a thin `node scripts/render-mutation-report.mjs > /tmp/mutation-report.md` call, and the script doubles as the local verifier (first CLI argument overrides the default `reports/mutation/mutation.json` path, so any downloaded artifact re-renders by hand — the one-liner is documented in `docs/mutation-testing.md`). Status handling: (1) **Canonical vocabulary is the mutation-testing-schema `MutantStatus` enum as Stryker serializes it** — PascalCase `Killed`, `Survived`, `Timeout`, `NoCoverage`, `CompileError`, `RuntimeError`, `Ignored`; the exact lowercase spelling of each is accepted as a defensive alias, and **anything else aborts the render with a non-zero exit naming the status and file**. A Stryker vocabulary change must break visibly, never silently re-zero the report (the failure mode of issue #5's run 41054956364, whose inline renderer tallied PascalCase statuses against lowercase keys). The old script's camelCase keys (`timedOut`, `noCoverage`) are deliberately not aliases — no producer ever emitted them; accepting them would legitimize the bug's own vocabulary. (2) **Score semantics pinned to the documented formula** — detected = Killed + Timeout, total = every mutant in the JSON, score = detected/total at one decimal, per file and overall; a zero-mutant report renders `—` rather than dividing by zero. Error statuses (RuntimeError/CompileError) count in the denominator and as neither detected nor survived. (3) **Error-status visibility** — their counts are always in the summary line, and when non-zero an extra bullet lists `file (count)` pairs sorted by count descending, then file name (the reference run's 5 RuntimeErrors all sit in `src/services/polling-outcomes.ts`). (4) **Survived triage list order is pinned** — report-JSON file iteration order, mutant order within file, 200-row cap with an explicit overflow line (previous behavior, now actually reachable). (5) **Verification split** — the unit tests (`test/unit/render-mutation-report.spec.ts`) pin the format and every number over a synthetic all-statuses report (happy path, lowercase equivalence, alias acceptance, loud failure on unknown statuses including `toString`, cap, error-file ordering, zero-mutant edges) and run in `make check`; full-artifact verification against a real downloaded `mutation.json` is the manual pre-landing gate, not a committed fixture — a 3681-mutant artifact is generated output and would bloat the repository.

**Reasons.** The inline heredoc was the root enabler of the bug: untestable and unrunnable outside the workflow, it shipped with a case mismatch no local harness could catch, and the artifact numbers (85.6% = 3150/3681, 497 Survived, 29 NoCoverage, 5 RuntimeError) were only recoverable by re-deriving them from the JSON. Extracting one renderer gives the workflow, the unit tests, and hand verification the same code (the workflow's inline copy and a separate verifier script would drift or duplicate). PascalCase + lowercase aliases cover both real spellings the renderer may ever see without a vocabulary audit; the loud abort covers everything else, which silent tallies provably do not (the fallback `tally[m.status] = …` created unseen keys and read zero forever). The score formula matches `docs/mutation-testing.md`'s published semantics ("detected / total, detected = killed + timed out") and reproduces Stryker's own 85.6% verdict for the reference run, so no documentation meaning changes — only the numbers become true.

**Consequences.** Renderer format changes (bullet wording, table columns, cap size, ordering) are contract-visible in the issue body and must update the unit tests' expected markdown in the same commit. A future Stryker status (or a casing change beyond exact lowercase) fails the workflow's render step with the offending status named in the log instead of publishing wrong numbers; extending `STATUS_ALIASES` is a successor decision. If ignore comments ever reach the codebase and `Ignored > 0` in a report, whether ignored mutants belong in the score denominator (Stryker's own metrics exclude them; this renderer counts them per the documented formula) must be revisited in a successor decision. The workflow's artifact-upload and issue-upsert steps are unchanged; the end-to-end re-render lands with the next scheduled run or a manual dispatch after this reaches `master`.

## D-055 — Mutation-triage exclusions and the score's scoreable denominator: in-code Stryker ignores are deliberate artifacts, and the renderer adopts Stryker's own formula (spec §17.3)

**Date:** 2026-10-30 · **Status:** Accepted · **Spec:** [§17.3](plan/SPECIFICATION.md#173-enforced-quality-thresholds) · **Tasks:** [U-006](plan/tasks.md) · **References:** D-045, D-054

**Decision.** Two rules settle how mutation-triage exclusions work and how the report scores them. (1) **Equivalent or intentionally unspecified mutants are excluded in code, next to the line, with `// Stryker disable next-line <Mutators>` comments carrying a short English reason** — the exclusion is a reviewed artifact that travels with the code, per `docs/mutation-testing.md`. Stryker's ignore granularity is one line per mutator name, so an exclusion necessarily also covers line-mates of an equivalent mutant (for example, a `ConditionalExpression` ignore on a line where one variant is equivalent and another killable); the reason must say so when it happens, and the killing tests for those behaviors stay in the suite so removing the directive re-arms them. Exclusions are reserved for mutants with no observable behavior difference (dead return values, flags re-asserted by a later freeze, normalization results invisible to the parser, error inputs the runtime cannot produce) — never for behaviors a test could pin, and thresholds are never lowered instead. (2) **The report renderer's mutation score switches to Stryker's own formula** — `score = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage)`, per file and overall, replacing D-054's `detected / every-mutant` denominator: `Ignored` and the error statuses (`RuntimeError`, `CompileError`) leave the denominator (verified against the installed Stryker's `mutation-testing-metrics` `calculateMetrics`, where `mutationScore = totalDetected / totalValid` with `totalValid = detected + survived + noCoverage`). Both stay visible as counts — the summary line keeps the ignored and error tallies, error files keep their bullet, and the per-file table keeps the raw mutant total — so nothing becomes invisible, only the score stops disagreeing with the verdict line, which comes from Stryker's own threshold check.

**Reasons.** D-054 flagged this exact question as a successor decision the moment ignore comments first appear; U-006 is that moment (59 of the triaged run-41054956364 survivors are equivalents across `config-validation.ts`, `transport.ts`, `single-instance.ts`, and `registry.ts`). Keeping `Ignored` in the denominator after that would have made the issue's score strictly lower than Stryker's own — a self-inflicted repeat of issue #5's class of bug (numbers contradicting the verdict), and a permanent tax on honestly documenting equivalence. Matching Stryker is the self-consistent choice because the verdict, the break threshold, and the clear-text score the workflow logs all come from Stryker's formula; a diverging denominator could eventually flip the issue's optics red while Stryker stays green. In-code placement of the exclusions (over a config-level `excludedMutations` list) keeps every suppression one review-comment away from the code it suppresses, and the line-granularity cost is accepted knowingly: it is bounded, documented per directive, and recoverable — deleting a directive restores the mutants, and the suite's behavior pins then kill them again.

**Consequences.** The rolling issue's score line now reads `X% (D detected of S scoreable mutants …; ignored and error-status mutants are excluded, see D-055)`; `docs/mutation-testing.md`'s "How to read the report" section describes the scoreable denominator, and `test/unit/render-mutation-report.spec.ts` pins both the changed wording and an ignored-heavy fixture (50 killed + 50 survived + 30 ignored + 20 runtime errors ⇒ 50% of 100 scoreable, 150 total in the table). Stryker runs no longer generate the excluded mutants at all, so the raw totals shrink in future artifacts while the deliberate-exclusion inventory lives in the code. Adding a new `// Stryker disable` requires the same discipline as this task: a reasoned audit entry in the landing commit, tests for every line-mate behavior that stays killable, and no use of ignores as a substitute for a test that can actually be written. Whether equivalent-mutant exclusions should also be enumerated somewhere machine-readable (beyond Stryker's own JSON) stays open; nothing today consumes such a list.
